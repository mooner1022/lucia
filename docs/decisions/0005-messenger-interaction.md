# 0005. 메신저 대화 완성도: 파일 주고받기, 타이핑 표시, 도구 사용 알림, 나눠 보내기

- 날짜: 2026-11-16
- 상태: 확정
- 결정 방식: 사용자 요청("메신저 인터렉션의 완성도를 높혀"): 이미지·PDF 등 파일 받기와 확인, 생각·답변 중 타이핑 표시, 도구 사용 기록과 짧은 메시지, 에이전트가 파일을 첨부해 보내기, 구분자(`\n%%\n`)로 나눠 먼저 보내기.

## 실측(2026-11-16, VM 안 claude 2.1.325, haiku)

- stream-json 입력의 user 메시지 `content`에 `image`(base64)와 `document`(base64 PDF) 블록을 넣으면 모델이 읽는다. 3 KB 시험 파일은 물론 4.8 MB·7 MB PNG와 8.7 MB PDF도 읽었다. `sbx exec -i` stdin으로 약 18 MB를 넘겨도 6초 만에 끝났다.
- 깨진 PDF를 보내면 API가 거부한 것을 모델이 그대로 말하고 실행은 성공으로 끝난다. 같은 세션을 다시 이어 쓸 수 있었다(세션이 망가지지 않는다).
- `--include-partial-messages`를 켜면 `stream_event`로 텍스트 델타와 도구 입력 델타(`input_json_delta`)가 온다. 도구 입력도 조각으로 오므로 `report_result`의 `summary`를 받는 대로 풀 수 있다.

## 결정

- **파일 받기**: Discord DM의 첨부를 받는다(글 없이 파일만 와도 받는다). 소유자 확인 뒤, 받을 때 바로(Discord CDN 주소는 만료된다) 내려받아 `<data_dir>/files/in/`(0700/0600)에 둔다. 내려받을 때 크기 상한을 지킨다. 받을 주소는 Discord CDN 호스트만 허용한다.
- **여는 방법**: 파일을 VM에 두고 읽기 도구를 여는 대신, **요청 메시지에 내용 블록으로 싣는다.** 그래서 내장 파일 도구를 열지 않고 보호 영역(훅)도 그대로다.
  - 이미지(PNG·JPEG·GIF·WebP, 10 MB까지): `image` 블록.
  - PDF(10 MB까지): `document` 블록.
  - 상한은 실측한 크기(7 MB 이미지, 8.7 MB PDF)를 크게 넘기지 않게 잡았다. 받는 것은 30 MB까지이고, 넘는 것은 받아만 두고 "너무 커서 열지 않았다"고 알린다.
  - 텍스트 계열(txt·md·csv·json·로그·코드 등, UTF-8, 256 KB까지 읽고 넘으면 자른다): 글로 싣고 `<external_data>`로 감싼다.
  - Office 문서(docx·xlsx·pptx): 압축을 풀어 글만 뽑는다(풀린 크기와 항목 수에 상한).
  - 그 밖(음성·영상·실행 파일 등): 받아 두고 "받았지만 열 수 없다"고 알린다(이름·종류·크기만).
  - 종류는 확장자와 Discord가 준 MIME, 파일 앞부분 서명(매직 바이트)으로 정한다. 서명이 맞지 않으면 열지 않는다.
- **파일 보내기**: 에이전트는 파일 도구가 없으므로 두 가지만 첨부할 수 있다. (1) 새 MCP 도구 `file_create`로 만든 텍스트 파일(md·txt·csv·json·html·svg·ics 등, 1 MB까지), (2) 이미 받아 둔 파일. `report_result`에 `attachments`(파일 ID 목록)를 더한다. 데몬이 ID를 확인하고 이름을 정리한 뒤 마지막 메시지에 붙여 보낸다. 글을 이미 다 보냈으면 파일만 담은 메시지를 보낸다. 명세의 MCP 도구 목록에 `file_create`를 더한다(메신저로 직접 보내는 도구는 여전히 없다).
- **보관**: 주고받은 파일은 30일 보관하고 매일 백업 루틴 때 지운다. 저장소의 `files` 표에 방향, 이름, 종류, 크기, 해시, 실행 ID를 남긴다.
- **타이핑 표시**: 사용자가 보낸 말을 처리하는 동안(소유자 확인 뒤부터 마지막 메시지 직전까지) 8초마다 타이핑 표시를 보낸다. 나눠 보낸 뒤에는 바로 다시 켠다. 실패해도 실행에는 영향이 없다. 브리핑에는 쓰지 않는다.
- **도구 사용 알림**: 채팅에서 모델이 도구를 부르면(완성된 `assistant` 이벤트 기준) 짧은 한 줄을 작은 글씨(Discord `-# `)로 보낸다. 예: "웹 검색: …", "메일 검색: …". `report_result`는 알리지 않는다. 웹 검색은 활동 기록에도 남긴다(MCP 도구는 이미 남긴다). 브리핑은 알리지 않고 기록만 한다.
- **나눠 보내기**: 채팅 지침에서 답의 자연스러운 지점에 구분자 줄 `%%`(`\n%%\n`)를 넣게 한다. 채팅 실행에만 `--include-partial-messages`를 켜고, `report_result` 입력 델타에서 `summary`를 풀어 구분자가 나오면 그 앞까지 먼저 보낸다. 나머지는 실행이 끝나고 받은 보고로 보낸다.
  - 출력 계약(명세: 자유 텍스트를 그대로 흘리지 않는다)은 그대로다. 보내는 것은 `report_result`의 입력뿐이다.
  - 모든 보고→메시지 경로(채팅, 브리핑, 델타가 없을 때)가 같은 분할기를 쓴다. 그래서 `%%`가 그대로 나가지 않는다.
  - 일부를 보낸 뒤 실행이 실패하면(시간 초과, 보고 없음): 이미 보낸 것은 되돌릴 수 없으므로 "답을 끝까지 만들지 못했다"는 알림을 한 번 보내고, 에피소드에는 실제로 보낸 글을 남긴다.

- **지키는 것**:
  - 보이는 것과 보내는 것이 같다. 모델이 쓴 글(이름, 주소, 제목, 본문)은 이스케이프해 칸 값, 본문, 머리줄에만 넣는다. 제목, 칸 이름, 꼬리말에는 고정 문구와 데몬이 만든 값만 둔다.
  - `\` 이스케이프가 실제로 듣는 것을 본 곳은 일반 메시지 내용뿐이다. 임베드 안(칸 값, 설명)에서도 듣는지는 첫 실제 카드로 확인한다. 제목과 본문에 `**굵게** ||숨김|| [링크](https://example.com)`를 넣은 시험 메일을 요청하고, 카드에서 `\`가 보이거나 서식이 살아나는지 본 뒤 [거절]을 누르면 된다.

- **확인**:
  - 검증을 통과하는 가장 큰 메일을 그려 twilight-validate(Discord 한도 검사)로 확인했다(받는 사람 20명, 긴 주소, 250자 제목, 문장부호만으로 된 8,000자 본문). 본문이 빠짐없이 보이고, 열 때와 닫을 때 조각이 같다.
  - Discord에서 실제로 어떻게 보이는지는 아직 확인하지 않았다. 다음 발송 요청 때 사용자가 확인한다.

## 남는 한계

- 첨부 내용은 compact 뒤에는 요약으로만 남는다(원본 파일은 30일 동안 데몬에 있고, 에이전트가 ID로 다시 보낼 수는 있지만 다시 읽지는 못한다).
- 에이전트가 이미지·PDF를 새로 만들 수는 없다(코드 실행·파일 도구 없음).
- 첨부 파일 속 글(특히 남이 만든 PDF)은 외부 글이다. 사용자 요청이 아닌 지시가 들어 있을 수 있다. 텍스트는 `<external_data>`로 감싸고, 이미지·PDF 앞에는 그 점을 적는다.
- 일상 대화를 메신저처럼 짧은 말풍선으로 나누는 지침, 알림성 글·서버 채널의 나누기, 말풍선 사이 간격(관리 페이지 설정)은 결정 0026에서 더했다.

## 후속(2026-11-19): 모델 API가 응답하지 않을 때

- 사실(운영 기록): 전체 페이지 스크린샷 뒤의 API 요청이 186초 동안 응답 머리를 받지 못했다(`StreamNoResponse`). 그동안 사용자에게는 입력 중 표시만 되풀이됐고, 그 뒤 Claude Code가 다시 보내 이어 갔다.
  - 그림은 628×2000, 132 KB로 평범했다. 전체 페이지 스크린샷 14번 가운데 이 한 번만 그랬다. 그래서 API 쪽의 일시 장애로 본다.
- **알리기**: `claude -p` stream-json의 `system/api_retry` 이벤트(공식 문서 headless "Handle API retries")를 받아 `RunEvent::Retrying`으로 넘긴다.
  - 채팅이면 실행마다 한 번 "모델 서버가 N초 동안 응답하지 않아 다시 요청하고 있어요(1/10). 조금 늦어질 수 있어요."를 안내로 보낸다.
  - 서버 채널에는 올리지 않는다.
  - 받을 곳이 없는 실행(브리핑·루틴)은 로그에만 남긴다.
- **덜 기다리기**: 첫 시도의 응답 머리 대기를 `CLAUDE_STREAM_FIRST_BYTE_TIMEOUT_MS=90000`으로 줄였다 [제안].
  - 공식 문서 기준 기본값은 직접 API에서 180초 + 요청 본문 32KB마다 1초다.
  - 긴 생각은 머리 뒤의 본문이라 이 시간과 상관없다. 다시 보낼 때의 대기는 Claude Code가 정한다.
