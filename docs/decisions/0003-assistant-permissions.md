# 0003. 비서 권한 기준선(메일 읽기·승인 발송, 상용 상시 에이전트 기준)

- 날짜: 2026-11-16
- 상태: 확정. **내장 도구 범위는 결정 0059로 바뀌었다**(사람이 대화 중인 실행에 쉘·파일 도구를 연다).
- 결정 방식: 사용자가 방향을 정했고("나는 Muse나 Dots와 같이 내 일상을 보조하고 지원하는 에이전트를 원하는거야. 내 메일 내역을 조회하고, 내가 명시적으로 승인한 건에 한해 전송도 가능해야 해. 이외에도 권한이 너무 빡빡하게 잡혀있는 부분이 있다면 상용 상시 구동형 에이전트를 기준선으로 하여 완화해."), 세부는 상용 제품의 공개 자료를 기준으로 정했다.

## 기준으로 삼은 것

OpenAI dots와 Meta Muse(둘 다 2026년 가을 출시한 상시 구동 개인 에이전트). 1차 문서가 아니라 2차 자료(제품 비교 블로그, 기술 뉴스)를 읽었다. 기준선을 잡는 데 쓴 공통점:

- 메일·캘린더 읽기와 검색은 묻지 않고 한다. 백그라운드 조사는 읽기 전용이다.
- 메일 발송, 구매처럼 밖에 흔적을 남기는 일은 건마다 묻는 것이 기본이다. dots는 "한 번 승인이 계속 보낼 권한이 되지 않는다"고 하고, Muse는 커넥터별 "항상 허용"을 고를 수 있다.
- 결제·비밀번호 같은 것은 사람이 한다. Muse는 메일 커넥터에서 일회용 코드, 비밀번호 재설정 링크, 로그인 링크를 걸러 낸다.
- 활동 기록(한 일과 받은 허락)을 사람이 볼 수 있다.
- 프롬프트 인젝션은 풀리지 않은 문제로 보고, 승인 확인을 모델 밖에서 강제한다.

## 결정(D9)

| 등급 | 무엇 | 처리 |
|---|---|---|
| 읽기 | 메일 검색·읽기(본문 포함), 캘린더 일정 조회, 웹 검색 | 자동. 채팅과 브리핑 모두 |
| 로컬 쓰기 | 핵심 기억 고치기 | 자동. 채팅과 브리핑 모두 |
| 외부 쓰기 | 메일 발송 | 건마다 Discord 버튼 승인. "항상 허용" 없음. 24시간 안에 답이 없으면 만료(거부) |
| 주지 않음 | 메일·일정 삭제, 결제, 계정 설정 | 도구 자체가 없다 |

- **메일 읽기**: 데몬 MCP 도구 `mail_search`(Gmail 검색 문법), `mail_read`(본문 텍스트, 첨부는 이름만). 일회용 코드·비밀번호 재설정·로그인 링크로 보이는 메일은 본문과 미리보기를 넘기지 않는다(Muse와 같은 취지). 본문은 일정 길이에서 자른다.
- **캘린더 읽기**: `calendar_events`(기간, 검색어).
- **웹 검색**: Claude Code 내장 `WebSearch`. 검색은 Anthropic 서버가 하므로 VM 네트워크 출구를 새로 열지 않는다.
- **메일 발송**: 에이전트는 `mail_send`로 발송 **요청**만 만든다. 데몬이 내용을 고정해 저장하고, 소유자 DM에 카드(보내는 계정, 받는 사람 주소, 제목, 본문 전체)와 [보내기]·[거절] 버튼을 올린다. 소유자가 [보내기]를 누르면 **데몬이** Gmail로 보낸다. 모델은 승인 결과를 기다리지 않는다.
- **브리핑**(사람이 시작하지 않은 실행)은 발송 요청 도구를 받지 않는다(명세: 백그라운드는 쓰기 도구를 허용 목록에서 뺀다).
- **핵심 기억 쓰기를 외부 글을 읽은 뒤에도 막지 않는다.** 앞서 "메일을 읽은 실행은 기억 쓰기를 막겠다"고 제안했으나 버렸다: 상주 세션은 재개되므로 메일 글이 다음 실행 맥락에도 남아, 실행 단위로 막는 것은 의미가 없다. 세션 전체를 교대까지 막으면 기억이 사실상 멈춘다. 대신 밖으로 나가는 모든 쓰기를 사람 승인으로 막고, 기억 개정 이력과 활동 기록을 관리 페이지에 보인다. 상용 제품도 메일을 읽은 뒤 기억 갱신을 막지 않는다.
- **활동 기록**: 메일 검색·읽기, 일정 조회, 발송 요청·승인·거절·만료·발송 결과, 핵심 기억 변경을 저장소에 남기고 관리 페이지에 최근 것부터 보인다.

## 명세와 다른 점

- **3단계의 승인 버튼을 당겨 온다**(메일 발송만). 명세 3단계 완료 기준 중 "무응답 승인은 거부로 끝난다"를 이 경로에서 지킨다.
- **승인 경로**: 명세는 `--permission-prompt-tool` → 데몬 MCP 승인 도구 → Discord 버튼이다. 메일 발송은 이 경로가 아니라 **비동기 데몬 도구**로 한다. MCP HTTP 요청은 60초에 끊기고(PoC P6), 사람이 답할 때까지 실행을 붙잡아 둘 수 없다. 승인 요청은 SQLite에 고정된 내용과 함께 남아 데몬을 다시 시작해도 유지되고, 버튼에는 요청 ID만 실린다.
- **보호 영역 변경**: `plugin/hooks/`의 허용 목록에 `WebSearch`를 더한다. 위 사용자 지시가 근거다. 입력을 해석하지 못하면 막는 동작(fail closed)은 그대로 두고, 이름을 정확히 적은 도구만 더한다.
- **Google 범위**: `gmail.send`를 더한다(발송만 되는 가장 좁은 범위). 다시 동의해야 한다. 같은 계정으로 다시 동의하면 사전 체크 기준점을 유지한다(다른 계정이면 0002의 규칙대로 새로 잡는다).

## 발송 승인의 안전 규칙

- 카드에는 보낼 내용 전부가 보인다. 길면 나눠 올리고 버튼은 마지막 메시지에 단다. 본문 상한은 8,000자이며 넘으면 요청을 받지 않는다. 카드 모양(Discord 임베드)은 결정 0005 "승인 카드 모양"에 있다.
- 버튼을 누르면 먼저 응답하고(Discord 3초 제한), 누른 사람이 소유자인지 확인한다. 승인은 `pending`인 행만 바꾸는 조건부 갱신으로 하므로 두 번 눌러도 한 번만 보낸다.
- 만료는 누를 때와 주기 점검 양쪽에서 확인한다. 보내기에 실패하면 다시 시도하지 않고 알린다. 보내는 도중 데몬이 멈춰 `approved`로 남은 요청은 다시 시작할 때 "보냈는지 모름"으로 닫고 알린다.
- 받는 사람과 제목에 줄바꿈이 있으면 거부한다(헤더 주입). 받는 사람은 주소 형식만, ASCII만 받는다(비슷하게 생긴 비ASCII 도메인을 카드에서 구별할 수 없으므로).
- 카드의 받는 사람·제목·본문은 메신저 마크다운을 끈다(문장부호 이스케이프). 스포일러(`||…||`)나 가린 링크(`[글](주소)`)로 일부가 가려지면 보이는 것과 보내는 것이 달라진다.
- 발송 범위(`gmail.send`)를 받지 않았으면 요청부터 받지 않는다(승인까지 받고 403으로 실패하지 않게). 모델에게 "다시 연결해 달라고 전하라"고 돌려준다.
- 카드를 올리지 못하면 요청을 닫고, 글로라도 그 대화에 알린다(에이전트가 이미 "카드를 올렸다"고 답했을 수 있다).
- **보내는 주소**(2026-11-16 사용자 요청으로 추가): 에이전트가 `from`으로 별칭을 고른다. 고를 수 있는 것은 Gmail의 send-as 목록 중 계정 주소와 확인을 마친 별칭뿐이고, 데몬이 요청 때 목록과 대조한다. 카드에 이름과 주소가 그대로 보인다.

## 다음으로 미룬 것([제안])

- 캘린더 일정 만들기·고치기: 같은 승인 경로로 더한다(`calendar.events` 범위가 필요하다).
- 리마인더·후속 조치 등록: 3단계(명세의 진행 상태).
- 웹 페이지 열기(`WebFetch`): VM 네트워크 출구가 필요하고, 기억을 밖으로 빼내는 통로가 된다. Muse처럼 사이트별 승인과 네트워크 정책을 함께 만들 때 연다.

## 남는 위험

- 메일 본문의 지시문이 핵심 기억을 바꿀 수 있다(기억 오염). 밖으로 나가는 쓰기는 승인으로 막히고, 기억 변경은 활동 기록과 개정 이력으로 사람이 볼 수 있다. 3단계 인젝션 검사로 줄인다.
- 승인 카드를 읽지 않고 누르면 막을 수 없다. 카드는 받는 사람 주소를 그대로(표시 이름 없이) 보인다.
