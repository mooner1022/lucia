# 0014. 작업 레코드, 작업 세션, Discord 작업 스레드

- 날짜: 2026-11-17
- 상태: 확정. 상한·만료 기간은 [제안].
- 결정 방식: 사용자 지시 "1, 3, 4 작업들 모두 순차적으로 진행해"의 3단계 남은 항목(작업 세션과 스레드, 상태 머신). 명세 §실행 계층(작업 세션), §메신저 추상화(Discord 초기 방침, 능력 선언), §작업 모델과 승인을 따른다.
- DM 스레드: Discord 문서(threads)에서 스레드를 열 수 있는 부모 채널은 서버 채널(텍스트, 공지, 포럼)뿐이다. DM에서는 스레드를 쓸 수 없다고 보고, 채널 능력 선언대로 DM에서는 낮춘 표현을 쓴다.

## 결정

### 작업 레코드와 상태 머신

- **상태**: `lucia_core::TaskStatus`. 전이는 데몬만 한다(`can_move_to`).
  - 생성 → 실행 중 → (승인 대기 또는 입력 대기) → 결과 보고 → 완료.
  - 실패, 취소, 만료는 따로 끝나는 상태다.
  - 완료로는 결과 보고 뒤에만 간다.
- **저장**: 저장소 `tasks`, `task_events`(마이그레이션 0009).
  - 상태 전이는 조건부 갱신이다(그새 바뀌었으면 하지 않는다). 모두 기록한다.
  - 작업에는 시작 주체(`Initiator`, 결정 0013)와 출처, 진행을 보낼 대화, 작업 세션, 마지막 보고를 둔다.
- **승인 대기**는 상태로만 두었다. 작업 안의 외부 쓰기(메일, 폼 제출)는 지금처럼 그 자리에서 승인 카드를 올린다. 카드가 닫힐 때 작업 상태를 바꾸는 연결은 아직 없다.

### 누가 맡기고, 어떻게 도나

- **맡기기**: 사람과의 대화(채팅)에서만 `task_start(title, brief)`로 맡긴다.
  - 후속 조치나 작업 세션은 새 작업을 맡기지 못한다(`human_only`).
  - 지시문 패턴(결정 0010의 인젝션 검사)이 있으면 맡기지 않는다.
  - 끝나지 않은 작업은 20개까지다[제안].
- **채팅 지침**: 오래 걸리거나 따로 해야 하는 일은 맡기고, 맡았다고만 짧게 답한다. 바로 답할 수 있는 일은 맡기지 않는다.
  - 열린 작업은 맥락의 `<tasks>`에 보인다.
  - 사용자의 답·조건은 `task_message`로, 그만하라고 하면 `task_cancel`로 처리한다.
- **작업 줄**: 채팅과 따로 한 번에 하나씩 돈다[제안]. 긴 작업이 채팅을 막지 않는다.
  - 작업마다 따로 Claude 세션(작업 세션, 세션 기록 역할 `task`)을 쓴다. 상주 세션과 같은 샌드박스·작업 공간이다.
  - 이어 할 때는 그 세션을 재개한다.
- **작업 세션의 범위**(`RunProfile::Task`): 채팅에서 맡긴 후속 조치와 같다(브라우저, 승인 카드를 거치는 외부 쓰기). 여기에 `task_update`(진행 한 줄, 답이 필요하면 `needs_input`)를 더한다.
  - 맡기기·전하기·취소·로그인 요청·기억 지우기는 없다.
  - 작업 세션이 등록한 후속 조치는 출처 `followup`이다(사람이 맡긴 사슬).
- **결과**: `report_result`를 작업 대화로 보낸다.
  - 상주 대화가 알도록 소유자 대화에 에피소드("[작업 결과: …]")로 남긴다.
  - 상태는 "확인 기다림"이 되고, 완료 확인 카드(승인 종류 `task_done`, 7일)를 올린다.
  - **[완료]** → 완료.
  - **[아직]** → 답 기다림. 사람의 말이 오면 같은 세션으로 이어 한다.
  - **카드 만료** → 만료.
- **답을 기다리다 멈춘 것**: "답 기다림·확인 기다림·승인 대기"로 7일 움직임이 없으면 만료한다[제안].
- **시간 제한**: 작업 세션 실행 한 번은 `sandbox.task_timeout_secs`(기본 1800초)다. 채팅(`timeout_secs`)보다 길다.
- **시작 주체에 따른 범위**: 사람이 맡긴 작업(`Human`, `Delegated`)만 위 범위다. 사람 없이 시작한 작업(`Autonomous`, 나중의 루틴·기기)은 `RunProfile::TaskLimited`(브리핑 범위 + 진행 알림)로 돈다.
- **결과를 먼저 저장한다**: 보고를 받으면 결과와 에피소드를 먼저 저장하고 보낸다. 보내지 못하면 확인 기다림으로 두고 알린다.
- **맡겼다는 답은 약속이 아니다**: 그 실행이 `task_start`를 불렀으면 "결과 나오면 알려 드릴게요"에 약속 되묻기(결정 0010)를 하지 않는다.
- **배포**: `deploy/install.sh`는 하는 중인 작업이 있으면 재시작하지 않는다(`--force`로 무시).
- **데몬 재시작**:
  - 시작도 못 한 작업은 다시 넣는다.
  - 실행 중이던 작업은 실패로 닫고 알린다. 다시 하면 같은 외부 동작을 두 번 할 수 있어서다.

### 작업 대화: 스레드 또는 DM(채널 능력 선언)

- **어댑터**: `ChannelAdapter::open_thread(parent, name)`(기본은 `Unsupported`)를 둔다. Discord 어댑터는 서버 텍스트 채널에 공개 스레드(자동 보관 1주)를 연다.
- **스레드를 쓰는 조건**: 관리 페이지 시스템 화면 "작업 스레드"에 채널 ID를 정했고, 채널이 스레드를 지원할 때.
  - 진행과 결과, 완료 카드가 모두 그 스레드로 간다.
  - 스레드에 쓴 말은 상주 대화가 아니라 그 작업으로 간다.
- **스레드가 없으면**(채널을 비웠거나 스레드를 열지 못하면) 소유자 DM으로 낮춘다.
  - 메시지 앞에 "[작업: 이름]"을 붙인다.
  - 답은 Lucia에게 말하면 `task_message`로 전한다.
- **Discord 설정**(사용자가 할 일, 관리 화면에 적었다):
  1. 서버에 작업 채널을 만들고 봇을 초대한다.
  2. 개발자 포털에서 Message Content Intent를 켠다.
  3. 채널 ID를 넣는다.
- **켰을 때 데몬이 하는 일**: 작업 채널을 정하면 게이트웨이가 서버 메시지와 그 내용 intent를 요청하고 다시 붙는다. 서버 채널의 메시지·버튼도 받는다. 누가 허용된 사람인지는 지금처럼 코어가 본다.
  - Message Content Intent가 꺼져 있으면 Discord가 연결을 닫는다(4014). 그러면 작업 스레드를 끄고 DM 전용으로 다시 붙어, 까닭과 고치는 법을 알린다(봇 전체가 끊기지 않게). 관리 페이지에서 채널을 다시 저장하면 다시 시도한다.
  - 작업 스레드에 파일을 올리면 글만 작업에 전하고, 첨부는 DM으로 보내 달라고 하게 했다.
  - 서버의 작업 스레드가 아닌 다른 채널에 소유자가 쓴 말도 받는다. 상주 대화가 처리하고 그 채널에 답한다.

### 브라우저 함께 쓰기

- 브라우저는 하나이고 상주 대화와 작업이 함께 쓴다. 명세 "자원 종류별로 동시 실행 수를 제한"에 따라, 한쪽이 마지막으로 쓴 뒤 3분 안에는 다른 쪽이 쓰지 못하게 한다[제안].
- 막힌 쪽 모델에게는 "다른 작업이 쓰고 있다, 나중에 하거나 그렇다고 보고하라"고 돌려준다. 페이지와 요소 참조가 섞이지 않게 하려는 것이다.

### 보이는 곳

- 관리 페이지 개요 "맡은 작업": 진행 중인 작업(상태, 스레드·DM, 마지막 보고)과 취소, 최근에 끝난 작업.
- 활동 기록: 맡김, 보고, 완료, 취소.

## 확인(2026-11-17)

- **시험**:
  - 상태 전이: 보고 없이 완료로 가지 않는다. 끝난 작업은 움직이지 않는다. 모두 기록된다.
  - MCP 도구:
    - 후속 조치·작업 세션은 맡기지 못한다.
    - 채팅이 맡기면 레코드가 생기고 작업 줄에 들어간다.
    - 진행 알림은 작업 세션만 쓴다. `needs_input`이면 답 기다림이 된다.
    - 끝난 작업에는 전하지 못한다.
  - 엔진(DM):
    - 따로 세션으로 실행하고, 보고를 보내고, 확인 기다림과 완료 카드로 간다. 결과 에피소드를 남긴다.
    - 이어 하기는 같은 세션을 재개한다. 끝난 작업은 다시 돌지 않는다.
  - 엔진(스레드):
    - 작업 채널을 정하면 스레드를 열고 진행이 스레드로만 간다.
    - 스레드의 말은 상주 대화를 부르지 않고 작업으로 간다.
  - 완료 카드: [완료] → 완료, [아직] → 답 기다림.
  - Discord:
    - 서버 채널의 말·버튼은 켰을 때만 받는다.
    - 스레드 이름은 100자로 자른다.
  - 브라우저: 한쪽이 쓰는 동안 다른 쪽은 막힌다.
- **찾아 고친 것**: 작업 결과를 기록할 때 저장소 잠금을 쥔 채 알림 대상을 다시 읽어 멈췄다(시험에서 발견). 잠금 전에 읽게 고쳤다.
- **실제 모델**(sonnet, 개발 샌드박스 `lucia-dev`, 2026-11-17):
  - "무선 이어폰 세 가지 국내 최저가를 조사해 비교표로, 시간 걸려도 괜찮아"
    → 채팅이 `task_start`를 불러 맡기고, "맡겼다, 끝나면 알려 드리겠다"고만 답했다. 약속 되묻기는 걸리지 않았다.
    → 작업 세션이 따로 세션으로 웹 검색해 출처와 확인 시점을 붙인 비교표를 보고했다. 상태는 보고 → 완료 카드였다(개발 채널은 버튼이 없어 카드가 닫혀 답 기다림).
  - 같은 설정에서 일반 채팅 한 번(웹 검색)도 바뀐 권한 구조(결정 0013)로 정상이다.
- **실제로 아직 안 본 것**:
  - 운영 Discord에서 작업 결과와 완료 카드의 모양.
  - 작업 세션이 상주 세션과 같은 VM에서 동시에 도는 모습.
  - Discord 서버 스레드. 사용자가 서버 채널과 Message Content Intent를 켜야 볼 수 있다.

## 하지 않은 것

- **승인 대기 연결**: 작업 안의 승인 카드가 닫힐 때 작업 상태를 바꾸지 않는다. 지금은 보고에 "카드를 확인해 달라"가 들어간다.
- **작업별 비용 상한**(명세 §실행 한도): 6단계(개발 위임)에서 함께 한다. 지금은 원장에 실행 ID(`task-…`)로 비용이 남는다.
- **작업 세션의 임시 샌드박스**: 신뢰도가 낮은 작업을 임시 샌드박스에서 하는 것은 6단계에서 한다.
