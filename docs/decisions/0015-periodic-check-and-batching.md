# 0015. 주기 점검과 알림 묶기

- 날짜: 2026-11-17
- 상태: 확정. 주기, 기준 시간, 묶음 크기는 [제안].
- 결정 방식: 사용자 지시 "1, 3, 4 작업들 모두 순차적으로 진행해"의 3단계 남은 항목. 명세 §기억과 연속성("주기 점검: … 훑을 항목이 없으면 코드 단계에서 끝내 토큰을 쓰지 않는다")과 §스케줄링("알림 묶기: 같은 시간대에 생긴 소식은 … 하나로 묶는다. 방해 금지 시간대를 둔다. 긴급도가 높은 소식만 예외로 즉시 보낸다")을 따른다.

## 결정

### 주기 점검(내장 루틴 `periodic-check`)

- **언제**: 매일 09시부터 21시까지 3시간마다(현지 시각). 늦어진 점검은 1시간 안에만 하고, 그보다 늦으면 건너뛴다(다음 점검이 곧 온다).
- **무엇을 보나**(모두 코드로, 모델 없이):
  - 답 기다림·확인 기다림 상태로 24시간 넘게 움직임이 없는 작업(결정 0014).
  - 3시간 안에 만료되는 승인 카드(메일 발송 등).
- 찾은 것은 바로 보내지 않고 "소식"으로 쌓는다. 같은 항목(작업+상태, 승인 ID)은 하루에 한 번만 쌓는다.
- 훑을 것이 없으면 그대로 끝난다. 관리 페이지 루틴 기록에 "훑을 것이 없음"으로 남는다.
- **하지 않은 것**:
  - "서로 연결된 소식을 찾기"(새 소식을 기존 작업·약속에 엮기)는 판단이 필요해 모델을 불러야 한다. 지금은 아침 브리핑과 채팅 맥락(진행 상태, 작업)이 맡는다.
  - 점검에서 모델을 부르는 단계는 [제안]으로 남긴다. → 결정 0031의 신호 처리 2단계(작은 모델 분류)로 확정했다.

### 알림 묶기

- **소식**(저장소 `notices`, 마이그레이션 0010): 급하지 않은 데몬 소식을 쌓는다. 지금은 주기 점검만 쌓는다. 나중의 기기 이벤트처럼 사람 없이 생기는 소식도 여기에 넣는다(결정 0013).
- **보내는 때**: 가장 오래된 소식이 30분을 넘었거나 5건이 모이면 "📬 모아 보는 소식" 메시지 하나로 보낸다.
  - 작업자가 조용할 때(5분마다)와 주기 점검 뒤에 확인한다.
  - 방해 금지 시간(결정 0010)에는 보내지 않고, 끝난 뒤 처음 확인할 때 보낸다.
  - 메신저가 연결되지 않았으면 다음에 보낸다.
- **바로 가는 것**(묶지 않음):
  - 오류·인증 만료 알림(`alert`, 긴급).
  - 사용자가 맡긴 일의 결과(채팅 답, 후속 조치 결과, 작업 결과).
  - 승인 카드.
- 아침 브리핑과 합치지 않았다. 브리핑은 모델이 쓰고, 소식은 모델 없이 보낸다.

## 확인(2026-11-17)

- 시험(`periodic_check_collects_and_batches_without_the_model`):
  - 훑을 것이 없으면 아무것도 쌓거나 보내지 않는다.
  - 이틀 동안 확인을 기다린 작업은 소식 하나가 된다. 같은 날 다시 점검해도 다시 쌓지 않는다.
  - 30분 전에는 보내지 않고, 지나면 하나로 묶어 보낸다. 모델 호출은 0번이다.
  - 방해 금지 시간에는 쌓기만 하고, 끝난 뒤 보낸다.
- 저장소: 같은 키는 기간 안에 한 번, 보낸 것은 다시 보내지 않는다.
- **실제로 아직 안 본 것**: 운영 Discord에서 묶음 메시지가 오는 것. 답을 24시간 기다린 작업이나 곧 만료되는 카드가 있어야 생긴다.
