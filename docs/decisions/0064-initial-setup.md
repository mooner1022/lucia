# 0064. 초기 설정 화면과 프로필 이름: GitHub 공개를 앞두고 처음 쓰는 사람을 안내한다

- 날짜: 2026-11-21
- 상태: 확정. 화면의 짜임(여섯 단계, 단계의 상태 규칙, 안내 글)과 이름의 한도(1~24자)는 사용자가 세부를 정하지 않은 설계라 [제안]이다.
- 결정 방식: 사용자 지시. 이 프로젝트를 GitHub에 공개할 것이므로 새로 쓰는 사람이 관리 대시보드에서 봇의 이름, 프로필 이미지, Firebase(FCM), Google API, Discord 정보 같은 것을 입력하는 "초기 설정" 화면이 필요하다는 것이 출발이다. 설계는 사용자가 하고 작성만 맡겼다.
- 관련 결정: 0002(관리 페이지), 0043(앱 연동, 푸시), 0046(이미지 생성), 0060(프로필 이미지), 0061(정적 Svelte 화면, 화면 규칙), 0062(디자인 언어), 0063(앱에서 로그인 입력)
- 바꾸는 것: 결정 0060의 "하지 않은 것" 첫 항목(관리 페이지에서 프로필 그림을 보거나 올리기). 이제 소유자도 관리 페이지에서 정하고 지운다.

## 배경

- 지금까지 처음 설치한 사람이 하는 일은 흩어져 있었다. Discord 봇 토큰·소유자, Google 클라이언트 JSON, 앱 토큰, Firebase 서비스 계정, OpenAI 키는 "연결" 화면에, 샌드박스 만들기와 설정 파일은 `CLAUDE.md`의 명령에, 프로필 그림은 Lucia에게 말해서(결정 0060) 정해야 했다. 무엇이 필수이고 무엇이 선택인지, 어디서 얻는지도 어디에도 적혀 있지 않았다.
- 봇의 이름은 어디에도 없었다. 화면의 머리글과 맺음, 탭 제목에 "Lucia"가 박혀 있었다.

## 결정

### 초기 설정 화면(`/start`)

- 관리 페이지에 화면 하나를 더한다. 메뉴의 "관리" 묶음 맨 끝에 "초기 설정"(좁은 화면의 아래 빠른 메뉴는 그대로)이고, 언제든 열 수 있다.
- **여섯 단계를 위에서 아래로**, 구역 하나씩 세로로 쌓는다(단계마다 길이가 달라 두 단으로 나누지 않는다. 위에 구역 건너뛰기 탭이 있다).

  | 단계 | 하는 일 | 쓰는 처리기 |
  |---|---|---|
  | 1. 이름과 모습 | 이름 정하기, 프로필 그림 올리기·지우기, 캐릭터 화면 링크 | `/profile/name`, `/profile/avatar`, `/profile/avatar/remove` |
  | 2. Discord | 봇 토큰, 소유자 사용자 ID, 어디서 얻는지 | 연결 화면과 같다(`/discord/token`, `/discord/owner`) |
  | 3. Google 메일·일정 | 클라이언트 JSON(파일·붙여 넣기), "Google로 연결", 어디서 얻는지 | 연결 화면과 같다(`/google/client/upload`, `/google/client`, `/google/connect`, `/google/paste`) |
  | 4. 앱과 푸시 | 앱 토큰 발급, 알림 받을 곳, FCM 서비스 계정 JSON, 어디서 얻는지 | 연결 화면과 같다(`/clients/new`, `/app/notify`, `/app/fcm`) |
  | 5. 이미지 생성 | OpenAI API 키 | 연결 화면과 같다(`/images/key`) |
  | 6. 환경(읽기 전용) | 설정 파일 경로, 상주·브라우저·스크립트 샌드박스와 접속 API의 상태, 점검 요약, 사용자가 터미널에서 돌릴 명령 | 없음 |

- **필수는 대화할 곳 하나뿐이다**: Discord 봇 토큰과 소유자가 모두 있거나, 알림 받을 곳으로 고른 앱이 있으면 끝났다(`snapshot.setup.complete`). 나머지는 모두 선택이다. 끝나지 않았을 때는 Discord와 앱 단계가 "필요"(둘 중 하나면 된다), 나머지는 "선택"이다. 끝난 단계는 "완료"다.
- **상태와 한 줄 요약은 데몬이 계산한다**(`admin/setup.rs`). 화면은 받은 글을 그대로 적는다. 목록과 JSON 모양은 `web/admin/docs/derived.md` 14장.
- **연결 화면의 처리기를 그대로 쓴다.** 새 쓰기 처리기를 만들지 않았다(프로필 둘, 안내 끄기·켜기만 새것). 그런데 그 처리기들은 늘 `/connections`로 돌려보낸다. 그래서 `ActionForm`에 **`stay`**를 더했다: 서버가 화면 안의 다른 곳으로 가라고 해도 지금 화면에 남고 안내만 가져온다(`PostButton`, `Confirm`도 이어 준다). 이동은 서버가 정하는 값이 아니라 화면이 정하므로 열린 리다이렉트가 생기지 않는다. 바깥 주소(Google 동의 화면)와 로그인으로 가라는 답(세션이 끝났다)은 `stay`여도 그대로 따른다. 서버가 "하지 못했다"고 답하면 화면을 다시 그리지 않아 친 값이 남는다. 데몬의 처리기는 바뀌지 않았다.
- **Google 동의 뒤**: 동의가 끝나면 전과 같이 결과 화면(로그인 없이 열리는 "Google 연결")이 열리고, 거기서 "연결 화면으로" 간다. 초기 설정으로 돌아오지는 않는다(루프백 주소로 돌아오는 요청이라 어디서 시작했는지 모른다). 단계의 안내 글에 적었다.
- **환경 단계는 읽기만 한다.** 데몬은 `sbx`를 실행하지도 설정 파일을 쓰지도 않는다. 상태는 이미 있는 점검 결과(`luciad check`와 같은 것, 10분마다)와 설정에서 읽고, 해야 할 일은 명령으로만 알려 준다(`deploy/create-sandbox.sh`, `deploy/create-browser-sandbox.sh`, `deploy/create-script-sandbox.sh`, `luciad script-check`, `luciad check`). 설정 파일 경로는 `Config::load`가 기억해 둔 것을 보여 준다(모르면 기본 위치).
- **접속 API가 꺼져 있으면** 앱 단계는 폼을 감추고 설정 키(`[gateway] bind`)를 말하는 읽기 전용 안내만 보인다(대시보드는 `lucia.toml`을 쓰지 않는다).

### 첫 화면과 안내

- **로그인 뒤 첫 화면**: 대화할 곳이 없고 안내를 끄지 않았으면 `/start`, 아니면 `/`(`AdminState::landing`). 로그인에는 따로 정해 둔 도착지가 없어 이것이 기본 도착지다. 이미 설정한 설치(Discord 토큰과 소유자가 있거나 알림 받을 곳이 앱)는 전과 같이 홈으로 간다. 로그인한 채 `/login`을 열었을 때도 같다.
- **홈의 안내**: `!complete && !dismissed`일 때만 홈 맨 위에 안내 상자가 뜨고 `/start`로 잇는다. 설정을 마친 설치에는 보이지 않는다.
- **끄기·켜기**: `/start/dismiss`(설정 `setup.dismissed = 1`, 홈으로), `/start/reopen`(지움, 초기 설정으로). 끄는 것은 끝낸 것이 아니다(`complete`는 그대로이고 로그인 뒤 첫 화면과 홈 안내만 달라진다).

### 이름(`profile.name`)

- 저장소 설정 `profile.name`. 없으면 기본 "Lucia". 정할 때 앞뒤 공백을 자르고, 1~24자(유니코드 글자 단위), 제어 문자(줄바꿈·탭 포함) 없음. **비워서 저장하면 정한 이름을 지워 기본으로 돌아간다.**
- `POST /profile/name`(활동 기록 `profile_name`). 프로필이 붙어 있으면 `Profile::set_name`으로 연결된 앱에 알리고, 없으면 저장소에만 적는다(관리 페이지 시험과 시험 데이터 서버).
- **이름이 닿는 곳(두 군데뿐)**:
  1. **관리 화면**: 모든 화면 응답(로그인한 화면과 로그인 없는 화면)의 `name`. 틀의 머리글("<이름> 관리"), 본문 맺음("<이름> · 관리 페이지"), 로그인 없는 화면의 카드 머리, 탭 제목("<화면 이름> · <이름>"). 화면은 계산하지 않고 받은 `name`을 쓴다. 로그인 없는 화면의 `name`은 처리기 28곳이 아니라 `spa::layer`가 처리기가 끝난 뒤 한 곳에서 싣는다.
  2. **앱 API**: `welcome.profile.name`, `GET /v1/profile`과 `GET /v1/me`의 `profile.name`, 번호 없는 `profile` 프레임의 `name`. 이름이 바뀌어도 프레임이 가고, 프레임은 늘 지금의 이름과 그림 전체를 싣는다(게이트웨이가 그림의 변경 구독과 이름의 변경 구독을 함께 듣는다). 더하기뿐이라 고치지 않은 앱도 그대로 동작한다. 사양서 5.3·5.5·8.7·12.1·14와 `docs/app-api-changes.md` 맨 위 항목.
- **이름이 닿지 않는 곳**(일부러 그대로 둔다):
  - Lucia가 자기를 부르는 이름과 말투: 캐릭터 파일(`character/character.md`)의 일이다. 화면의 이름 칸 도움말과 링크가 그렇게 말한다.
  - 모델에 가는 글(시스템 프롬프트, 요청 메시지, 지침), 도구 설명, 활동 기록과 알림 글("Lucia가 …"), Discord·푸시로 가는 글, 화면 곳곳의 본문에 적힌 "Lucia"(예: "Lucia가 제안한 …")
  - Discord에 보이는 봇의 이름: Discord 개발자 포털에서 정한다.

### 프로필 그림을 소유자도 정한다(0060에서 바뀐 점)

- 결정 0060은 "관리 페이지에서 프로필 그림을 보거나 올리기"를 하지 않았다. 처음 설치한 사람이 Lucia에게 부탁해야 하는 것은 순서가 맞지 않으므로(그림이 없으면 말을 걸 곳부터 만들어야 한다) 이제 소유자가 직접 정할 수 있다.
- `POST /profile/avatar`(multipart `csrf`, `file`)와 `POST /profile/avatar/remove`. **Lucia의 도구와 같은 규칙과 같은 길**: `Profile::set(…, "owner", …)`로 정하면 `Avatar.by`가 `owner`로 남고, 구독하는 게이트웨이가 연결된 앱에 `profile` 프레임을 보내고, 연결된 Discord 봇에는 `ProfileAccess::apply_discord`(처음 바꾸기 전에 원래 아바타를 보관함에 넣는다)·`clear_discord`로 도구와 같이 적용한다. 이를 위해 `ProfileAccess`를 `Runtime`에 두고 데몬이 `AdminState`에 붙인다(`set_profile`).
- 규칙은 같지만 안내가 다르다: Lucia에게는 "쉘이나 `code_run`에서 pillow로 자르고 …"라고 하지만 소유자에게는 어긴 것을 모두 알리고 규칙 한 줄만 말한다(`profile::check_for_owner`). 그림 규칙은 `움직이지 않는 PNG·JPEG, 정사각형, 한 변 128~2048px, 3 MB까지`다.
- 요청 크기 상한을 규칙(3 MiB)의 세 배(9 MiB)로 올렸다. axum의 기본 2 MiB에서 끊기면 규칙 안의 그림(2~3 MiB)도 올라가지 않고, 큰 사진은 까닭 없이 거절되기 때문이다. 9 MiB까지는 받아서 어긴 규칙을 모두 알려 준다. 넘으면 글로 거절한다(413).
- 현재 그림은 관리 페이지에서 볼 수 있다: `GET /profile/avatar/file/{id}`(로그인한 세션만, 내용 해시 id라 오래 캐시, 화면 전환으로 가로채지 않는 주소). 결과 안내에 Discord 쪽에서 한 일의 문장이 그대로 들어간다("Discord 봇의 아바타도 바꿨다(원래 아바타는 보관함에 있다: …)" 등).

## 위험과 받아들인 것

- **Discord 아바타는 다른 사람에게도 보인다.** 소유자가 직접 정하는 것이라 승인 카드 없이 한다(결정 0060과 같다). 원래 아바타는 보관한다.
- **안내 글의 외부 주소**: 단계의 도움말에 Discord 개발자 포털, Google Cloud 콘솔, Firebase 콘솔의 주소를 링크로 적었다(`target="_blank"`, `rel="noreferrer"`). 그 서비스들의 메뉴 이름은 바뀔 수 있어 안내 글이 낡을 수 있다.
- **Google 앱이 "테스트" 상태이면** 사용자 유형이 외부일 때 내 계정을 테스트 사용자로 넣어야 한다고 안내에 적었다. 테스트 상태 앱의 토큰이 얼마 뒤 만료되는지는 Google의 정책이라 데몬이 다루지 않고 확인하지 않았다.
- **새 설치의 첫 화면이 바뀐다.** 설정이 비어 있으면 로그인 뒤 홈이 아니라 초기 설정으로 간다. 이미 Discord나 앱을 정한 설치는 달라지지 않는다.
- 이름은 24자까지의 한 줄이다. 아주 긴 이름(끊을 곳 없는 글)이 머리글을 깨지 않게 줄을 바꾸고 어디서든 끊는다.

## 하지 않은 것

- **알림 글과 프롬프트의 "Lucia" 바꿔 치기**: 이름을 정해도 모델에 가는 글, 도구 텍스트, Discord·푸시로 가는 알림 글은 그대로다. 이름과 말투의 자리는 캐릭터 파일이다. 알림 글을 이름에 맞추려면 문장마다 고쳐야 하고 시험·학습 루프가 같은 글에 기대고 있어, 사용자가 원할 때 따로 한다.
- **Discord 봇의 이름 바꾸기**: 개발자 포털에서 정한다(데몬이 `PATCH /users/@me`로 이름을 바꾸는 것은 하지 않았다).
- **`lucia.toml` 쓰기**: 대시보드는 설정 파일을 고치지 않는다. 접속 API·브라우저·스크립트를 켜는 설정은 키와 값을 안내만 한다.
- **샌드박스 만들기**: 데몬은 `sbx`를 실행하지 않는다. 명령을 안내만 한다(`deploy/create-*-sandbox.sh`).
- 새 쓰기 처리기를 더하는 것, 연결 화면의 폼과 글을 줄이거나 바꾸는 것(연결 화면은 그대로다. 시험이 지킨다).
- 이름을 앱이 정하게 하는 것(앱 쪽에서 이름을 보내는 메서드), 이름의 다국어.

## 어떻게 만들었나

설계는 사용자가 했고 작성은 한 번에 맡겼다. 데몬 쪽(프로필 이름, 이름 구독, 처리기, 스냅숏·`derive` 값, 로그인 첫 화면)과 화면 쪽(`Start.svelte`, `stay`, 이름 배선, 시험 데이터·시험)을 함께 짰다.

## 검증

- **시험**(모델·실제 Discord·실제 앱·실제 Google을 쓰지 않았다):
  - Rust 작업 공간 전체 599개 통과(이번에 10개 추가: 데몬 안 `profile` 2, 접속 API 1, 관리 페이지 7). clippy 경고 0, fmt 통과.
