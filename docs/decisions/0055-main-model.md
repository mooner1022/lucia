# 0055. 주 모델을 사용자가 고른다

- 날짜: 2026-11-20
- 상태: 확정. 고를 수 있는 모델의 목록과 설명 문구는 [제안].
- 결정 방식: 사용자 지시("주 모델 선택 기능 구현을 추가해").
- 관련 결정: 0004(세션 compact), 0040(`/권한` 명령), 0043(앱 명령과 범위), 0049(맥락 한 번만 싣기)

## 그전

- 모델은 설정 파일 `[models]`에만 있었다(`chat`, `briefing`, `retro`, `classify`). 바꾸려면 파일을 고치고 데몬을 다시 띄워야 했다.
- 운영은 `chat`·`briefing` 모두 `sonnet`이었다.

## 결정

- **주 모델**은 Lucia가 생각하는 실행이 쓰는 모델 하나다. 사용자가 고르면 다음이 모두 그 모델로 돈다.
  - 대화, "기억해 줘", 약속 되묻기, 맡긴 작업(작업 세션), 반복 루틴이 깨운 실행(지금까지 `chat` 모델).
  - 아침 브리핑, 주간·저녁 보고, 목표 점검, 신호가 깨운 실행, 하루 정리, 일관성 점검(지금까지 `briefing` 모델).
  - 둘을 따로 두지 않는 까닭: 이 실행들은 같은 상주 세션을 쓴다. 프롬프트 캐시는 모델마다 따로라, 한 세션에서 모델이 번갈아 바뀌면 그때마다 대화 전체를 새로 쓴다.
- **바꾸지 않는 것**: 회고(`retro`)와 신호 분류(`classify`)의 작은 모델. 설정 파일 그대로다.
- **고르지 않았으면** 설정 파일의 `chat`·`briefing`을 그대로 쓴다(지금까지와 같다).
- **고를 수 있는 것**: `fable`, `opus`, `sonnet`, `haiku`와 "기본(설정 파일 값)". Claude Code의 모델 별칭이라 그 계열의 최신 모델을 따라간다. 버전이 붙은 이름이나 자유 입력은 받지 않는다(오타 하나로 모든 대화가 실패하지 않게).
- **바꾸는 곳**:
  - 관리 페이지 "캐릭터" 화면의 "주 모델".
  - 소유자의 Discord 명령 `/모델 [모델]`. 비우면 지금 모델과 고를 수 있는 것을 보인다.
  - 앱의 `command`(`name: "모델"`). 범위를 따로 두지 않는다. 주 모델은 안전 장치가 아니고, 앱 토큰은 이미 대화로 사용량을 쓸 수 있다. 앱에서 바꾸면 알림 대화에 기록이 남는다(결정 0043의 `/권한`과 같다).
  - 앱의 `commands`는 명령마다 지금 값(`current`)을 함께 준다(`권한`에도 더했다). 앱이 고르는 화면에 지금 값을 표시하려고 답의 글을 풀어 읽지 않게 한다.
  - 모델 도구는 없다(Lucia가 스스로 자기 모델을 바꾸지 않는다).
- **적용**: 다음 실행부터. 도는 실행은 그대로 끝난다. 데몬을 다시 띄우지 않는다.
- **세션**: 그대로 이어 쓴다. 바꾼 뒤 첫 실행은 새 모델이 대화 전체를 처음부터 읽는다. 자동으로 정리(compact)하거나 새 세션으로 넘기지 않는다. 맥락이 클 때는 사용자가 "지금 정리"를 먼저 누르면 된다.
- **저장**: 저장소 설정 `models.main`. 값이 깨졌거나 모르는 이름이면 고르지 않은 것으로 본다. 바꾼 것은 활동 기록(`main_model`)에 남는다.
- **구현**: 실행 경로는 메모리의 사본만 읽는다(`models.rs`의 `MainModel`). 저장소 잠금을 쥔 채 모델 이름을 읽는 자리가 있어, 읽을 때 저장소를 다시 잠그지 않는다. 엔진, 관리 페이지, 명령 처리기가 한 벌을 나눠 쓴다.

## 알아 둘 것

- 유능한 모델일수록 구독 사용량을 빨리 쓴다. 원장의 비용(자동 실행의 하루·주간 한도가 보는 값)도 같이 커진다. 사람 없이 도는 브리핑과 정기 보고도 고른 모델로 돈다.
- compact 기준(20만)은 모델마다 달리 두지 않았다. 공개 문서로는 네 모델 모두 창이 100만 토큰이지만(2026-11), 샌드박스에서 잰 것은 12만 토큰까지다.
- 개발 명령(`ask`, `briefing`, `routine`)도 저장소의 선택을 따른다.

## 하지 않은 것

- 바꿀 때 자동으로 compact하기. 정리도 모델 호출이고, 맥락이 작을 때는 손해다. 안내만 했다. 앱은 사용자가 고르면 먼저 정리를 청할 수 있다(결정 0056).
- 대화용과 정기 실행용을 따로 고르기(위의 캐시 이유).
- 추론 강도(effort) 고르기. 지시에 없었다.
- 작은 모델(`retro`, `classify`) 고르기.

## 확인(2026-11-20)

- **시험**: 고른 모델이 대화와 브리핑에 함께 적용되고 다시 떠도 남는 것. 모르는 저장값은 설정 파일 값으로 떨어지는 것. 엔진이 다음 실행부터 새 모델을 쓰고 같은 세션을 이어 쓰는 것. `/모델`이 소유자만 받고, 늦은 명령은 적용하지 않고, 서버에서 바꾸면 DM에 남기는 것. Discord 선택지가 데몬이 아는 모델과 같은 것. 앱의 `commands`·`command`. 관리 화면의 폼(기준 목록에는 더하기만 있었다).
- **실제**(개발 설정, 맥락 약 12만 토큰의 상주 세션 하나에서 차례로):

  | 순서 | 고른 값 | 실제 모델 | 새로 쓴 토큰 | 걸린 시간 | 원장 비용 |
  |---|---|---|---|---|---|
  | 1 | `haiku` | claude-haiku-5-5 | 118,852 | 7.4초 | $0.14 |
  | 2 | `opus` | claude-opus-5-5 | 121,859 | 5.8초 | $1.01 |
  | 3 | `fable` | claude-fable-5-2 | 125,763 | 7.4초 | $2.08 |
  | 4 | (기본) | claude-sonnet-5-5 | 108,238 | 6.4초 | $0.46 |

  - 네 번 모두 같은 세션(`7f7eddcf`)을 이어 썼고, 도구 호출(기억 찾기)도 됐다. 2번에서 Opus는 1번(Haiku)에서 한 질문을 그대로 답했다.
  - 바꿀 때마다 맥락 전체를 새로 썼다. 원래 모델(Sonnet)로 되돌아갈 때도 마찬가지였다(42분 전까지 쓰던 캐시가 대부분 쓰이지 않았다).
  - 같은 세션의 직전 Sonnet 실행(모델을 바꾸지 않음)은 새로 쓴 토큰이 11,147이었다.
- 운영 샌드박스(`lucia`)와 개발 샌드박스의 Claude Code는 같은 판(2.1.325)이다.
- **아직 보지 않은 것**: 운영에서 관리 페이지와 `/모델`로 바꾸는 것(코드는 시험으로만 봤다). 20만 토큰에 가까운 세션에서의 전환.
