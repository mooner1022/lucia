# 0065. 받아 쓰는 설치: 릴리스 묶음, 한 줄 설치, 준비물 채우기

- 날짜: 2026-11-21
- 상태: 확정(구현해 커밋했고, 아직 배포하지 않았다). 묶음의 구성, 설치 위치, 준비물을 대신 설치하는 범위는 사용자가 세부를 정하지 않은 설계라 [제안]이다.
- 결정 방식: 사용자 요청. 설치가 번거롭고 의존성이 많으니 쓰기 쉽게 만들고, 준비물은 스크립트가 설치해 주면 좋겠다는 것이다. 설계는 작성자가 했다. 처음 사용자에게 말한 구상과 다르게 갔다(아래 "하지 않은 것" 첫 항목과 "남는 준비물"의 `python3`).
- 관련 결정: 0009(캐릭터 고치기), 0012(systemd 사용자 서비스, 배포), 0014·0050(재시작과 하던 일), 0061(관리 화면을 바이너리에 넣는다), 0064(초기 설정)
- 바꾸는 것: 결정 0012의 배포 순서 가운데 "릴리스 빌드"는 받아 쓰는 설치에서 건너뛰고, "`sqlite3 .backup`"은 `luciad store-backup`으로 바뀐다. 레포에서 빌드하는 설치(0012의 방식)는 그대로 쓸 수 있다.

## 배경

- 0012의 배포는 레포를 받아 직접 빌드하는 길 하나였다. 준비물이 Rust 1.93 이상, Node.js, `sqlite3`, `python3`, `systemd-creds`이고 첫 빌드에 10분쯤 걸렸다.
- `deploy/setup.sh`가 묻고 답하며 처음 올리기를 안내하지만, sudo가 필요한 준비물(kvm 그룹, sbx 설치)은 명령만 알려 주었다.
- GitHub에 공개하면 처음 쓰는 사람이 이 길을 따라와야 한다. 빌드 도구 없이 받아서 쓰는 길과, 빠진 준비물을 허락을 받고 채워 주는 길이 필요하다.

## 결정

### 릴리스 묶음(`deploy/package.sh`)

- 관리 화면 빌드(`deploy/build-ui.sh`) → 릴리스 빌드 → `luciad ui-check` → 바이너리 버전이 `Cargo.toml`의 버전과 같은지 확인 → 묶음 만들기.
- 결과는 `dist-release/`의 `lucia-x86_64-linux.tar.gz`, `lucia-x86_64-linux.tar.gz.sha256`, 그리고 레포 맨 위 `install.sh`의 사본이다(`/dist-release/`는 `.gitignore`에 있다).
- 묶음 안(최상위 디렉터리 `lucia-x86_64-linux/`):

  | 경로 | 내용 |
  |---|---|
  | `luciad` | 데몬 바이너리(관리 화면이 들어 있다) |
  | `VERSION` | `Cargo.toml`의 버전(`0.1.0` 꼴) |
  | `deploy/` | 설치·설정·걷어 내기·샌드박스 만들기 스크립트, 서비스 유닛, 설정 예시, Traefik 예시. `package.sh`와 `build-ui.sh`는 뺀다 |
  | `plugin/` | 상주 샌드박스에 읽기 전용으로 붙는 훅 |
  | `character/` | 기본 캐릭터 |
  | `README.md`, `docs/DEPLOY.md` | 읽을거리 |

- `deploy/`·`plugin/`·`character/`·문서는 **커밋된 것**(`git archive HEAD`)만 넣는다. 작업 트리에서 고친 파일(이 서버가 쓰는 캐릭터 등)은 들어가지 않는다. 바이너리는 작업 트리로 빌드하므로, 추적하는 파일이 고쳐져 있으면 `package.sh`가 멈춘다(시험으로 만들 때만 `LUCIA_PACKAGE_ALLOW_DIRTY=1`).
- tar 안 파일의 순서·소유자·시각을 고정한다(시각은 그 커밋의 것).
- `package.sh`는 x86-64에서만 돈다.
- 릴리스 워크플로(`.github/workflows/release.yml`): `v*` 태그를 올리면 Ubuntu 24.04 러너에서 관리 화면 빌드와 시험(`deploy/build-ui.sh`) → `cargo test --workspace` → `deploy/package.sh "$GITHUB_REF_NAME"` → `gh release create`로 묶음, 체크섬, `install.sh`를 올린다(릴리스 노트는 자동 생성). Rust는 안정판, Node.js는 LTS다.
  - **태그는 Cargo 작업 공간의 버전과 같아야 한다**(`v0.1.0` ↔ `version = "0.1.0"`). 다르면 `package.sh`가 멈춘다.
  - Ubuntu 24.04에서 빌드하는 까닭: 여기서 만든 바이너리의 glibc가 그보다 새 배포판에서 모두 돈다. Lucia가 실제로 도는 곳은 systemd 256 이상이라 24.04보다 새 배포판이고, 이 러너에서는 실제 자격 증명을 쓰는 시험 셋이 스스로 건너뛴다(쓸 수 있는지를 먼저 본다).

### 한 줄 설치(`install.sh`)

```sh
curl -fsSL https://github.com/mooner1022/lucia/releases/latest/download/install.sh | bash
```

- 스크립트 전체를 함수 하나로 감싼다. 내려받다 끊겨 반쯤 온 스크립트가 실행되지 않게 하려는 것이다.
- 순서:
  1. root가 아닌지, x86-64 리눅스인지, `curl`·`tar`·`sha256sum`·`python3`가 있는지 본다. 하나라도 아니면 멈춘다(빠진 도구는 `sudo apt install <도구>`를 알려 줄 뿐 설치하지 않는다).
  2. 묶음과 `.sha256`을 받아(HTTPS만, 재시도 3번) `sha256sum -c`로 맞춰 본다. 맞지 않으면 멈춘다.
  3. 묶음에 `luciad`, `VERSION`, `deploy/setup.sh`가 있는지 본다.
  4. `~/.local/lib/lucia/release`에 푼다. **이 디렉터리는 자리를 지킨 채 내용만 바뀐다**: 묶음의 파일을 하나씩 새 파일로 바꿔 넣고(`.part`에 복사한 뒤 이름을 바꾼다), 묶음에 없는 옛 파일과 빈 디렉터리를 지운다. 샌드박스가 이 안의 `plugin/`을 붙여 쓰므로 디렉터리를 지웠다 새로 만들지 않는다.
  5. 이미 설치돼 있으면(`~/.local/lib/lucia/luciad`가 있고 `~/.config/systemd/user/luciad.service`가 있다) `release/deploy/install.sh`로 업데이트한다. 처음이면 `release/deploy/setup.sh`로 간다.
- `curl | bash`에서는 표준 입력이 스크립트라 `setup.sh`의 답은 `/dev/tty`에서 읽는다. 터미널이 없으면 풀기까지만 하고, 이어서 돌릴 명령(`release/deploy/setup.sh`)을 찍고 끝낸다.
- 환경 변수: `LUCIA_VERSION=v0.1.0`(받을 릴리스, 기본은 가장 새것), `LUCIA_NO_SETUP=1`(풀기만 한다). 파이프의 `bash` 쪽에 둔다: `curl -fsSL … | LUCIA_VERSION=v0.1.0 bash`.
- 이 스크립트에는 `deploy/install.sh`에 줄 인자(`--force`, `--no-restart`)를 넘기는 길이 없다. 그것이 필요하면 `release/deploy/install.sh`를 직접 부른다.
- **체크섬은 내려받다 깨지지 않았는지만 본다.** 누가 만들었는지는 증명하지 않는다(받는 곳이 이 저장소의 GitHub 릴리스라는 것이 근거의 전부다). 묶음에 서명은 없다.

### 받아 쓰는 설치 방식(스크립트의 두 방식)

- 스크립트는 자기 레포 자리(`deploy/`의 위)에 **빌드해 둔 `luciad`와 `VERSION`이 있으면** 받아 쓰는 설치로 동작한다. 없으면 이제까지처럼 레포에서 빌드한다. 이 서버는 뒤쪽이다.
- `deploy/install.sh`: 화면 빌드와 릴리스 빌드를 건너뛰고 그 바이너리를 설치한다. 설치 전에 `ui-check`로 화면이 온전히 들어 있는지 보는 것은 같다. 나머지(저장소 백업, 바이너리 설치, 유닛 설치, 하던 일을 기다렸다 재시작)도 같다. 서비스 유닛의 `WorkingDirectory`는 그 레포 자리로 맞춘다(받아 쓰는 설치에서는 `~/.local/lib/lucia/release`).
- `deploy/setup.sh`: Rust와 Node.js를 요구하지 않는다. 끝의 안내가 "업데이트: 한 줄 설치 명령"으로 바뀐다.
- `deploy/create-sandbox.sh`:
  - 캐릭터는 `~/.config/lucia/character`를 붙인다. 그 안에 `character.md`가 **없을 때만** 기본 캐릭터를 복사해 넣는다. 그래서 관리 페이지 "캐릭터"에서 고친 것이 업데이트로 덮이지 않는다. 데몬은 캐릭터 파일의 호스트 쪽 경로를 샌드박스의 마운트에서 찾으므로(결정 0009) 관리 페이지는 이 파일을 고친다.
  - plugin은 풀어 둔 릴리스의 `plugin/`을 붙인다. 업데이트는 그 안의 내용만 바꾼다.
  - 레포에서 빌드하는 설치는 이제까지처럼 레포의 `plugin/`, `character/`를 붙인다. 환경 변수 `LUCIA_PLUGIN_DIR`, `LUCIA_CHARACTER_DIR`로 둘 다 바꿀 수 있다.
  - 샌드박스는 한 번 만들면 마운트 경로가 고정된다. 업데이트가 마운트를 바꾸지는 않는다.

### 저장소 점검 명령: `luciad store-status`, `luciad store-backup`

- 배포 스크립트가 `sqlite3` 명령 없이 저장소를 다루게 한다. 둘 다 설정을 읽지 않고 `--db <경로>`를 받는다. 저장소는 **읽기 전용으로** 열고 마이그레이션하지 않는다(`Store::open`을 쓰지 않는다). 없는 파일을 빈 저장소로 만들어 버리지 않는다. 돌고 있는 데몬과 함께 써도 된다(WAL).
- `luciad store-status --db <경로>`: 세 줄을 찍는다.

  ```
  running_tasks=<하는 중인 작업 수>
  inbox=<받은 편지함의 메시지 수>
  run_in_flight=<0 또는 1: 하는 중인 정기 작업이 있는가>
  ```

  세 값은 한 번의 읽기 트랜잭션에서 읽는다. 표가 아직 없는 옛 스키마는 0으로 본다. 파일을 읽지 못하면 실패한다.
- `luciad store-backup --db <경로> --out <경로>`:
  - SQLite 온라인 백업으로, 복사를 시작한 시점에 커밋된 모습을 한꺼번에 담는다(제한 시간 120초).
  - 사본은 새 파일로 만든다. 0600이고, 이미 있으면 덮어쓰지 않고 실패한다.
  - 사본을 부속 파일(`-wal`, `-shm`) 없이 한 파일로 끝나게 바꾸고(저널 방식 DELETE) `PRAGMA integrity_check`가 `ok`인지 본다. 통과하지 못하면 사본을 지우고 실패한다. 어떤 실패에서도 만들다 만 파일을 남기지 않는다. 디스크에 내려간 것까지 확인한 사본만 남는다.
  - 사본을 복원해 쓸 때는 `Store::open`이 다시 WAL로 바꾼다.
- `deploy/install.sh`는 **새로 설치할 바이너리로** 이 둘을 부른다.
  - 받아 쓰는 설치에는 빌드 전 확인이 없다. 레포에서 빌드하는 설치는 빌드 전에 지금 설치된 바이너리로 한 번 미리 보지만, 그것은 읽지 못하면(예전 바이너리라 이 명령이 없다 등) 넘어간다.
  - 설치 직전의 확인은 엄격하다: 새 바이너리로 상태를 읽지 못하면 멈춘다. 하는 중인 작업이 있어도 멈춘다. `--force`로 둘 다 건너뛴다. `--no-restart`면 이 확인을 하지 않는다(재시작하지 않으니 하던 일이 끊기지 않는다).
  - 저장소 파일이 있으면 백업은 언제나 한다(`--force`, `--no-restart`와 상관없다). 백업이 실패하면 설치를 멈춘다. 백업 없이 마이그레이션하지 않는다. 위치와 보관은 그대로다(`<data_dir>/backup/lucia.sqlite.<시각>`, 최근 20개).

### 준비물을 허락을 받고 채운다(`deploy/setup.sh`)

- **Ubuntu 24.04 이상에서만, `sudo`와 `apt-get`이 있을 때만** 한다(Docker가 sbx를 지원하는 곳). 실행할 명령을 그대로 보여 주고 묻는다. 기본은 "아니오"이고, 하나씩 묻는다. `--check`에서는 묻지도 하지도 않는다(진행하면 물어본다는 안내만 보인다). (sbx를 대신 설치하는 조건이 24.04 이상이라는 뜻이다. Lucia 자체는 systemd 256 이상이 필요해 24.04에서는 준비물 확인에서 멈춘다.)

  | 빠진 것 | 하는 명령 |
  |---|---|
  | 사용자가 `kvm` 그룹에 없다 | `sudo usermod -aG kvm $USER` |
  | `sbx`가 없다 | `curl -fsSL https://get.docker.com \| sudo REPO_ONLY=1 sh`(Docker의 apt 저장소를 더한다. Docker의 설치 스크립트를 받아 root로 돌린다), 이어서 `sudo apt install docker-sbx`. `curl`이 없으면 먼저 `sudo apt install curl`을 묻는다 |
  | `python3`가 없다 | `sudo apt install python3` |

- sbx 명령은 Docker의 설치 문서(<https://docs.docker.com/ai/sandboxes/install/>)에 있는 것 그대로다. 위 명령을 돌린 뒤 준비물을 다시 확인한다.
- 다른 배포판이나 `sudo`가 없는 곳에서는 같은 명령을 보여 주기만 하고 멈춘다. 보여 주는 명령은 apt 기준이다.
- 다시 로그인하지 않고도 이어 가도록, 이 셸에 `kvm` 그룹이 없으면 `setup.sh`는 `sg kvm`으로 sbx를 부른다(이전과 같다).
- 비밀(토큰, 키)은 묻지 않는다. 그것은 설치 뒤 관리 페이지의 "초기 설정"에서 넣는다(결정 0064).

## 남는 준비물

받아 쓰는 설치로도 없어지지 않는 것이다.

- KVM이 되는 x86-64 리눅스(`/dev/kvm`).
- systemd **256 이상**(사용자 서비스, 자격 증명 암호화의 `systemd-creds --user`가 256부터 있다). Ubuntu 24.04는 255라 되지 않는다. 확인한 곳은 Ubuntu 26.04(systemd 259)다. `setup.sh`는 명령이 있는지가 아니라 실제로 암호화가 되는지를 본다.
- `sbx`: Docker의 제품이라 이 묶음에 넣어 다시 배포할 수 없다. Ubuntu 24.04 이상에서는 위처럼 설치를 대신 해 준다.
- Docker 계정 로그인(`sbx login`)과 Claude 구독 로그인. 사람이 브라우저에서 해야 한다.
- **`python3`**: 처음에는 없앨 수 있다고 말했으나 없애지 못했다. 한 줄 설치 스크립트(받은 파일 맞추기), `setup.sh`·`uninstall.sh`(설정 파일 읽고 쓰기), 브라우저·코드 실행 샌드박스를 만드는 스크립트, sbx 유닛(`lucia-sbx.service`)의 확인이 쓴다.
- 한 줄 설치 스크립트는 `curl`, `tar`, `sha256sum`도 쓴다.
- ARM용 묶음은 만들지 않는다. Docker의 문서는 sbx의 64비트 Arm 지원을 적고 있지만, 이 묶음과 설치 스크립트는 x86-64만 받는다. Arm에서 레포에서 빌드하는 길은 시험하지 않았다.

## 하지 않은 것

- **설치·설정을 데몬의 하위 명령으로 다시 쓰기, `plugin/`·`character/`를 바이너리에 넣기.** 처음 사용자에게 말한 구상은 이쪽이었고, 그때 `python3`도 없앨 수 있다고 했다. 하지 않았다.
  - 실제 호스트에서 돌려 확인한 것이 쉘 스크립트뿐이다. 다시 쓰면 빈 기계에서 시험할 수 없는 새 코드가 설치의 가장 앞을 맡게 되는데, 여기서는 빈 기계에서 시험할 방법이 없었다.
  - 그래서 스크립트를 그대로 두었고, 스크립트가 쓰는 `python3`도 남았다(위 "남는 준비물").
- **Docker 이미지.** 데몬은 호스트의 sbx를 부르고 호스트의 루프백 포트로 샌드박스와 통신한다. 컨테이너에 넣으려면 KVM, sbx 소켓, 호스트 네트워크를 안으로 열어야 해서 경계가 약해지는데, 얻는 것은 적다.
- **`.deb` 패키지.** 데몬은 사용자 서비스이고, sbx는 우리가 당겨 올 수 있는 apt 의존성이 아니다. 패키지로 내려면 apt 저장소를 따로 운영해야 하고, 패키지 업그레이드는 "저장소 백업 → 바이너리 교체 → 재시작"의 순서(`deploy/install.sh`)를 건너뛴다.
- **묶음 서명**과 **ARM 묶음**: 하지 않았다(위와 "알려진 빈틈").

## 릴리스 내는 법

1. 작업 공간 버전(`Cargo.toml`의 `[workspace.package] version`)을 올리고 커밋한다(`Cargo.lock`도 함께 바뀐다).
2. 태그 `v<버전>`(예: `v0.1.1`)을 만들어 올린다. 태그와 버전이 다르면 워크플로가 멈춘다.
3. 워크플로가 끝나면 릴리스 페이지에 묶음, `.sha256`, `install.sh` 셋이 있는지 본다.
4. **손으로 만든 묶음(`deploy/package.sh`를 내 기계에서 돌린 것)은 올리지 않는다.** 그 기계의 glibc에 묶인다. 올리는 묶음은 릴리스 워크플로가 만든 것뿐이다. 로컬에서 만드는 것은 묶음을 시험할 때뿐이다.

`install.sh`는 레포 맨 위의 그것이고, 태그가 가리키는 커밋의 판이 릴리스에 올라간다. `releases/latest/download/…`는 가장 새 릴리스를 가리킨다.

## 검증

- 시험(모델을 쓰지 않았다):
  - Rust 작업 공간 전체 621개 통과(이번에 22개 추가: `crates/luciad/tests/store_cli.rs` 4, `crates/lucia-store/src/maintenance.rs` 단위 시험 16, `crates/luciad/src/store_cli.rs` 단위 시험 2). clippy 경고 0, fmt 통과.
  - `store-status`가 정확히 세 줄을 찍는 것, 없는 파일에서 실패하고 아무것도 만들지 않는 것, `store-backup`이 0600의 사본을 만들고 알리는 것, 덮어쓰기를 거절하고 없는 저장소에서 실패하는 것(사본이 남지 않는 것 포함).
  - 스크립트 정적 검사: `bash -n` 통과. shellcheck는 이 서버에 없어 돌리지 않았다.
- 스크립트는 저장소의 시험이 아니라 가짜(스텁) 환경에서 직접 돌려 보았다. 그 시험 스크립트는 저장소에 없다. 확인한 것:
  - 레포에서 빌드한 설치(이 서버)에서 한 줄 설치가 내려받기 전에 멈추는 것, 풀린 자리에 만든 `.env`가 업데이트 뒤에도 남고 예전 묶음에만 있던 파일은 지워지는 것, 저장소를 읽지 못하면 풀기 전에 멈추는 것.
  - 묶음 만들기(로컬), 내려받기와 풀기, 체크섬이 틀린 묶음의 거절, 터미널이 없을 때 풀기까지만 하고 다음 명령을 찍는 것.
  - 받아 쓰는 설치의 `setup.sh`가 빌드 없이 `install.sh`까지 가는 것.
  - 업데이트: 백업을 만들고, `release/` 디렉터리를 자리에서 맞추는 것(`plugin/` 디렉터리의 inode가 그대로다. 묶음에 없는 옛 파일은 지워진다).
  - 하는 중인 작업이 있으면 설치를 멈추는 것, 저장소를 읽지 못하면 진행하지 않고 멈추는 것.
  - 준비물 제안: 모두 거절하면 아무 명령도 돌지 않는다. 모두 승낙하면 위 표의 명령만 정확히 돈다. Ubuntu가 아니면 명령을 보여 주기만 한다.
- 돌고 있는 운영 저장소를 대상으로 `store-status`와 `store-backup`을 읽기 전용으로 돌려 성공했다.
- **실제로는 아직 안 본 것**:
  - GitHub 워크플로가 한 번도 돈 적이 없다(태그를 올려야 돈다). `actions/checkout@v7`, `actions/setup-node@v7`이 있는 것은 확인했으나 워크플로 전체는 안 돌렸다.
  - 빈 기계에서 처음부터 끝까지 돌려 본 적이 없다.
  - 실제 `sudo`로 하는 설치(kvm 그룹, Docker 저장소, `docker-sbx`).
  - sbx v0.51보다 새로운 판. 처음 설치하는 사람은 스크립트들을 확인한 판보다 새로운 sbx를 받는다.
  - 실제 VM이 `release/plugin`을 자리에서 맞춘 뒤의 파일을 보는지(마운트가 새 파일을 보여 주는지)는 시험하지 않았다.

## 알려진 빈틈

- `Cargo.toml`의 `license = "UNLICENSED"`이고 `LICENSE` 파일이 없다. 바이너리를 공개 릴리스로 올리면 더 중요해진다. 정하지 않았다.
- 첫 릴리스가 없는 동안 README의 한 줄 설치 명령은 404를 돌려준다.
- 묶음에 서명이 없다(체크섬뿐).
- 업데이트는 풀기 전에 확인한다: 돌고 있는 설치면 한 줄 설치가 받은 바이너리로 저장소를 읽어, 하는 중인 작업이 있거나 저장소를 읽지 못하면 아무것도 바꾸지 않고 멈춘다. 다만 그 확인과 실제 재시작 사이에 새 작업이 시작되면 `deploy/install.sh`의 확인에서 멈추고, 그때는 `release/`만 새것이 된다(이어서 하려면 `release/deploy/install.sh`를 다시 부른다). 한 줄 설치로는 `--force`나 `--no-restart`를 넘길 수 없다.
- `release/` 안에 사용자가 따로 만든 파일(예: `release/deploy/traefik/.env`)은 업데이트가 지우지 않는다. 묶음의 `MANIFEST`로 "예전 묶음에는 있었고 새 묶음에는 없는 파일"만 지운다. 묶음에 든 파일을 고친 것은 업데이트가 덮어쓴다.
- 관리 페이지의 "초기 설정" 환경 단계와 `luciad check`의 안내는 `deploy/create-browser-sandbox.sh`처럼 레포 기준의 상대 경로를 찍는다. 받아 쓰는 설치에서는 `~/.local/lib/lucia/release`에서 돌려야 맞다.
- 걷어 내기: 받아 쓰는 설치에서는 `release/`가 바이너리 디렉터리(`~/.local/lib/lucia`) 안에 있어 "바이너리" 단계가 함께 지운다. 설정 디렉터리를 지우면 `~/.config/lucia/character`(고친 캐릭터)도 함께 지워진다.
- 레포에서 빌드한 설치 위에서는 한 줄 설치가 내려받기 전에 멈춘다(서비스 유닛의 작업 디렉터리가 `release/`가 아니면 레포 설치로 본다). 두 방식을 한 서버에서 섞지 않는다.
- `python3`가 `setup.sh`가 제안하는 준비물에 들어 있지만, 한 줄 설치 스크립트가 `python3` 없이는 시작하지 않으므로 그 길에서는 이 제안에 닿지 않는다(레포에서 `setup.sh`를 직접 돌릴 때만 제안한다).

## 덧붙임(2026-11-21): 첫 릴리스

- `v0.1.0` 태그의 워크플로는 시험 단계에서 실패해 릴리스를 만들지 못했다. Ubuntu 24.04 러너(systemd 255)에서 `systemd-creds --user`가 되지 않는데, 관리 화면 시험 셋(이미지 키 저장, 초기 설정 상태, 로그인 뒤 첫 화면)이 실제 자격 증명을 쓰면서도 건너뛰지 않았다. 셋에 같은 확인(쓸 수 있을 때만 돈다)을 넣었고, `systemd-creds`가 실패하는 환경을 로컬에서 흉내 내 전체 시험이 통과하는 것을 봤다.
- 올라간 태그는 옮기지 않는다. 버전을 0.1.1로 올려 `v0.1.1`로 첫 릴리스를 낸다(`v0.1.0` 태그에는 릴리스가 없다).
- `v0.1.1`의 워크플로는 끝까지 갔다(화면 빌드와 시험, Rust 시험, 묶음, 릴리스). 릴리스에 `lucia-x86_64-linux.tar.gz`, `.sha256`, `install.sh`가 올라갔다.
- 공개 주소로 확인한 것: `releases/latest/download/install.sh`가 저장소의 것과 같고, 임시 홈에서 그 스크립트가 묶음을 받아 체크섬을 맞추고 풀었다(버전 0.1.1, 관리 화면 포함). 바이너리가 요구하는 glibc는 2.39다.
- 여전히 하지 않은 것: 빈 서버에서 설정까지 가는 실제 설치. 이 서버(레포에서 빌드하는 설치)에는 이 판을 배포하지 않았다.
