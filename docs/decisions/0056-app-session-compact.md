# 0056. 앱이 세션 정리를 청하고 끝날 때까지 기다린다

- 날짜: 2026-11-20
- 상태: 확정. 기다리는 시간과 권하는 `min_tokens` 값은 [제안].
- 결정 방식: 사용자 지시("앱에서 정리 요청을 전송하고 동기적으로 완료를 기다릴 수 있는 api를 추가해. 앱에서 사용자가 선택 시 이를 먼저 요청한 후 그 다음 모델이 변경될 수 있도록").
- 관련 결정: 0004(세션 compact), 0043(앱 메서드), 0050(재시작 복구), 0055(주 모델)

## 그전

- 세션 정리는 자동(크기, 유휴)과 관리 페이지의 "지금 정리"뿐이었다. "지금 정리"는 큐에 넣고 바로 돌아오며, 결과는 나중에 화면에서 본다.
- 주 모델을 바꾸면 새 모델이 대화 전체를 다시 읽는다(결정 0055). 먼저 정리하라는 안내는 있었지만 앱에서 할 길이 없었다.

## 결정

- 앱 메서드 **`session.compact`**: 상주 세션을 정리하고, 끝난 뒤에 결과로 답한다. 범위는 두지 않는다(주 모델 바꾸기와 같은 판단: 안전 장치가 아니고, 앱 토큰은 이미 대화로 모델을 부를 수 있다).
- **작업 큐에서 돈다**(`Job::Compact`). 대화·정기 작업과 겹치지 않고 차례를 기다린다. 메서드는 답 통로로 결과를 기다린다.
- **결과**(`outcome`): `compacted`(앞뒤 토큰), `unchanged`, `small`, `none`, `reset`. 다섯 모두 성공 답이다(그 뒤 모델을 바꿔도 된다). 정리를 돌리지 못했으면 오류 `failed`다.
- **다시 불러도 한 번만 돈다**: 마지막 정리 뒤에 실행이 없으면 모델을 부르지 않고 `unchanged`로 답한다. 호출은 연결에 묶여 있지 않아, 앱이 뒤로 가서 답을 놓쳐도 정리는 끝난다. 다시 연결해 부르면 `unchanged`를 받는다.
  - 이 확인은 큐 안(작업자)에서 한다. 접속 API에서 미리 보면 도는 대화와 엇갈린다.
  - 관리 페이지의 "지금 정리"는 그대로 늘 돈다(캐릭터 파일을 바로 적용하는 데 쓰기 때문이다).
- **짧은 대화는 건너뛴다**: `min_tokens`를 주면 맥락이 그보다 작을 때 `small`로 답한다. 대화 크기를 알려 주는 메서드를 따로 두지 않고, 크기로 가르는 일을 데몬이 한다.
- **한 번에 하나**: 앱이 청한 정리가 큐에 있거나 도는 동안의 요청은 `busy`다.
- **기다리는 시간**: 실행 시간 제한 × 2 + 30초(운영 630초). 앞선 실행 하나와 정리 하나가 각각 시간 제한을 다 써도 답이 들어온다. 넘기면 `timeout`이다.
  - 그때 답 통로가 닫힌다. 아직 차례가 오지 않은 요청은 작업자가 건너뛴다(앱이 그 사이 모델을 바꿨다면 늦은 정리는 새 모델로 대화 전체를 읽는다).
  - 이미 시작한 정리는 끝까지 간다.
- **재시작**: 정기 작업처럼 하는 동안 `runtime.running`에 적어 둔다. 배포 스크립트가 끝나기를 기다리고, 끊기면 다시 뜬 뒤 한 번 다시 한다(기다리는 앱은 `closed`를 받거나 연결이 끊긴다).
- **순서**: 정리는 지금 주 모델이 한다. 그래서 앱은 정리 → 모델 바꾸기 순서로 부른다. 둘을 한 호출로 묶지 않았다(사용자 지시가 따로 부르는 것이고, 정리만 따로 쓸 수도 있다).
- 개발 명령 `luciad routine --config <개발 설정> compact`를 더했다(실측용).

## 잰 것(개발 설정, 2026-11-20)

같은 상주 세션(맥락 약 12만 8천 토큰, 주 모델 Sonnet, 마지막 실행 뒤 약 6시간 50분).

| 단계 | 모델 | 새로 쓴 토큰 | 걸린 시간 | 원장 비용 |
|---|---|---|---|---|
| 정리 | claude-sonnet-5-5 | (128,662 → 2,778) | 48초 | $0.36 |
| Opus로 바꾼 뒤 첫 대화 | claude-opus-5-5 | 39,268 | 6.2초 | $0.33 |
| (비교, 결정 0055) 정리 없이 Opus로 | claude-opus-5-5 | 121,859 | 5.8초 | $1.01 |

- 먼저 정리하면 새 모델이 처음 읽는 양이 약 3분의 1로 줄었다. 정리 비용을 더해도 $0.69로 $1.01보다 적다.
- 정리한 뒤에도 첫 실행은 약 3만 9천 토큰을 읽는다(시스템 프롬프트, 도구 목록, 세션 첫 턴의 지침 전체). 맥락이 이보다 충분히 클 때만 이득이라, 앱에는 `min_tokens` 80,000쯤을 권했다.
- 이 정리의 원장에는 캐시 토큰이 0으로 적혔다(`/compact` 실행은 토큰 내역이 잡히지 않는다). 비용 $0.36과 마지막 실행 뒤 약 6시간 50분이 지난 점으로 보아, 캐시가 식어 Sonnet이 대화 전체를 다시 읽은 것으로 추정한다. 한 시간 안에 대화가 있었다면 더 쌀 것이다(재지 않았다).
- 정리는 지금 모델이 하므로, 더 작은 모델로 갈 때(Fable → Haiku 등)는 먼저 정리하는 것이 손해일 수 있다. 이것은 가격으로 따진 추정이고 재지 않았다. 앱용 문서에도 추정이라고 적었다.
- 정리 뒤 Opus는 정리 전의 대화(문서 만들기, 사이트 정리 등)를 요약으로 답했다.
- 운영의 정리 23번: 평균 49초, 21~73초, 평균 $0.23.

## 하지 않은 것

- 모델을 바꿀 때 데몬이 알아서 정리하기(결정 0055 그대로, 사용자가 고른다).
- 대화 크기·정리 시각을 알려 주는 상태 메서드. 다시 불러도 안전하고 `min_tokens`가 있어 지금은 필요하지 않다.
- 도는 정리를 멈추기.
- 진행 프레임(정리는 모델 호출 한 번이라 중간 단계가 없다).

## 확인

- **시험**: 작업자 루프를 지나는 시험(대화가 먼저 큐에 있으면 그 뒤에 정리하고 답한다, 다시 청하면 모델을 부르지 않는다, 기다리는 쪽이 떠난 요청은 건너뛴다, 작은 맥락은 건너뛴다, 하는 중 표시를 지운다). 접속 API 시험(WebSocket으로 불러 결과 다섯 가지와 `busy`·`timeout`·`bad_params`·`unsupported`, 시간을 넘기면 답 통로가 닫히는 것, `welcome.methods`).
- **실제**: 위 표(정리는 개발 명령으로, 메서드와 같은 엔진 함수). 접속 API에서 실제 정리까지 이어지는 길은 실제 앱으로 보지 않았다(개발 데몬은 운영과 같은 Discord 봇을 써서 띄우지 않는다).
