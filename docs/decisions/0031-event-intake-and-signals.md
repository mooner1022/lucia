# 0031. 이벤트 입구와 단계형 신호 처리

- 날짜: 2026-11-18
- 상태: 확정. 값(확인 간격 5분, 분류 하루 48번, 깨우기 하루 12번, 미뤄진 "지금" 12시간)은 [제안]이고 관리 페이지에서 바꾼다.
- 결정 방식: 소유자 기능 개선안 B("이벤트 수신과 단계형 깨우기")를 검토한 적용안(`docs/proposals/functional-brief-review.md` §4)을 따랐다. 소유자 지시: "확인하고 적용해."
  - 메일 수신 방식은 물어서 정했다: "5분 증분 확인으로 진행하되, 웹소켓 등을 이용한 이벤트 연결에 대비한 밑작업을 해둬." Pub/Sub은 이번에 만들지 않는다.
- 결정 0015의 [제안](점검에서 모델로 소식 엮기)을 이 결정의 2단계로 확정한다.

## 배경

- 사전 체크는 이미 증분이었다(Gmail `historyId`, 캘린더 `syncToken`). 느린 까닭은 매시라는 간격이었다.
- 사전 체크가 찾은 변화는 아침 브리핑과 "변화마다 도는 루틴"에만 쓰였다. 루틴을 따로 만들지 않으면 낮에 온 중요한 메일을 다음 날 아침에 알았다.

## 결정

### 이벤트 입구(`events` 모듈)

- 바깥에서 "바뀐 것이 있다"는 소식이 들어오는 길을 하나로 모은다. 들어오는 것은 둘이다: 확인 요청(`Check`), 외부 이벤트(`Event`).
- **증분 확인**: 관리 페이지 "새 메일·일정 알림"의 확인 간격(기본 5분, 1~60분)마다 사전 체크를 작업 큐에 넣는다. 밀린 요청은 한 번으로 합친다. 바뀐 것이 없으면 API 한 번으로 끝나고 모델을 부르지 않는다.
  - 운영 설정 파일의 매시 사전 체크(`hourly-precheck`)는 남아 있어도 해가 없다(한 번 더 확인할 뿐). 관리 페이지에 "사전 체크(설정 파일)"로 보인다.
  - 감시(결정 0019)는 지금처럼 자기 간격대로 돈다.
- **기기 이벤트**(밑작업): 접속 API(결정 0021)의 `device` 역할 토큰이 WebSocket으로 `{"type":"event","key":…,"text":…}`를 보내면 같은 입구로 들어간다.
  - 기기는 사람이 아니다. 이벤트 프레임과 핑만 받고, 말 보내기·카드 누르기는 거절한다. 글은 외부 데이터로 다룬다.
  - 한 연결에 한 시간 60개 [제안]. 넘으면 거절한다(기기 고장이 모델 호출로 번지지 않게).
  - 이벤트 입구가 없는 실행(시험용 데몬 등)에서는 지금처럼 기기 연결을 받지 않는다.
- 다른 통로(Gmail Pub/Sub, 웹훅 중계 등)를 붙일 때는 이 입구에 `Check`나 `Event`를 넣는 어댑터 하나만 더한다.

### 신호 처리(세 단계, 저장소 `signals`, 마이그레이션 0018)

1. **코드**(사전 체크 안, 모델 없음)
   - 버림: Gmail 라벨이 스팸·프로모션·소셜인 메일, 한 번에 많이 와 개수만 아는 묶음, 내가 만들었거나 주최한 일정의 변화, Lucia가 바꾼 일정(표지 `extendedProperties.private.lucia`, 결정 0033에서 쓴다).
   - 관심 표시: 관리 페이지 "관심 발신자·키워드"(줄마다 하나)가 보낸 사람·제목에 들어 있으면.
   - 사전 체크가 Gmail 변화에 보낸 사람, 제목, 라벨, 미리보기(150자)를 싣는다. 보안 메일(일회용 코드, 재설정 링크)은 미리보기를 싣지 않는다(메일 읽기와 같은 판정).
2. **작은 모델**(`[models] classify`, 기본 `haiku`, 작업 큐 밖)
   - 기다리는 신호를 30개까지 묶어 한 번에 "지금 / 소식 / 버림"으로 나눈다.
   - 입력: 메일은 보낸 사람·제목·미리보기, 일정은 변화 한 줄, 기기 이벤트는 글. 본문은 넣지 않는다.
   - 입력은 공격자가 쓸 수 있는 글이다. 새 세션, 보고 도구만(`ReportOnly`), `<external_data>`로 감싸 닫는 태그를 위조하지 못하게 한다. 결과는 받은 ID와 정해진 세 값만 받고, 없거나 모르면 "소식"이다.
   - 관심 표시가 있는 것은 모델이 "버림"이라 해도 "소식"으로 온다(메일이 "버려라"고 시켜도 사라지지 않게).
   - 판정과 근거 한 줄을 활동 기록(`signal`)에 남긴다(마스킹).
   - 하루 상한(기본 48번), 꺼짐, 비용 상한이면 모델 없이 모두 "소식"으로 모은다.
3. **Lucia**(작업 큐 안, 상주 세션, 브리핑 범위 `Background`)
   - "지금"만 넘긴다. 메일 ID를 실어 `mail_read`로 읽게 하고, 알릴 가치가 없으면 `-`로 보고해 아무것도 보내지 않는다.
   - 브리핑 범위라 메일 발송·폼 제출은 없다(메일이 시킨 외부 쓰기가 사람 없이 나가지 않게). 위임 사이트 읽기와 후속 조치 등록은 된다. 위임 밖 사이트 카드가 승인되면 브리핑 사슬로 이어 한다(결정 0030).
   - 방해 금지 시간에는 미루고, 끝난 뒤 작업자가 조용할 때(5분마다) 넘긴다. 12시간 넘게 미뤄진 것은 소식으로 돌린다.
   - 하루 상한(기본 12번)·비용 상한이면 소식으로 돌린다. 넘기는 순간 표시해 실행이 실패해도 같은 신호로 다시 깨우지 않는다(실패는 알린다).
- **소식**은 지금의 묶음(결정 0015, "📬 모아 보는 소식")으로 간다. 한 줄은 `📨 보낸 사람 — 제목`.
- **브리핑과 겹치지 않게**
  - 브리핑은 지금처럼 모든 변화를 받되, 낮에 이미 알린 것(소식, Lucia의 알림)에는 "(이미 알림 보냄)"을 붙이고 지침에 "다시 자세히 쓰지 않는다"를 더했다.
  - 브리핑이 다룬 변화 가운데 아직 분류 전이거나 넘기기 전인 신호는 "브리핑에서 다룸"으로 닫는다(아침 7:30 사전 체크의 새 메일이 브리핑 뒤에 또 오지 않게).

### 관리 페이지

- 시스템 화면 "새 메일·일정 알림": 켜기, 확인 간격, 관심 발신자·키워드, 하루 분류·깨우기 상한, 오늘 쓴 횟수, 최근 신호 15개(판정, 근거, 관심).

## 하지 않은 것

- Gmail Pub/Sub(소유자 답). 입구에 어댑터만 더하면 붙는다. 캘린더는 Pub/Sub으로 알리지 않으므로 어느 쪽이든 증분 확인이다.
- 소스 오류 알림을 따로 줄이지 않았다. `alert`가 이미 같은 글을 6시간에 한 번만 보내 5분 간격에서도 하루 네 번까지다.
- 진행 중인 목표의 관심사(결정 0032)와 반응 규칙(결정 0034)은 그 결정에서 1·2단계에 더한다.

## 시험

- 바뀐 것이 없으면 모델 호출 0번(`no_change_means_no_model_call`).
- 관심 발신자 메일 → 1단계 통과(프로모션은 버림) → 2단계(새 세션, 분류 모델, 보고만, 외부 데이터) → 3단계(브리핑 범위, 메일 ID) → 한 번만 → 다음 날 브리핑에 "(이미 알림 보냄)".
- 상한이면 모델 없이 소식, 방해 금지면 미루고 끝난 뒤 넘김.
- 기기 이벤트는 같은 키 한 번, 접속 API에서 기기는 이벤트만(말·누르기 거절, 사람의 말로 들어가지 않음).
- 2단계 결과 읽기: 모르는 ID·판정은 버림, 관심사는 버리지 않음, 닫는 태그 위조 막기.
- 관리 페이지 설정 저장과 범위 밖 거절.
- 작업자 큐 전체(확인 요청 → 사전 체크 → 큐 밖 분류 → 큐로 돌아와 알림).

## 배포 뒤 검토로 고친 것(같은 날)

- **끄기**: 끄면 신호를 아예 만들지 않는다(예전에는 모두 소식이 됐다). 끈 뒤 남은 신호는 "브리핑에서 다룸"으로 닫는다.
- **"(이미 알림 보냄)"**: 소식은 실제로 나간 것만 알린 것으로 본다. 방해 금지로 쌓여 있던 소식은 브리핑이 다루고, 그 소식은 거둔다(브리핑 뒤에 같은 것이 또 가지 않게).
- 캘린더 쓰기 권한이 없으면 3단계 지침에서 캘린더 추가를 빼고 알림에 적게 한다(`calendar_note`).
- 실제 모델(개발 샌드박스, `luciad routine signals:sample`): 학과 사무실의 "[긴급] 내일 오전 9시 발표 순서 변경"과 친구의 "주말에 시간 돼?"는 now, 기술 뉴스레터는 drop. 출력 형식(`ID 판정 근거`)을 그대로 지켰고, 3단계 Lucia는 두 건을 짧게 알렸다(시험용 메일 ID라 원문은 찾지 못했다고 밝힘).
- 운영에서 처음 보는 것: 실제 메일에서 분류가 얼마나 "지금"을 고르는지, 하루 분류 횟수.
