# 0063. 앱에서 로그인 정보를 넣고, 사람 확인 화면을 넘겨받는다

- 날짜: 2026-11-21
- 상태: 확정. 한도(입력 칸 8개, 칸 이름 40자, 값 1000자)와 앱이 입력창을 그리는 방식은 [제안]. 화면 넘겨받기의 15분은 결정 0017의 값을 그대로 쓴다.
- 결정 방식: 사용자 지시 "지금은 앱에서 로그인을 요청해도 직접 관리 페이지에 접속해서 비밀번호를 기입하고 확인하는 일련의 과정이 필요해. 이런 과정을 앱 내에서 수행할 수 있도록 api를 개선해. 이와 유사한 상황이 또 있다면 함께 개선해."
- 관련 결정: 0006(로그인은 데몬이 한다, 입력 링크), 0017(인증 코드 카드, 화면 넘겨받기), 0038(입력 링크 다시 쓰기, 떨어진 작업), 0043(앱 연동, 알림 받을 곳, 범위), 0053(범위로 허락하는 방식)
- 앱 쪽 설명: `docs/app-api.md` 3.4, 5.3, 5.6, 6.7, 8.9, 9.1, 11, 12.5, 13, 14, 15, 17.5와 `docs/app-api-changes.md`

## 배경

앱을 쓰는 사용자도 로그인이 걸리면 관리 페이지로 가야 했다.

- **아이디·비밀번호**: 사이트에 로그인이 필요한데 저장된 로그인이 없으면 데몬이 글 하나를 보냈다. 글에는 관리 페이지의 일회용 링크(`/site-login/<토큰>`)가 있고, 사용자는 그 링크를 브라우저로 열어 값을 넣었다. 앱 대화로 오는 글이어도 길은 같았다. 앱의 승인 카드는 이미 값을 하나 받을 수 있었지만(`prompt`, 결정 0017) 칸이 하나뿐이었고, 로그인 정보를 받는 카드는 없었다.
- **사람 확인(캡차 등)**: 비밀번호를 넣은 뒤 사이트가 사람 확인을 띄우면 데몬은 관리 페이지 "브라우저 넘겨받기"의 링크를 보냈다(결정 0017, 0038). 그 화면은 관리 페이지에만 있었다. 밖에서 관리 페이지에 들어가려면 2단계 인증도 필요하다(결정 0043).

## 비슷한 상황을 훑어 본 것

| 상황 | 앱에서 | 이번 결정 |
|---|---|---|
| 로그인 정보 입력(처음, 또는 저장된 로그인이 거절됨) | 링크로 관리 페이지 | 앱 카드로 옮겼다(아래 1) |
| 사람 확인 화면 풀기 | 관리 페이지 | 앱 메서드로 옮겼다(아래 2) |
| 인증 코드(OTP) | 카드(`prompt`)가 이미 앱에서 된다 | 안내 글에서 "Discord 카드"라는 말만 뺐다 |
| 저장된 로그인으로 다시 로그인(`site_login`) | 승인 카드가 이미 앱에서 된다 | 그대로 |
| Google 연결·다시 연결 | 관리 페이지 | 하지 않았다(아래 "하지 않은 것") |
| OpenAI API 키 | 관리 페이지 | 하지 않았다 |
| 상한·위임·감시 조정 등 설정 | 관리 페이지 | 하지 않았다 |

## 결정

### 1. 로그인 정보 입력을 앱 카드에서

- **언제 카드로 가나**(`SiteLogins::card_target`): 알림 받을 곳(결정 0043)이 앱 대화이고 승인 데스크가 있을 때다. 이때 사용자에게 아이디·비밀번호를 청하는 곳은 모두 카드다. 처음 로그인뿐 아니라 저장된 로그인이 사이트에 거절됐을 때의 "다시 넣어 주세요"도 같다. 알림 받을 곳이 Discord이면 예전처럼 글과 링크다(Discord로 비밀번호를 받지 않는다. 결정 0006 그대로).
- **카드**: 승인 종류 `login_input`. 첫 버튼 "로그인 정보 입력"에 새 필드 **`form`**이 붙는다. 칸은 `username`(글, 1~100자), `password`(가려서 받는 글, 1~200자), `save`(켜고 끄는 칸, "이 로그인 저장(다음부터는 승인만)")다. 둘째 버튼은 "취소"다. 카드 본문에는 입력 링크도 있다("버튼이 없거나 안 되면: <링크>"). 사이트 주소(`origin`)와 요청한 까닭(`reason`)이 칸으로 보인다. 만료는 입력 링크와 같다(설정 `[browser] login_input_minutes`, 기본 10분). 만료되면 로그인하지 않는다.
- **누르기**: 앱이 입력창을 띄우고, 사용자가 확인하면 `press`에 새 필드 **`inputs`**(칸 이름 → 값)를 실어 보낸다. `form`이 있는 버튼을 `inputs` 없이 누르면 무시한다(카드는 열린 채 남는다). `inputs`가 있기만 하면(빈 객체 `{}`도) 로그인을 시도한다. 데몬은 칸의 `min_len`·`max_len`을 프레임에서 검사하지 않는다(앱이 먼저 확인한다). 한도는 칸 8개, 칸 이름 40자, 값 1000자이고 넘으면 `bad_frame`이다. 값은 다듬지 않는다(비밀번호의 앞뒤 공백도 값이다). 아이디의 앞뒤 공백만 로그인 모듈이 지운다.
- **데몬이 하는 일**: 승인 데스크가 값을 로그인 모듈(`SiteLogins::submit_input`)에 곧장 넘기고, 비밀번호를 가림 필터에 등록한 뒤 **떨어진 작업**(결정 0038)으로 로그인한다. 카드는 바로 닫히고 "⏳ 로그인하고 있습니다. 결과는 곧 알려 드립니다."가 보인다. 요청이 이미 만료됐거나 다른 곳에서 쓰고 있으면 "❌ …"로 닫힌다.
- **결과는 경우에 따라 다르게 온다**(카드가 닫힐 때의 "⏳"는 받았다는 뜻일 뿐이다):

  | 결과 | 앱이 받는 것 |
  |---|---|
  | 로그인 성공 | "✅ …에 로그인했습니다. …" `text` |
  | 이미 로그인돼 있었다 | "✅ <사이트>: 이미 로그인돼 있었습니다. …" `text`(넣은 비밀번호는 확인하지 못해 저장하지 않는다) |
  | 인증 코드가 필요하다 | 인증 코드 카드(`prompt`가 있는 카드). `text`는 없다 |
  | 사이트가 사람 확인을 띄웠다 | "🧩 …" `text`(화면 넘겨받기 안내, 아래 2) |
  | 사이트가 거절하는 등 다시 넣을 수 있는 실패 | "⚠️ … 로그인하지 못했습니다: …" `text`와 **새 카드**(새 `ref`, "앞선 시도" 칸에 까닭) |
  | 시도를 다 썼다(3번) | "⚠️ … 이 링크로 3번 시도해 닫았습니다. …" `text`만. 카드로 한 시도도 "이 링크"라고 쓰여 온다. 다시 하려면 Lucia에게 요청한다. |
  | 시도하지 못했다(빈 칸·너무 긴 값, 사람이 브라우저를 넘겨받는 중) | 새 카드만(`text`는 없고, 시도로 세지 않는다) |
  | 150초 안에 끝나지 않았다 | "⚠️ …" `text` + 새 카드(시도로 센다) |

- **다시 넣기**: 다시 넣을 수 있는 실패면 **새 카드**를 올린다. 같은 요청(같은 토큰)이라 시도 수는 링크와 합쳐 3번이다(`INPUT_ATTEMPTS`). 새 카드의 "앞선 시도" 칸에 실패한 까닭이 보인다. 시도하지 못한 경우(빈 칸·너무 긴 값, 사람이 화면을 넘겨받는 중)는 세지 않고 알림 없이 새 카드로만 알린다.
- **카드와 링크는 한 요청이다**: 같은 토큰을 쓴다.
  - 카드에서 로그인을 시작하면 링크는 "하는 중", 끝나면 그 결과를 보인다.
  - 카드의 "취소"를 누르면 링크도 닫는다. 만료로 닫힌 카드는 링크를 닫지 않는다(링크는 제 시간에 스스로 닫힌다).
  - 링크로 로그인을 끝내도 열려 있던 카드는 저절로 닫히지 않는다. 그 카드를 누르면 "❌ 이미 끝난 요청입니다…"로 닫힌다.
- **앱이 끊겨 있고 푸시도 없으면**: 카드는 Discord DM으로 간다(결정 0043의 라우팅 그대로). Discord 어댑터(`send_card`)가 `form`이 있는 버튼을 그리지 않으므로 그곳에서는 "취소"만 보이고, 본문의 링크가 길이다. 능력 `forms`는 앱만 켜 두지만 코드가 그 값을 읽어 가르지는 않는다. 걸러내는 곳은 Discord 어댑터다.
- 새 프로토콜 조각은 판 2 안에서 더하기만 한다(앱은 모르는 필드를 무시한다): 버튼의 `form`, `press.inputs`, `welcome.capabilities.forms`.

### 2. 사람 확인 화면 넘겨받기를 앱에서

- **범위 `browser_handover`**(기본 꺼짐): 관리 페이지 → 연결 → 토큰의 "범위"와 발급 폼에서 "브라우저 화면 넘겨받기 허용"으로 켠다. 범위가 없으면 아래 메서드가 `welcome.methods`에 보이지 않고 불러도 `forbidden`이다.
- **메서드 넷**: `browser.handover.state`(상태), `start`(시작), `input`(클릭·글·키·스크롤), `end`(끝). 브라우저를 켠 데몬에서만 등록되므로 브라우저가 꺼진 데몬은 `welcome.methods`에 넷 다 없다.
- **화면**: `GET /v1/browser/handover/frame/{tab}`이 JPEG 한 장을 준다. 저장하지 않게 한다(`Cache-Control: no-store`). 이미지의 한 픽셀이 브라우저 화면의 한 CSS 픽셀이라 이미지 위의 좌표를 그대로 `input`의 `click`에 쓴다.
- **관리 페이지와 같은 것**: 같은 `BrowserTools`의 넘겨받기를 부른다. 최대 15분(`HANDOVER_MAX`), 넘겨받는 동안 Lucia의 모든 실행이 브라우저를 쓰지 못한다. 새 창(본인인증 팝업 등)은 탭으로 남고 끝내면 닫힌다. 한 번에 넣는 글 2000자, 한 번에 굴리는 양 ±3000px도 같다. 시작과 끝은 활동 기록에 남고(`handover_start`, `handover_end`) 넣은 글과 누른 자리는 남기지 않는다. 화면 이미지는 저장하지 않는다.
- **앱이 이 화면을 열 때를 아는 법**: 사람 확인이 뜨면 데몬이 알림 글("🧩 …")을 보낸다. 알림 받을 앱의 토큰에 이 범위가 있으면 글이 "앱의 브라우저 화면 넘겨받기(또는 관리 페이지 \"브라우저 넘겨받기\")에서"라고 안내한다. 앱에 이 일을 알리는 전용 프레임은 없다(남은 질문).

### 3. 안내 글

- 인증 코드 카드의 안내를 "Discord 카드의 [코드 입력]이나…"에서 "카드의 [코드 입력]이나…"로 고쳤다. 앱에서도 같은 카드이기 때문이다.
- Lucia가 받는 도구 결과("로그인 입력 링크를 Discord로 보냈다")도 "알림으로"로 고쳤고, 카드를 올렸을 때의 새 문구(`Requested::InputCard`)를 더했다. 모델에게는 이번에도 비밀번호를 묻지 말라고 알린다.

## 보안

### 비밀번호가 가는 길

| 단계 | 어디서 어디로 | 비고 |
|---|---|---|
| 1 | 앱 → 데몬 | WebSocket `press.inputs`. 밖은 `wss`, 집 안은 `ws`(결정 0043: 집 LAN·VPN을 믿는다) |
| 2 | 접속 API → 승인 데스크 | `SecretText`로 감싼다. `Debug`와 로그에 값이 찍히지 않는다. 입력 칸의 값(`FormValue`)도 `Debug`에 값이 없다 |
| 3 | 승인 데스크 → `SiteLogins` | `execute_form`이 로그인 모듈에 넘긴다. 승인 기록·활동 기록·카드 문구에는 결과 문구만 남긴다(값이 없다) |
| 4 | `SiteLogins` → 브라우저 | 받는 즉시 가림 필터에 등록하고 브라우저 로그인에 넘긴다(한 글자씩 키 입력, 결정 0038) |
| 5 | (저장을 켰을 때만) 호스트 | 비밀번호는 `systemd-creds`, 아이디는 설정 저장소. 입력 링크와 같다 |

**가지 않는 곳**: Lucia(모델), 로그, 원장, 활동 기록, 승인 기록, 앱으로 보내는 프레임 상자, 대화 기록, Discord. Discord로는 비밀번호를 받지 않는다. Discord 어댑터가 `form` 버튼을 그리지 않으므로 앱이 끊겨 카드가 Discord로 돌아가도 그곳에서 값을 받는 길은 없다.

- 카드에 저장되는 것: 사이트, 까닭, 입력 링크의 토큰과 주소, 앞선 시도의 까닭. 토큰은 링크를 연 사람이 그 요청에 로그인 정보를 넣을 수 있는 권한이라 Discord 글에 링크를 실을 때와 같은 노출이다. 입력 요청 자체는 데몬 메모리에만 있으므로, 데몬이 다시 떠서 요청이 사라진 뒤에 카드가 남아 있다면 눌렀을 때 "❌ 시간이 지난 요청입니다…"로 닫힌다.
- 앱은 `secret` 칸의 값을 저장하거나 로그에 남기지 않는다(`docs/app-api.md` 13장).

### 화면 넘겨받기를 앱에 열면 생기는 위험

- **토큰이 새면**: 이 범위가 있는 토큰을 가진 사람은 **로그인된 브라우저 세션을 보고 조작할 수 있다**(쿠키가 든 프로필이다).
- **관리 페이지와 다른 점**: 밖에서 관리 페이지에 들어가려면 2단계 인증이 필요하지만(결정 0043) 앱 토큰에는 두 번째 요소가 없다. 같은 일이 토큰 하나로 된다.
- **그래서**:
  - 기본은 꺼짐이고 토큰마다 따로 켠다. 토큰별 범위 폼의 체크 상자 도움말은 이 위험을 적는다(발급 폼의 도움말은 "기본은 꺼짐"만 적는다).
  - 범위는 매 호출마다 다시 읽는다. 끄면 다음 호출부터 `forbidden`이다.
  - 최대 15분이고, 끝낼 때까지만 Lucia의 브라우저 사용이 막힌다.
  - 시작·끝은 활동 기록에 남는다. 어느 클라이언트가 했는지는 활동 기록에 없고 데몬 로그에만 클라이언트 ID로 남는다.
  - **토큰이 샜거나 앱을 잃어버렸다면 관리 페이지에서 바로 취소한다.** 취소한 토큰은 화면을 보거나 조작하지 못한다. 이미 시작된 넘겨받기는 최대 시간이 지나거나 관리 페이지에서 "끝내기"를 누를 때까지 남는다.

## 하지 않은 것

- **Google 연결·다시 연결**: OAuth 동의는 어차피 브라우저가 필요하다.
- **OpenAI API 키 입력**: 요청을 기다리는 흐름이 없다(데몬이 사용자에게 값을 청하지 않고, Lucia가 "관리 페이지 \"연결\"에서 넣어 달라"고 말할 뿐이다). 한 번 정하는 설정 비밀이라 관리 페이지에 둔다.
- **설정을 가리키는 글**(비용 상한, 위임 거두기, 감시 조정 등): 입력 요청이 아니라 설정을 바꾸는 일이라 이번 범위 밖이다.
- **라우팅 바꾸기**: 카드가 앱으로 가는 때는 앱이 "알림 받을 곳"일 때뿐이다(`docs/app-api.md` 11장, 그대로). 알림 받을 곳이 Discord이면 앱을 쓰는 중에도 로그인 요청은 Discord 글과 링크로 간다.
- **다른 승인 카드 종류의 도구 결과 문구**: 메일 발송·감시 제안 등에서 Lucia가 받는 글에는 아직 "Discord 카드"라고 적혀 있다. 이번에 고친 것은 로그인 쪽뿐이다.
- **비밀번호를 Discord로 받기**: 결정 0006 그대로 받지 않는다.
- **끌기(drag)·오른쪽 클릭·파일 올리기**: 결정 0017의 한계 그대로다. 슬라이더를 끄는 캡차는 앱에서도 못 넘는다.

## 알려진 한계

- **시도를 다 쓴 알림**: "이 링크로 3번 시도해 닫았습니다"라고 쓰여 온다. 카드로 한 시도도 같다.
- **링크로 끝낸 요청의 카드**: 링크에서 로그인을 끝내도 열려 있던 카드는 저절로 닫히지 않는다. 누르면 "❌ 이미 끝난 요청입니다…"로 닫히고, 두면 만료로 닫힌다(인증 코드 카드와 같다). 링크에서 낸 실패에는 열린 카드가 있으면 새 카드를 올리지 않는다.
- **앞선 시도 칸의 까닭**: 사이트가 돌려준 문구다(200자까지). 새 카드를 올릴 때 가림 필터를 거친다.
- **예전 앱**: `form`을 모르는 앱은 그 버튼을 보통 버튼으로 그린다. 누르면 칸이 없는 누름이라 아무 일도 없다. 데몬은 앱이 `form`을 아는지 알 수 없다(능력은 데몬이 앱에 알리는 쪽뿐이다). 본문의 링크가 길이다.
- **화면 넘겨받기가 필요하다는 신호**: 앱이 받는 것은 알림 글뿐이다. 앱은 `browser.handover.state`를 불러 보거나 사용자가 화면을 열 때 시작한다.
- **브라우저가 닫혀 있으면**: `browser.handover.start`가 브라우저를 새로 띄운다. 로그인하던 화면이 이미 닫혔다면(브라우저를 한동안 쓰지 않으면 닫힌다, 결정 0038의 안내) 그 화면은 돌아오지 않는다.
