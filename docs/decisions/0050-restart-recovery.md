# 0050. 재시작 복구: 받은 메시지를 남기고, 끊긴 일을 알리거나 이어서 한다

- 날짜: 2026-11-20
- 상태: 확정. 한도(기다리던 메시지 12시간, 정기 작업 다시 하기 60분, 배포가 기다리는 180초)는 [제안].
- 결정 방식: 사용자 지시("1, 2, 4, 5 … 개선해")의 2번(재시작하면 대기 중이던 일이 흔적 없이 사라진다).
- 관련 결정: 0012(systemd 서비스), 0014(재시작하면 실행 중인 작업은 실패로 닫는다)

## 잰 것(운영 4일)

- 작업 큐는 메모리에만 있었다. 데몬은 4일 동안 44번 시작됐다(대부분 배포).
- 사용자 메시지 184건 가운데 4건이 답을 받지 못했고, 그중 2건이 재시작 시각과 맞았다. 하루 정리도 한 번 끊겼다(사람이 손으로 다시 걸었다).
- 끊긴 실행은 원장에 흔적이 없었다.

## 결정

- **받은 편지함**(`inbox` 표, 마이그레이션 0028): 받은 메시지를 큐에 넣기 전에 적고, 처리가 끝나면(답이나 실패 알림이 간 뒤) 지운다.
  - 다시 뜬 뒤 **기다리던 것**은 받은 순서대로 이어서 처리한다(12시간 안의 것. 더 오래된 것은 알리기만 한다).
  - **처리하다 끊긴 것**은 다시 하지 않고 그 대화에 알린다: "데몬이 다시 시작되면서 하던 답이 끊겼습니다 … 필요하면 다시 말씀해 주세요."
    - 다시 하지 않는 까닭: 도구 기록은 실행이 끝난 뒤에야 남는다. 끊긴 실행이 메일 카드를 올렸는지, 그림을 만들었는지(돈) 데몬이 알 수 없다.
- **정기 작업**: 하는 동안 설정 `runtime.running`에 적는다. 끊겼으면 다시 뜬 뒤 한 번만 다시 한다(시작한 지 60분 안). 또 끊기거나 늦었으면 알린다. 후속 조치는 스스로 다시 걸리므로 뺐다.
- **남은 실행 끝내기**: 호스트 쪽이 죽어도 VM 안의 claude는 끝까지 돌아 세션에 턴을 남긴다(2026-11-16 실측). 다시 뜰 때 데몬이 띄운 실행(명령줄에 실행별 토큰이 있다)을 VM에서 끝낸 뒤에 복구를 시작한다.
- **멈추는 중**: 데몬이 멈춤 신호를 받으면 먼저 표시한다. 그 뒤 끊기는 일은 흔적을 지우지 않고(다시 뜬 뒤 복구가 본다), "작업 처리 중 오류" 알림도 보내지 않는다. 예전에는 이 알림이 먼저 갔다.
- **배포**: `deploy/install.sh`가 재시작 전에 받은 편지함과 하는 중인 정기 작업이 비기를 기다린다(기본 180초, `LUCIA_DEPLOY_WAIT`, `--force`면 기다리지 않는다). 그래도 끊기면 위의 복구가 맡는다.

## 하지 않은 것

- 끊긴 답을 자동으로 다시 하기(위의 까닭).
- Discord 첨부 주소는 시간이 지나면 만료된다. 오래 기다린 메시지의 첨부는 받지 못할 수 있다(글은 처리한다).
- 작업 세션(작업 줄)과 큐 밖에서 도는 루틴 스크립트는 예전 규칙 그대로다(작업은 실패로 닫는다).
- 디스크 감시: 같은 조사에서 나왔지만 이번 지시에 없어 만들지 않았다(빌드 디렉터리만 치웠다).

## 확인(2026-11-20)

- **시험**: 받은 편지함의 넣기·시작·끝. 다시 뜬 작업자가 끊긴 답을 알리고, 기다리던 메시지를 처리하고(모델 요청은 그 하나뿐), 끊긴 정기 작업을 한 번 다시 하고, 흔적을 치우는 것. 두 번째로 끊긴 정기 작업은 알리기만. 멈추는 중에 끊긴 메시지는 남는다.
- 받은 메시지의 길 전체(받기 → 큐 → 작업자)를 지나는 시험을 더하다가 결함을 하나 찾았다: 복구가 도는 동안(남은 실행 끝내기에 몇 초 걸린다) 도착한 메시지는 받은 편지함과 큐 양쪽에 있어 두 번 처리됐다. 복구로 처리한 메시지의 큐 사본은 넘기게 고쳤다.
- 실제 재시작으로는 이 배포 뒤부터 본다(다음 배포들이 곧 시험이 된다).
