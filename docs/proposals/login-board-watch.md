# 로그인 게시판 감시와 빠른 알림 [제안]

- 날짜: 2026-11-18
- 상태: 사용자 승인("이렇게 진행해"), 적용함. 1단계는 결정 0036, 2·3단계는 결정 0037. 값은 모두 [제안]이고 관리 페이지에서 바꾼다. 아래 본문은 검토 때의 글이라, 적용하며 달라진 것은 결정 문서를 따른다(예: 로그인이 풀렸을 때 재로그인 카드를 자동으로 보내지 않고 알림으로 안내).
- 계기: 사용자 "지금은 사이트 변경 감지 등을 사용하려면 해당 사이트가 공개 페이지여야 하는데, 로그인이 필요한 커뮤니티 게시판 등은 여기에 적용이 불가해서 빠른 폴링과 알림이 불가한 문제가 있어. 개선안을 고안해."

## 1. 지금 무엇이 되고 무엇이 안 되나

### 지금 되는 길

| 길 | 로그인 페이지 | 간격 하한 | 모델 | 변화가 가는 곳 |
|---|---|---|---|---|
| 페이지 감시(결정 0019) | 안 됨(쿠키 없이 가져옴) | 30분 | 0 | 브리핑·묶음 소식 |
| 루틴 스크립트 `lucia.fetch`(0025) | 안 됨(같은 `SafeFetch`) | 5분 | 0 | 스크립트가 `notify` |
| 스크립트 없는 루틴 → Lucia가 브라우저로 읽기(0025·0028) | 됨(위임한 사이트, 로그인된 프로필) | **60분** | **매번** | Lucia의 보고 |

로그인 게시판은 이미 볼 수 있다. 다만 "한 시간에 한 번, 매번 모델을 깨워서"만 된다. 빈칸은 둘이다.

- **(가) 모델 없이 로그인 페이지 읽기**: 데몬의 가져오기는 쿠키가 없다. 로그인된 쿠키는 브라우저 샌드박스 안 프로필에만 있다.
- **(나) 빠른 확인과 즉시 알림**: 공개 감시도 지금은 안 된다.
  - 하한이 30분이다.
  - 변화가 신호 처리(결정 0031)에 들어가지 않는다(`watch:`는 신호 소스가 아니다). 그래서 "지금" 알림이 될 길이 없고, 브리핑이나 묶음 소식으로만 간다.
  - 구간 해시 비교는 게시판에 맞지 않는다. 글이 계속 올라오는 게시판은 확인할 때마다 "바뀜"이 되어 세 번 만에 잡음으로 멈춘다(`PAUSE_AFTER = 3`). 무엇이 새로 올라왔는지도 말하지 못한다(구간 앞 600자뿐).

(가)만 고치면 로그인 게시판을 읽어도 곧 멈춘다. (나)가 먼저다.

### 코드에서 확인한 제약

- 브라우저(`browser/sandbox.rs`)는 **탭 하나, 잠금 하나**다.
  - 시작할 때 남은 탭을 닫고, 새로 열리는 창(팝업)도 닫는다.
  - 감시가 그 탭을 쓰면 대화 중인 Lucia가 보던 화면을 옮겨 버린다.
- **10분 쓰지 않으면 Chrome을 닫고 VM이 쉰다.** 쿠키는 정상 종료 때 디스크에 쓴다.
  - 10분보다 짧은 간격으로 브라우저를 쓰면 2 GB VM이 늘 깨어 있다. 이 호스트는 다른 서비스와 메모리를 나눈다.
- 로그인 흐름(`browser/logins.rs`)은 이미 있다. 내장·일반 프로필, 저장된 로그인(`systemd-creds`), 위임된 로그인(0028), 일회용 입력 링크, OTP 넘김(0017).

## 2. 제안 요약

세 단계로 나눈다. 1단계만으로 공개 게시판이 바로 쓸 만해지고, 2단계가 로그인을 더한다.

1. **게시판 감시(항목 단위)와 빠른 경로**: 공개·로그인 공통.
   - 구간 해시 대신 "글 목록의 새 항목"을 본다.
   - 키워드로 거른다.
   - 데몬이 모델 없이 바로 알리거나, 신호 처리에 넣는다.
   - 확인은 작업 큐 밖 전용 타이머로 하고, 하한은 3분이다.
2. **세션 빌려 읽기**: 데몬이 로그인된 브라우저에서 그 사이트의 쿠키만 꺼내 가벼운 HTTP로 읽는다. 감시와 루틴 스크립트가 함께 쓴다.
3. **(필요할 때만) 브라우저 읽기 모드**: 자바스크립트로 그리는 게시판처럼 HTTP로 안 되는 곳만 쓴다. 따로 둔 감시 탭에서 읽고, 그런 감시가 있는 동안 브라우저를 계속 켜 둔다.

## 3. 1단계: 게시판 감시와 빠른 경로

### 항목 단위 감시(`mode = items`)

- **항목 찾기**: 글 링크의 모양으로 찾는다(링크 패턴).
  - 예: 경로 `/bbs/board.php`와 쿼리 `bo_table=free`가 맞고, 글 번호 `wr_id`가 있는 링크.
  - 항목 키는 정규화한 주소(글 번호)다. 제목은 링크 글이다.
  - 제목 뒤 댓글 수(`[3]`)가 바뀌어도 키가 같으니 새 글이 아니다.
  - CSS 선택자보다 사이트 개편에 덜 깨지고, 카드에서 사람이 읽기 쉽다. 선택자는 패턴으로 안 되는 곳에만 선택으로 둔다.
- **패턴 정하기**: 대화 중 Lucia가 정한다.
  - 브라우저로 게시판을 보고 패턴을 고른다.
  - `watch_propose`가 그 자리에서 한 번 가져와 본다.
  - 찾은 항목 앞 5개를 카드에 보인다. 못 찾으면 만들지 않는다(루틴의 "만들 때 시험"과 같다).
- **새 항목**:
  - 첫 확인은 기준선이다.
  - 그 뒤 처음 보는 키가 새 글이다. 본 키는 해시로 500개까지 남긴다.
  - 고정 공지처럼 늘 있는 글은 이미 본 것이라 다시 알리지 않는다.
- **잡음 멈춤 다시 정하기**:
  - 항목 감시에서는 "새 글이 있음"이 정상이라 연속 변화로 멈추지 않는다.
  - 대신 한 번에 새 항목이 30개를 넘으면 의심한다(패턴이 깨졌거나 목록이 통째로 바뀜). 알리지 않고 기준선만 다시 잡고 소식으로 알린다.
  - 항목이 0개가 되면 오류다(로그아웃이나 개편, 아래 2단계).

### 거르기와 알림 방식

감시마다 정한다.

- **키워드**: 제목에 들어가야 할 말과 빼야 할 말. 없으면 모든 새 글이다.
- **알림 방식**(`notify`), 세 가지 중 하나:
  - `now`: 키워드에 맞는 새 글을 **모델 없이** 바로 보낸다. 예: "📌 [게시판 이름] 새 글: 제목 <링크>".
    - 방해 금지 시간이면 끝날 때 묶어 보낸다.
    - 이 기본 경로는 토큰이 들지 않는다.
  - `classify`: 새 글을 신호(결정 0031)로 넣는다.
    - 소스는 `watch:<id>`, 보낸 곳 키는 감시 ID다.
    - 1단계 거르기 → haiku 분류 → 지금이면 Lucia를 깨운다.
    - 반응 카드와 보낸 곳 규칙(0034)도 그대로 따른다. [필요 없어요]면 그 감시를 조용히 한다.
  - `digest`: 묶음 소식과 브리핑으로만 보낸다(지금 방식).
- **상한**: 감시 하나가 하루에 보내는 `now` 알림은 20건까지다. 넘으면 소식으로 돌리고 한 번 알린다. 관리 페이지에서 바꾼다.

### 새 글 뒤에 스크립트 붙이기(사용자 제안)

키워드로 안 되는 판단을 위한 길이다. 예: 가격이 얼마 아래인 판매글, 본문에 특정 조건이 있는 글, 내 글에 달린 새 댓글.

- **거르는 순서**: 싼 단계가 비싼 단계의 문을 지킨다.

  | 단계 | 하는 것 | 비용 | 언제 도나 |
  |---|---|---|---|
  | ① 새 글 찾기 | 데몬 코드(Rust)로 목록을 비교한다 | 0. VM도 깨지 않는다 | 확인할 때마다 |
  | ② 키워드 | 데몬 코드 | 0 | 새 글이 있을 때만 |
  | ③ 스크립트 | 스크립트 샌드박스의 Python. 필요하면 글 본문도 같은 세션으로 가져온다 | 토큰 0. 스크립트 VM이 잠깐 깬다 | ②를 지난 새 글이 있을 때만 |
  | ④ haiku 분류(선택) | 짧은 판단 | 아주 적다 | 스크립트가 넘긴 것만 |
  | ⑤ Lucia 깨우기 | 요약, 다음 할 일, 후속 조치 | 크다 | 스크립트나 분류가 "지금"이라 할 때만 |

  - 스크립트는 ③에서 끝낼 수 있다. 알릴 글을 직접 쓰면 모델 없이 보낸다(`lucia.notify`). 판단이 필요할 때만 `lucia.wake`로 Lucia를 깨운다.
  - 스크립트를 확인 때마다 돌리지 않는 것이 핵심이다. 스크립트 샌드박스도 1 GB microVM이라, 3분마다 돌리면 브라우저와 같은 문제(늘 깨어 있거나 매번 처음부터 띄우기)가 생긴다. ①·②가 새 글이 있을 때만 문을 열어 준다.
- **이미 있는 것을 잇는다**: 새 장치를 만들지 않고 반복 루틴(결정 0025)을 쓴다.
  - 루틴의 `on_change: watch:<id>` 조건은 사전 체크가 그 감시에서 변화를 찾으면 바로 돈다(`queue_change_fires`). 스크립트는 변화 목록을 `lucia.input["changes"]`로 받는다.
  - 지금은 변화가 "구간이 바뀜" 하나뿐이다. 이것을 새 글 하나당 변화 하나(제목, 링크, 글 번호)로 바꾼다. 작성자는 게시판마다 자리가 달라 뽑지 않는다(결정 0036).
  - 1단계의 빠른 타이머로 확인하는 감시도 같은 자리로 변화를 넘긴다.
  - 그래서 스크립트 쓰기, 만들 때 시험, 기준 상태(`lucia.state`), 실패 세 번이면 멈춤, 관리 화면을 그대로 쓴다.
- **스크립트가 붙은 감시의 알림**: 감시의 알림 방식은 끄고(`notify = script`) 스크립트가 알림을 정한다. 같은 글을 두 번 알리지 않게 하려는 것이다.
- **본문 가져오기**: 스크립트의 `lucia.fetch(url, session=True)`(2단계)로 같은 사이트의 글 본문을 읽는다.
  - 브라우저 방식 감시의 사이트라면 본문도 브라우저로 읽어야 할 수 있다. 그때는 스크립트의 브라우저 읽기 한 가지(`browser_read`)를 더한다. 3단계에서 정한다.
- **가드**: 0025 규칙 그대로다. 로그인 게시판 글은 비공개 자료로 친다. 그래서 다른 사이트로 `fetch`도 하는 스크립트는 루틴 승인 카드를 거친다. 같은 사이트 세션 읽기만 하면 카드가 없다.
- **누가 만드나**: 대화에서 Lucia가 감시와 루틴을 함께 만든다. 예: "중고 게시판에 그래픽카드 30만 원 아래 글 올라오면 알려 줘" → 감시(키워드 "그래픽카드") + 가격을 뽑는 스크립트. 만들 때 지금 목록으로 한 번 시험해 결과를 보인다.

### 빠른 경로

- **전용 타이머**: 1분마다 확인할 때가 된 감시를 고른다.
  - 사전 체크와 작업 큐 밖에서 돌고, 모델이 없으니 대화를 막지 않는다(`spawn_classify`와 같은 자리).
  - 감시 간격에 ±10% 흔들림을 준다.
- **사이트 예의**:
  - 같은 호스트는 3분에 한 번까지 확인하고, 한 번에 하나만 가져온다.
  - 가능하면 조건부 요청(`If-None-Match`, `If-Modified-Since`)을 쓴다.
  - 429·5xx면 간격을 두 배씩 늘려 60분까지 쉰다.
- **하한**(관리 페이지):
  - 항목 감시: 3분, 기본 10분.
  - 구간 감시: 30분에서 10분으로 내린다.
  - 브라우저 모드(3단계): 따로 두지 않는다(브라우저를 계속 켜 둔다, 5절).
- 기존 구간 감시는 그대로 두고 경로만 같은 타이머로 옮긴다.

## 4. 2단계: 세션 빌려 읽기(로그인 페이지)

### 두 방식 비교

| | A. 쿠키를 꺼내 HTTP로 (추천) | B. 브라우저 탭으로 읽기 |
|---|---|---|
| 무게 | 확인마다 HTTP 한 번. VM은 쿠키를 새로 받을 때만 깬다 | 브라우저와 VM(2 GB 할당)을 계속 켜 둔다 |
| 빠르기 | 3분 하한이 가능하다 | 켜 두면 3분도 된다 |
| 자바스크립트로 그리는 게시판 | 못 읽는다(목록을 주는 JSON 주소를 찾으면 된다) | 읽는다 |
| 봇 검사(Cloudflare 등) | TLS 지문이 Chrome과 달라 막힐 수 있다 | 진짜 브라우저라 강하다 |
| 대화와 겹침 | 없다 | 브라우저 잠금을 나눈다. 대화 중이면 건너뛴다 |
| 쿠키가 가는 곳 | 데몬 메모리(호스트). 디스크·로그·저장소에는 남기지 않는다 | VM 안에만 |

**둘 다 만들고 감시마다 고른다(사용자 제안).** 감시에 `fetcher = auto | http | browser`를 둔다.

- **만들 때(`auto`)**:
  1. 쿠키 없이 HTTP로 가져와 항목을 찾으면 공개 HTTP로 정한다.
  2. 아니면 쿠키를 붙인 HTTP로 가져와 찾으면 A로 정한다.
  3. 그래도 못 찾고 브라우저로는 찾으면 B로 정한다. 카드에 "브라우저를 계속 켜 둔다"고 적는다.
  4. 셋 다 못 찾으면 만들지 않는다.
  - 고른 방식과 그 까닭(예: "HTTP로는 목록이 비어 있다")을 카드에 보인다.
- **사람이 고르기**: 대화에서 Lucia에게 말하거나 관리 페이지 감시 화면에서 방식을 바꾼다. 바꾸면 그 방식으로 한 번 시험해 보고 기준선을 다시 잡는다.
- **돌다가 바꾸기**:
  - A가 봇 검사에 막히면(403·챌린지 페이지, 로그아웃이 아닌데 항목 0개) B로 한 회차만 대신 읽어 본다.
  - 그게 되면 B로 바꾸자는 카드를 한 번 올린다. B는 브라우저를 늘 켜 두는 비용이 있어 사람 없이 바꾸지 않는다.
  - 카드에 답하기 전에는 A로 계속 시도하고, 실패는 오류로 보인다.
  - B에서 A로 내리는 것(가벼워지는 쪽)은 사람이 고를 때만 한다. 자주 오가지 않게 하려는 것이다.
- **같은 일을 하는 두 구현**: 둘 다 `watch::Fetch`를 구현한다. 항목 찾기·거르기·알림·세션 만료 처리는 공통이고, 다른 것은 "페이지 글을 어떻게 받나"뿐이다.

- 인증 정보는 이미 호스트가 가진다(저장된 로그인 비밀번호가 `systemd-creds`에 있다). 쿠키가 데몬 메모리에 있는 것은 같은 경계 안이다.
- 대부분의 커뮤니티 게시판(그누보드·XE·카페형)은 서버가 목록을 HTML로 그린다.

### A의 동작

- **세션 꺼내기**:
  - 브라우저가 떠 있을 때 CDP로 그 사이트 출처의 쿠키만 읽는다(`Network.getCookies(urls=[출처])`).
  - 사용자 에이전트도 브라우저 것을 그대로 쓴다.
  - 쿠키는 데몬 메모리에만 둔다. 마스킹 필터에 등록하고, 데몬이 다시 뜨면 비어서 처음 쓸 때 다시 꺼낸다.
  - 꺼내려고 브라우저를 띄우는 것은 세션당 한 번이고, 끝나면 유휴 종료로 닫힌다.
- **보내는 곳 묶기**:
  - 쿠키는 그 호스트(위임이 덮는 범위)로만 붙인다.
  - 넘겨주기 도착지가 위임 밖이면 따라가지 않고 오류로 남긴다.
  - GET만 쓴다.
  - 차단 목록·사설 주소 검사는 `SafeFetch` 그대로다.
- **응답 쿠키**: 응답이 새 쿠키를 주면 데몬의 쿠키 상자만 고친다.
  - 브라우저에 되써 넣지는 않는다(단순하게).
  - 세션을 돌려 쓰는 사이트면 브라우저 쪽 세션이 풀릴 수 있다. 그러면 브라우저가 다음에 쓸 때 위임된 로그인으로 다시 들어간다.
  - 실제로 문제가 되면 되쓰기(`Network.setCookies`)를 더한다.

### 세션이 풀렸을 때(변화로 치지 않는다)

- **알아보는 법**(만들 때 기준을 잡아 둔다):
  - 로그인 경로로 넘겨줌.
  - 401·403.
  - 비밀번호 칸이 보임.
  - 항목이 0개.
  - 만들 때는 쿠키 있이·없이 두 번 가져와 본다. 같으면 공개 게시판이니 세션을 쓰지 않는다.
- **순서**:
  1. 브라우저에서 쿠키를 다시 꺼내 한 번 더 해 본다. 브라우저 쪽이 더 새 세션일 수 있다.
  2. 그래도 안 되면 위임에 `login`이 있고 저장된 로그인이 있을 때만 브라우저로 위임된 로그인을 한다(0028). 그 뒤 쿠키를 다시 꺼낸다.
     - 다시 로그인은 호스트당 6시간에 한 번까지다. 계정 잠금을 피하려는 것이다.
  3. 위임이 없거나, 실패하거나, OTP가 필요하면 감시를 `login_needed`로 멈춘다. 기존 재로그인 카드나 입력 링크를 한 번 보낸다.
     - 로그인이 되면 다음 확인부터 이어간다. 기준선은 그대로라, 그 사이 올라온 글을 한 번에 알린다(30개 상한 안에서).

### 만들기와 가드(핵심만)

- **누가**: 지금처럼 감시는 사람이 카드에서 승인해야 시작한다.
  - 제안은 대화와 목표 점검이 할 수 있다(`watch_propose`).
  - 세션을 쓰는 감시도 이 카드 한 장으로 충분하다.
- **카드**: 기존 `watch_review`에 다음을 더한다.
  - "로그인된 세션으로 이 주소를 N분마다 읽는다"는 줄.
  - 시험으로 찾은 글 앞 5개, 키워드, 알림 방식.
  - 그 사이트에 읽기 위임이 없으면 [감시 시작]이 읽기 위임도 만든다고 적는다.
    - 로그인 위임은 따로다(관리 페이지나 `site_grant_propose`).
- **사이트 규칙 경고 한 줄**: 계정으로 자주 읽으면 사이트 규칙에 따라 계정이 제한될 수 있다고 카드에 적는다.
- **저장**:
  - 새 글 제목·링크는 알림과 신호에만 남는다. 본 키는 해시다.
  - 로그인 게시판의 제목은 비공개 글이다. 신호와 알림 기록은 기존 보존 기간을 따르고, 따로 30일 정리를 더한다.
- **모델에게 갈 때**(classify, 브리핑): 외부 데이터로 감싼다. 출구 검사 대조 자료(0029)에도 넣는다(로그인 페이지에서 읽은 비공개 글이다).

### 루틴 스크립트에서도 쓰기

`lucia.fetch(url, session=True)`를 더한다. 게시판이 목록을 JSON으로 주거나 글 본문까지 봐야 하는 등 패턴 감시로 안 되는 곳을 위한 길이다.

- 위임한 호스트만 받는다.
- 루틴이 선언하는 도구 이름은 `fetch_session`이다.
- 비공개 자료 읽기로 친다. 그래서 일반 `fetch`(바깥으로 보내기)와 함께 선언하면 루틴 승인 카드를 거친다(0025 규칙 그대로).

## 5. 3단계: 브라우저 읽기 모드(필요할 때)

- 만들 때 고르기, 사람이 바꾸기, A가 막혔을 때 바꾸자는 카드는 4절의 `fetcher` 규칙을 따른다.
- **감시 탭을 따로 둔다**: 대화용 탭을 옮기지 않는다. 시작 때 남은 탭을 닫는 규칙과 팝업 닫기에서 이 탭은 뺀다.
- **잠금**: 브라우저 잠금이 잡혀 있으면(대화 중 조작) 그 회차를 건너뛴다.
- **켜 두기**:
  - 브라우저 모드 감시가 하나라도 켜져 있으면 유휴 종료를 하지 않고 브라우저를 계속 켜 둔다.
  - 간격 하한은 따로 두지 않고, 같은 사이트 3분이라는 예의만 남긴다.
- **15분 하한을 버린 까닭**(사용자 지적):
  - 10분 유휴 종료에 15분 간격이면 VM은 5분 쉬고 매번 처음부터 VM과 Chrome을 띄운다.
  - 메모리는 비는 동안의 평균이 아니라 차 있을 때가 문제다. 5분 비워 봐야 다른 서비스에 도움이 거의 없고, 띄울 때마다 CPU만 더 든다.
  - 그래서 계속 켜 두는 것과 드물게 확인하는 것 사이에서 하나를 고른다. 중간 값은 둘의 나쁜 점만 갖는다.
- **관리 페이지**: "브라우저 상시 켜짐(브라우저 모드 감시 N개)"과 VM 메모리를 보인다. 상시 켜 두기가 싫으면 그 감시를 끄거나 HTTP 방식으로 바꾼다.
- 구현 전에 개발 샌드박스로 두 가지를 잰다: 켜 두었을 때 실제 메모리(할당 2 GB 중 얼마를 쓰는지), 처음부터 띄우는 시간.

## 6. 다른 길(코드 없이 또는 나중에)

- **사이트의 알림 메일**: 새 글·댓글 알림 메일을 주는 사이트면 그것을 켜는 것이 가장 가볍다. 지금의 메일 신호와 관심어(0031)로 바로 "지금" 알림이 된다. 채팅 지침에 "로그인 게시판 감시를 부탁받으면 먼저 사이트의 메일 알림이나 RSS가 있는지 본다"를 더한다.
- **기기가 밀어 넣는 이벤트**: 휴대폰 앱의 알림(카페·커뮤니티 앱 푸시)을 기기 토큰으로 이벤트 입구(0031, `device` 역할)에 넣는 길. 외부 기기 계획과 함께 본다.

## 7. 비용과 위험

- **모델**: `now`와 `digest`는 확인당 0토큰이다. `classify`만 haiku 분류 상한(기본 하루 48)을 나눠 쓴다.
- **호스트 자원**:
  - A는 HTTP 한 번이라 거의 없다.
  - B는 브라우저 VM을 계속 켜 둔다.
- **남는 위험**:
  - 봇 검사가 있는 사이트는 A가 막힐 수 있다(B로 돌린다).
  - 세션을 돌려 쓰는 사이트는 브라우저 쪽 세션이 풀릴 수 있다(위임된 로그인이 덮는다).
  - 잦은 확인이 사이트 규칙에 걸릴 수 있다(호스트당 3분, 백오프, 카드 경고).

## 8. 사용자가 정할 것

1. 세션 읽기 방식: 둘 다 만들고 감시마다 자동으로 고른다(사용자 제안, 4절). 정할 것은 A가 막혔을 때 B로 바꾸는 것을 카드로 물을지(추천), 사람 없이 바꿀지다.
2. 키워드가 맞는 새 글의 기본 알림: **모델 없이 바로(`now`, 추천)** 또는 haiku 분류(`classify`).
3. 간격 하한: 항목 감시 3분, 기본 10분이 괜찮은지. 브라우저 모드 감시가 있으면 브라우저를 계속 켜 두는 것이 괜찮은지.
4. 진행 범위: 1~3단계 모두. 순서는 1단계(게시판 감시·빠른 경로) → 2단계(A) → 3단계(B와 방식 고르기)로 하고, 단계마다 시험한 뒤 배포한다.
