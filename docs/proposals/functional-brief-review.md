## 1. 사실 확인: 개선안의 전제와 지금 코드가 다른 곳

1. **"위임서(mandate)"는 없다.** 앞 개선안의 위임서는 고쳐서 **사이트 위임**(`site_grants`, 결정 0028)으로 들어갔다. 호스트 단위의 전역 위임이고, 어떤 일에 묶이지 않는다.
   - 그래서 "목표 하나에 위임서 하나(`mandate_id`)"는 "목표가 쓰는 사이트 위임을 보여 주는 것"으로 바꾼다.
   - 목표를 포기해도 위임은 거두지 않는다(다른 일이 같이 쓴다). 관리 페이지에서 따로 거둔다.
   - `mandate_review` 카드는 없다. 위임이 필요하면 지금의 `site_grant_propose` 카드를 쓴다.
2. **캘린더 쓰기는 없다**(`STATUS.md` §5, 앞 검토 §3.4에서 소유자가 정할 기능으로 남김). C가 이것을 전제로 하므로 C와 함께 넣는다(§3 소유자 답).
3. **사전 체크는 이미 증분이다.** Gmail은 `historyId`, 캘린더는 `syncToken`으로 바뀐 것만 가져오고, 바뀐 것이 없으면 모델을 부르지 않는다. 느린 까닭은 방식이 아니라 **간격(매시)**이다.
   - 매시 사전 체크는 레포 밖 운영 설정(`lucia.toml`)의 cron 항목이다. 내장 정기 실행이 아니다.
4. **사전 체크가 찾은 변화는 지금 브리핑과 "변화마다 도는 루틴"에만 쓰인다.** 낮에 중요한 메일이 와도 루틴을 따로 만들지 않았으면 다음 날 아침에 안다.
5. **소스 오류 알림은 이미 같은 글을 6시간에 한 번만 보낸다**(`alert`). 간격을 5분으로 줄여도 같은 인증 오류는 하루 네 번까지라 따로 고치지 않는다.
6. **`device` 역할 토큰은 자리만 있다**(결정 0021). 표시 장치(F)는 기기가 준비돼야 시험할 수 있다.

## 3. 소유자 답(2026-11-18)

- **메일 즉시 수신**: 5분 증분 확인으로 간다. 웹소켓 같은 이벤트 연결에 대비한 밑작업을 해 둔다. Pub/Sub은 이번에 만들지 않는다.
  - 밑작업: 데몬 안에 **이벤트 입구**를 하나 두고, 증분 확인과 접속 API(WebSocket)의 기기 이벤트가 같은 신호 처리로 들어가게 한다. 나중에 Pub/Sub 같은 통로를 붙일 때는 이 입구에 어댑터 하나를 더한다.
- **목표 점검의 하위 루틴**: 사람 없이 만들기까지 허용. 단, 만든 루틴은 만든 실행(목표 점검)보다 넓은 범위로 돌지 않는다.
- **캘린더 쓰기**: 참석자 없는 내 일정은 바로 만들고 고친다. 지우기는 카드. 참석자가 있는 일정은 카드.

## 4. B: 이벤트 수신과 단계형 깨우기(결정 0031)

### 4.1 이벤트 입구

- 데몬 안에 입구 하나(`events` 모듈). 들어오는 길:
  1. **증분 확인**: 관리 페이지 "이벤트 확인 간격"(기본 5분 [제안], 1~60분)마다 사전 체크를 작업 큐에 넣는다. 운영 설정의 매시 사전 체크는 남아 있어도 해가 없다(한 번 더 확인할 뿐).
  2. **접속 API의 기기 이벤트**(밑작업): `device` 역할 토큰이 WebSocket으로 보내는 `event` 프레임을 같은 입구로 받는다. 기기는 사람이 아니므로 외부 이벤트로 다루고, 다른 프레임(말 보내기, 카드 누르기)은 받지 않는다.
- 다른 통로(Gmail Pub/Sub, 웹훅 중계 등)는 같은 입구에 "증분 확인 요청" 또는 "외부 이벤트"로 넣는 어댑터만 더하면 된다. 이번에는 만들지 않는다.

### 4.2 신호 처리(세 단계)

- **1단계(코드)**: 새 메일·일정 변화·외부 이벤트를 거른다.
  - 버림: Gmail 분류가 프로모션·소셜인 메일, 내가 만든(또는 Lucia가 만든) 일정 변화.
  - 관심 표시: 관리 페이지 "관심 발신자·키워드" 목록, 진행 중인 목표가 선언한 관심사(A 뒤), 반응 규칙(D 뒤)과 맞으면 표시한다.
  - 나머지는 2단계로 넘긴다.
- **2단계(작은 모델, 기본 `haiku`)**: 넘어온 것을 한 번에 묶어 "지금 알릴 것 / 소식으로 모을 것 / 버릴 것"으로 나눈다.
  - 입력은 발신자, 제목, 짧은 미리보기(150자, 보안 메일은 빼고), 관심 표시, 알림 규칙뿐이다. 본문은 넣지 않는다.
  - 입력은 공격자가 쓸 수 있는 글이다. 새 세션, 보고 도구만, `<external_data>`로 감싸고, 결과는 정해진 값만 받는다(모르면 "소식").
  - 판정과 근거 한 줄을 활동 기록에 남긴다(마스킹).
  - **하루 상한**(기본 48번 [제안], 관리 페이지). 넘으면 1단계를 통과한 것을 그대로 소식으로 모은다.
  - 결정 0015의 [제안](주기 점검에서 모델로 소식 엮기)을 이것으로 확정한다.
- **3단계(Lucia)**: "지금 알릴 것"만 상주 세션에서 Lucia를 깨운다. 범위는 브리핑과 같다(`Background`: 읽기, 로컬 쓰기, 위임 사이트 읽기). 메일이 시킨 외부 쓰기가 사람 없이 나가지 않게 하려는 것이다.
  - 방해 금지 시간에는 끝난 뒤로 미룬다.
- 처리한 변화에는 따로 표지를 남겨 두 번 나누지 않는다. 브리핑은 지금처럼 모든 변화를 받되, 이미 알린 것은 "(알림 보냄)"으로 표시해 되풀이하지 않게 한다.

### 4.3 수용 기준과 시험

- 바뀐 것이 없으면 모델 호출 0번(시험).
- 관심 발신자 메일 → 1단계 통과 → 2단계 "지금" → 3단계 실행(가짜 실행기로 시험).
- 상한에 닿으면 소식으로 모은다.
- 개선안 회귀 시험 3번(Pub/Sub 끊김 → 폴링)은 Pub/Sub을 쓰지 않으므로 해당 없다. 확인 오류 알림은 지금처럼 같은 글을 6시간에 한 번만 보낸다(§1-5).

## 5. A: 목표(결정 0032)

- **목표**: 제목, 목적, 끝났다고 볼 조건, 마감(선택), 상태(진행 중 → 대기(사람 차례) → 완료/포기), 점검 주기(기본 하루 1번 [제안]), 진행 기록, 관심사(발신자·키워드·도메인, B 1단계에 쓰임).
- **만들기**: 대화에서 `goal_create`(사람 필요). 카드는 없다. 사람이 대화에서 맡긴 일이고, 루틴·후속 조치도 대화에서 카드 없이 만든다. 필요한 사이트 위임만 지금처럼 `site_grant_propose` 카드로 받는다. 이것이 개선안의 "한 번의 승인"이다.
  - 하위 항목(후속 조치·루틴·감시·작업)은 만들 때 `goal` 인자로 잇는다.
- **목표 점검 실행**: 점검 주기마다, 그리고 하위 항목에서 신호가 오면(루틴 깨우기, 후속 조치 발사, 2단계에서 그 목표 관심사로 "지금"이 된 것) 깨어난다. 사람 없음.
  - 범위: 브리핑 사슬과 같은 등급(로컬 쓰기, 위임 사이트 읽기) + 목표 도구(진행 기록, 상태, 다음 점검) + **자기 목표의** 하위 루틴·후속 조치 만들기·고치기·끝내기.
  - 목표는 실행 맥락(`runctx`)에서 정한다. 모델이 준 목표 ID를 믿지 않는다.
  - **넓어지지 않게**: 목표 점검이 만든 루틴이 깨운 실행과 등록한 후속 조치는 목표 점검과 같은 범위로 돈다(지금 루틴 깨우기는 `Followup` 범위라, 이대로면 넓어진다). 루틴에 출처를 남겨 깨울 때 범위를 고른다.
  - 사이트 위임을 만들거나 넓히지 못한다(P5). 필요하면 상태를 "대기"로 두고 소식으로 알린다(대화에서 위임).
  - 끝났다고 보면 [완료]/[아직] 카드.
  - 한 목표의 점검은 하루 6번 [제안]까지(신호 → 점검 → 새 하위 항목 → 신호 고리를 막는다).
- **포기·완료**: 하위 후속 조치 취소, 하위 루틴·감시 끄기. 사이트 위임은 그대로(§1-1).
- 관리 페이지 "목표" 화면, 아침 브리핑에 진행 중인 목표 한 줄씩.

## 6. C: 교차 정합성 검사와 캘린더 쓰기(결정 0033)

- **캘린더 쓰기 도구**: `calendar_create`, `calendar_update`는 참석자 없는 내 일정만 로컬 쓰기(자동, 직전 상태 보관, 활동 기록, 소식). 참석자가 있으면(고칠 일정에 이미 있어도) 승인 카드. `calendar_delete`는 카드. 초대 메일은 보내지 않는다(`sendUpdates=none`). 검사는 데몬이 한다.
  - Lucia가 만든 일정에는 표지(`extendedProperties.private`)를 달아, 증분 확인에서 돌아온 변화를 1단계에서 버린다(자기를 다시 깨우지 않게).
  - 동의 범위가 없으면 "관리 페이지에서 Google을 다시 연결" 안내로 실패한다. 읽기는 예전 토큰으로 그대로 된다.
- **검사 실행**(`consistency-check`): 하루 2번 [제안](12:30, 18:30) + B의 신호. 먼저 코드로 날짜 후보가 있는 새 메일을 뽑고, 없고 일정 변화도 없으면 모델을 부르지 않는다.
  - 범위: 브리핑 범위 + 캘린더 쓰기(참석자 없는 것만 자동).
  - 메일의 마감·약속이 캘린더에 없으면 추가(참석자 없음) 또는 제안 카드. 일정 겹침, 이동 시간 부족, 기억과 다른 일정은 소식이나 확인 질문.
  - 제안 기록(수락·거절·무시)을 남기고, 거절한 것은 다시 제안하지 않는다.

## 7. D: 반응에서 배우기(결정 0034)

- **반응 단추**: 2단계에서 나온 단독 알림에 [유용해요]/[브리핑에만]/[필요 없어요]. 사람이 누른다.
  - 개선안은 "나" 기억 항목에 쌓자고 했다. 단추가 고치는 규칙은 키(발신자·종류)와 값이 분명한 표가 맞아 **전용 표**(`notice_rules`)에 두고, 관리 페이지에서 보고 지운다. 2단계 입력과 1단계 거르기에 쓴다.
- **일정 기반 방해 금지**: 관리 페이지에서 켜면 캘린더의 바쁜 일정 동안을 조용한 시간으로 쓴다. 제목 예외 단어. 오류와 "지금" 중 마감 임박 건은 예외.
- **단계적 독촉**: 마감이 있는 알림을 `nudges`로 추적한다. D-3 소식, D-1 단독 알림, 당일 아침 카드([처리했어요]/[나중에]) [제안]. 처리 여부는 단추, 대화에서 Lucia가 표시(`nudge_done`), 관련 일정 변화·메일 발송, 목표 진행으로 본다.

## 8. E·F(결정 0035)

- **막힘 보고**: `report_result`에 `blocked`(하려던 것, 못 한 까닭, 풀 방법)를 더한다. 데몬이 같은 모양으로 보이고 기록한다. 범위 밖 거절 문구에 이 형식을 쓰라고 적는다. 풀 방법이 사이트 위임이면 대화에서는 `site_grant_propose`, 사람 없는 실행은 지금의 `site_egress` 카드.
- **주간 자기 보고**(`weekly-review`, 일요일 19:00 [제안]): 데몬이 숫자를 모으고(목표 진행, 자동 외부 쓰기, 막힘, 만료 카드, 실패·멈춘 루틴, 모델별 비용) Lucia가 정리한다. 제안은 실행하지 않고 카드로만 올린다. [진행]을 누르면 카드에 보인 글을 소유자가 말한 것처럼 대화에 넣는다(보이는 것 = 실행하는 것).
- **저녁 미리보기**(21:00 [제안]): 내일 일정, 마감, 목표의 다음 단계. 아침 브리핑은 밤사이 바뀐 것 위주로 줄인다.
