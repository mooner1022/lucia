개인 상시 비서 에이전트 — 작업 명세
​Nov 16, 2026 · ​@문민기
개요
홈서버(Ubuntu 26.04.1)에서 상시 구동하며 사용자와 진행 중인 일을 기억하고, 그 기억을 바탕으로 스
스로 후속 조치를 이어 가는 1인용 비서를 만든다. 매번 처음부터 시작하는 일회성 에이전트가 아니라, 쓸
수록 맥락과 요령이 쌓이는 비서가 목표다. 주된 일은 일정 확인·정리·알림이고, 개발 작업 위임은 보조 기
능이다.
사용자: 본인 1명. 다른 사람에게 서비스하지 않는다. Claude 구독 인증을 쓰기 위한 전제 조건이기
도 하다.
핵심 성질:
연속성: 어제 나눈 대화, 지난주에 맡긴 일, 사용자의 선호를 기억하고 이어서 다룬다.
유기성: 한 소스에서 알게 된 사실을 다른 일정·대화와 연결하고, 약속한 후속 조치를 스스로 챙
긴다.
성장: 성공한 작업은 재사용 가능한 스킬과 도구로 굳혀 다음에는 더 빠르고 싸게 처리한다.
주요 시나리오:
정해진 소스(학교 공지·과제, 메일, 캘린더, 시험 공고 등)를 주기적으로 확인하고, 바뀐 것만 기
존 맥락과 엮어 알린다.
채팅으로 요청을 받는다: 조사, 정리, 리마인더. 이전 대화를 다시 설명하지 않아도 된다.
가끔 레포 대상 개발 작업을 맡긴다.
초기 비목표: 다중 사용자·팀 승인, 여러 메신저 동시 지원, 대시보드, 결제·예약 같은 고위험 쓰기 자
동화.
설계 원칙
모든 설계 판단은 아래 여덟 가지를 기준으로 한다. 상충하면 위쪽 원칙이 우선이다.
1. 인증 정보는 호스트만 가진다. 모델과 VM은 토큰·비밀번호를 보지 못하고, 결과 텍스트만 주고받는
다. Meta Muse의 Sentinel과 같은 방향이다.
2. 에이전트 루프는 만들지 않는다. Claude Code를 엔진으로 쓰고, 그 바깥(기억, 스케줄, 상태, 알림,
승인)만 직접 구현한다.
3. 기억은 일급 시민이다. 모든 실행은 관련 기억을 읽고 시작하고, 끝나면 배운 것을 남긴다. 대화와 작
업은 세션을 이어서 다루고, 세션이 끊겨도 기억 저장소가 맥락을 복원한다.
4. 규칙은 코드로 강제한다. 지켜야 하는 제약은 프롬프트가 아니라 도구 허용 목록, 훅, 데몬의 검증으
로 건다. 에이전트가 배운 스킬도 이 규칙을 바꿀 수 없다.
5. 백그라운드는 읽기 전용이 기본이다. 외부에 흔적을 남기는 쓰기는 승인을 거친다.

6. 바뀐 게 있을 때만 모델을 부른다. 변화 감지는 순수 코드가 먼저 한다. 반복되는 일은 점점 코드로 옮
겨 간다.
7. 바꿀 수 있는 경계를 둔다. 메신저, 실행 백엔드(구독 ↔ API 키), 브라우저는 인터페이스 뒤에 둔다.
8. 조용한 실패는 없다. 인증 만료, 작업 실패, 세션 끊김은 반드시 사람에게 알린다.
시스템 구성
호스트 데몬이 판단과 인증 정보를 모두 갖고, sbx 안에는 실행 코드만 둔다.
점선 상자는 외부 서비스다. 데몬이 상주 작업 공간의 세션을 이어 실행하면, 에이전트는 결과 보고와 승
인 요청을 MCP로만 돌려보낸다. 모델 토큰은 sbx 프록시가, 웹사이트 로그인 값은 데몬이 CDP로 넣기
때문에 VM 안에는 인증 정보가 없다.
실행 계층
에이전트는 sbx 안의 상주 작업 공간에서 Claude Code 세션을 이어 가며 일한다. 데몬은 요청이 올 때
마다 claude -p 로 해당 세션을 이어 붙이고(stream-json), 세션이 끊겨도 기억 저장소로 맥락을 복원
한다.
세션 체계:
시스템 구성 · 호스트 데몬 7개 구성 요소, sbx 샌드박스 2개

상주 세션: 사용자와의 일상 대화와 브리핑을 이어 가는 장기 세션. --session-id 와 재개( -
r )로 계속 이어 붙인다. 컨텍스트가 커지면 요약을 기억 저장소에 남기고 새 세션으로 교대한다.
작업 세션: 오래 걸리거나 독립적인 작업(조사, 개발)은 별도 세션에서 한다. 시작할 때 관련 기
억을 주입받고, 끝나면 결과와 배운 점을 기억 저장소와 상주 세션에 돌려준다. Discord 작업 스
레드 하나가 작업 세션 하나다.
루틴 실행: 사전 체크가 감지한 변화를 처리하는 짧은 실행. 필요한 기억만 받아 처리하고, 결과
는 상주 맥락에 합류시킨다.
대화형 TUI를 상주시키지 않는 이유: hermitd처럼 대화형 TUI를 무인으로 몰면 대화창 정체와 키
입력 의존 문제가 생긴다. 세션 재개 방식은 같은 연속성을 결정적으로 제어할 수 있다.
호출 방식: claude -p 에 stream-json 입출력, --session-id , --plugin-dir , --mcp-
config , --permission-prompt-tool , --max-turns , --append-system-prompt-file
을 조합한다. 정확한 조합은 PoC에서 확정한다.
격리 경계: VM과 네트워크 정책이 경계다. sbx run claude 는 기본으로 --dangerously-
skip-permissions 를 붙인다는 점을 전제로 설계한다. 권한 모드를 직접 정해야 하면 shell 샌드
박스에 직접 설치해서 띄운다.
샌드박스 수명:
상주 작업 공간: 영구 샌드박스 하나. 세션 기록, 작업 파일, 배운 스킬을 유지한다. 세션 기록은
VM 밖에도 주기적으로 백업한다.
임시 샌드박스: 처음 다루는 레포나 낯선 사이트 탐색처럼 신뢰도가 낮은 작업만. 끝나면 지우고,
결과만 기억 저장소로 넘긴다.
브라우저: 로그인 프로필을 유지하는 전용 샌드박스 하나.
네트워크: 기본은 차단이고 허용 목록만 연다. Anthropic API, 호스트 데몬의 MCP 엔드포인트, 작
업에 필요한 최소 도메인이다.
MCP가 유일한 출구다. 데몬이 호스트에서 Streamable HTTP로 MCP 서버를 연다. 도구는 결과
보고, 작업 상태 갱신, 기억 조회·기록, 후속 조치 등록, 스킬 저장, 권한 승인 요청 수준으로 둔다. 메신
저로 직접 보내는 도구는 주지 않는다. 전송은 데몬이 한다.
plugin으로 묶는다. 사람이 쓴 스킬, 훅(PreToolUse 차단 규칙), MCP 설정을 plugin 하나로 묶는
다. 에이전트가 배운 스킬은 별도 디렉터리에 두고, 훅과 권한 설정에는 손대지 못하게 한다.
실행 백엔드는 설정 하나로 바꾼다. 구독 인증과 API 키를 전환할 수 있어야 한다. 구독 사용 정책이
올해 여러 번 바뀌었다.
출력 계약: 최종 결과는 MCP 결과 보고로 구조화해서 받는다. 에이전트의 자유 텍스트 출력을 메신
저로 그대로 흘리지 않는다.
캐릭터와 시스템 프롬프트
캐릭터는 별도 파일로 작성해 --append-system-prompt-file 로 기본 프롬프트 뒤에 붙인다. 매번
바뀌는 맥락은 시스템 프롬프트가 아니라 요청 메시지로 넣는다.

덧붙이기를 기본으로 한다: 기본 프롬프트의 도구 사용·안전·코딩 지침을 유지해야 개발 작업도 맡길
수 있다. 전체 교체( --system-prompt-file )는 비서 전용 프롬프트가 충분히 성숙한 뒤 검토한
다. 교체하면 빠지는 지침을 직접 책임져야 한다.
고정된 것과 바뀌는 것을 나눈다:
시스템 프롬프트: 캐릭터, 말투, 행동 원칙처럼 거의 안 바뀌는 것.
요청 메시지 앞부분: 핵심 기억, 진행 상태 요약처럼 데몬이 매번 조립하는 것.
이유: Claude Code는 대화의 첫 요청에서 만든 시스템 프롬프트를 세션에 기록하고, 압축 전
까지는 재개해도 그대로 쓴다. 바뀌는 맥락을 시스템 프롬프트에 넣으면 상주 세션에서 오래된
내용이 남는다.
캐릭터 변경은 세션 교대 때 적용된다. 다듬는 동안에는 --system-prompt-snapshot off 로 매
요청마다 다시 만들게 할 수 있다. 단, 캐시 효율이 떨어지므로 운영 중에는 끈다.
캐릭터는 말투에만 적용한다: 판단, 정확성, 승인 규칙은 캐릭터와 분리한다. 일정 같은 사실은 캐릭
터를 살리더라도 정확하게 전달하고, 캐릭터 설정이 안전 규칙보다 우선하지 않는다고 파일에 명시
한다.
캐릭터 본체는 보호 영역이다: 훅과 권한 설정처럼 에이전트와 학습 루프가 고칠 수 없다. 프롬프트
인젝션으로 성격이 바뀌는 것을 막기 위해서다. "말투를 좀 더 가볍게" 같은 취향은 핵심 기억에 쌓고,
본체 수정은 사람이 한다.
어디서나 같은 캐릭터: 데몬 실행에는 추가 프롬프트 파일로, 직접 여는 대화형 Claude Code에는
같은 내용을 output style로 등록해 쓴다.
버전 관리: 캐릭터 파일은 plugin과 같은 레포에서 git으로 관리해, 말투가 이상해졌을 때 변경 이력
을 추적한다.
메신저 추상화
처음에는 Discord만 구현하지만, 코어는 메신저를 모르게 만든다. 나중에 자체 앱을 만들면 코어는 그대
로 두고 어댑터만 추가한다.
경계: 코어는 플랫폼에 중립적인 메시지 모델만 다루고, 플랫폼별 차이는 채널 어댑터가 흡수한다.
들어오는 것: 발신자, 대화(스레드), 본문, 첨부, 답장 대상, 버튼 응답(승인 결과).
나가는 것: 텍스트(마크다운 하위 집합), 스레드 답장, 승인 요청(선택지와 만료 시각), 진행 상황 갱
신(메시지 수정), 첨부.
능력 선언: 어댑터가 버튼, 메시지 수정, 스레드, 길이 제한 같은 지원 기능을 선언한다. 코어는 그에
맞춰 표현을 낮춘다. 예를 들어 버튼이 없으면 텍스트 명령으로 승인받는다.
플랫폼 세부는 어댑터 안에 둔다: 길이 분할(Discord는 2,000자), 임베드, 슬래시 커맨드, 레이트 리
밋 재시도. 길드·역할 같은 Discord 개념이 코어로 새지 않게 한다.
신원과 허용: 허용 사용자 판단은 코어가 한다. 어댑터는 플랫폼 ID를 내부 사용자로 매핑만 한다. 기
본값은 거부다. hermitd처럼 "비워 두면 모두 허용"하지 않는다.

Discord 초기 방침: DM 또는 개인 서버의 전용 채널을 쓴다. 작업마다 스레드 하나를 열어 진행 상
황과 결과를 모으고, 승인은 버튼(Interaction)으로 받는다.
자체 앱 대비: 어댑터 인터페이스를 WebSocket이나 HTTP API로 그대로 노출할 수 있는 모양으로
잡는다. 자체 앱은 그 API의 클라이언트가 된다.
인증과 비밀 관리
모든 인증 정보는 호스트 데몬이나 sbx 프록시에만 있고, VM 안과 모델 컨텍스트에는 들어가지 않는다.
Claude: sbx의 호스트 측 로그인을 우선한다(토큰이 샌드박스에 들어가지 않음). 대안은 claude
setup-token (1년 유효, 모델 요청만 가능)이다. 토큰을 VM 안 환경 변수로 넣는 방식은 최후의 수
단이다.
외부 토큰(Discord 봇, Google, GitHub 등): systemd-creds 로 암호화해 보관하고
LoadCredential= 로 데몬에만 넘긴다. 데몬은 전용 시스템 사용자로 돌린다.
에이전트가 API를 직접 불러야 할 때만 sbx secret set 과 프록시 주입을 쓴다. 헤드리스에서는
sbx 비밀값이 파일 권한으로만 보호된다는 점에 유의한다.
Google API: 데몬이 사전 체크에서 직접 부른다. OAuth 동의 화면은 프로덕션 게시 상태로 둔다.
테스트 상태면 refresh token이 7일 만에 만료된다.
비밀 입력 경로는 두 가지다. 값의 수명과 중요도에 따라 고른다.
Discord modal(Interaction): 일회용 인증 코드(OTP), 재로그인 확인처럼 수명이 짧거나 덜
중요한 값. 채팅 기록에 남지 않아 편하지만, 입력값이 Discord 서버를 거치고 가림 입력도 없
다.
WireGuard 내부 전용 웹 폼: 오래 쓰는 비밀번호, API 키. 제3자 서버를 거치지 않는다.
어느 경로든 입력값은 받은 즉시 목적지(브라우저 주입 또는 비밀 저장소)로 보내고 메모리에서
폐기한다. 모델에는 절대 전달하지 않는다.
만료 감지: 모든 인증에 "감지 → Discord 알림" 경로를 둔다. Claude는 실행 오류(로그인 만료) 감
지와 주기적 상태 확인으로, setup-token은 발급 11개월 뒤 리마인더로 처리한다.
로그 위생: 인증 정보와 로그인 입력값은 로그, 원장, 메신저 어디에도 남기지 않는다. 저장 전 마스킹
필터를 통과시킨다.
브라우저와 웹사이트 로그인
비밀번호는 모델 경로에 절대 두지 않는다. 로그인은 사람이 하거나 데몬의 결정적 코드가 한다.
접근 방식 우선순위: 구조화된 소스(API, ICS, RSS) → 데몬의 결정적 스크래퍼(로그인 세션 사용)
→ LLM의 브라우저 조작. 마지막은 탐색이 필요한 일회성 작업에만 쓴다.
브라우저 샌드박스: 프로필(쿠키)을 유지하는 전용 샌드박스를 둔다. 사이트별 세션 상태는 데몬이
추적한다. 출구는 한국 가정용 IP여야 한다. 클라우드 브라우저 차단을 피하는 것이 이 구조의 강점이
다.

작업 모델과 승인
모든 일은 상태가 명시된 작업 레코드로 다루고, 되돌릴 수 없는 행동은 승인 없이 실행하지 않는다.
작업 출처: 루틴(스케줄), 사전 체크가 감지한 변화, 채팅 요청, 리마인더.
상태: 생성 → 실행 중 → (승인 대기 또는 입력 대기) → 결과 보고 → 완료. 실패, 취소, 만료는 별도 종
료 상태다. 완료 확인은 사람만 할 수 있다. 상태 전이는 데몬만 수행하고, 에이전트는 MCP로 요청만
한다.
권한 등급:
승인 경로: --permission-prompt-tool → 데몬 MCP의 승인 도구 → Discord 버튼. 응답이 없
으면 정해진 시간 뒤 거부로 끝낸다. 승인은 그 작업의 그 행동 하나에만 유효하고 재사용하지 않는
다.
백그라운드 작업은 읽기 전용 프로필로 실행한다. 쓰기 도구를 허용 목록에서 아예 뺀다.
실행 한도: 작업마다 턴 수, 시간, 비용 상한을 둔다. 넘으면 중단하고 보고한다.
동시성: 작업은 큐로 관리하고, 브라우저·개발 등 자원 종류별로 동시 실행 수를 제한한다.
재시도: 일시 오류만 제한적으로 재시도한다. 승인 거부나 정책 차단은 다른 경로로 우회하지 않는다.

스케줄링, 사전 체크, 비용 관리
모델은 바뀐 게 있을 때만 부른다. 대부분의 주기 점검은 토큰을 쓰지 않고 끝나야 한다.
스케줄러: cron 식 루틴과 일회성 리마인더를 SQLite에 저장해 재시작 후에도 유지한다. 놓친 실행
은 허용 지연 시간 안이면 실행하고, 넘으면 건너뛰고 기록한다.
사전 체크: 순수 코드로 소스별 변화를 감지한다(해시 비교, ICS 차분, 새 메일 여부 등). 변화가 없으
면 그대로 끝낸다.
소스는 모듈로 더한다. 사전 체크를 공통 인터페이스(트레이트) 뒤에 두고, 새 소스는 모듈 하나를 추
가하는 것으로 끝낸다. 결과는 "바뀐 것" 목록으로 규격화한다.
단계형 판단: 필요하면 저렴한 모델로 "알릴 가치가 있는가"를 먼저 판단하고, 큰 모델은 정리·작성에
만 쓴다. 모델과 노력 수준은 작업별로 설정한다.
알림 묶기: 같은 시간대에 생긴 소식은 브리핑 하나로 묶는다. 방해 금지 시간대를 둔다. 긴급도가 높
은 소식만 예외로 즉시 보낸다.
비용 원장: 실행마다 모델, 토큰, 소요 시간, 출처(루틴·채팅·이벤트)를 기록한다. 일·주 상한을 두고
넘으면 알림 또는 일시 정지한다.
사용량 한도 대응: 구독 한도 소진이나 속도 제한이 걸리면 작업을 대기열로 미루고 알린다.
기억과 연속성
비서의 연속성은 네 층의 기억이 만든다. 항상 읽히는 기억은 작게 유지하고, 나머지는 필요할 때 검색한
다. 사실·선호(기억)와 일하는 방법(스킬)은 서로 다른 곳에 둔다.
맥락 조립: 실행을 시작할 때 데몬이 핵심 기억, 진행 상태 요약, 이번 요청과 관련된 에피소드 검색 결
과를 묶어 넣는다. 맥락에는 크기 예산을 둔다.

약속은 레코드로 남긴다: 에이전트가 "다음 주에 다시 확인할게요" 같은 약속을 하면 반드시 MCP로
후속 조치를 등록한다. 데몬이 그 시각에 상주 세션을 깨운다. 등록되지 않은 약속 표현은 결과 보고
단계에서 감지해 되묻는다.
주기 점검: 일정 간격으로 진행 상태를 훑어 기한 임박, 답이 없는 일, 서로 연결된 소식을 찾고, 필요
하면 먼저 연락한다. 훑을 항목이 없으면 코드 단계에서 끝내 토큰을 쓰지 않는다.
연결해서 다룬다: 새 소식을 처리할 때 관련 진행 상태와 에피소드를 함께 보고, "지난주에 말한 그 과
제의 마감이 바뀜었다"처럼 기존 맥락에 엮어 알린다.
하루 정리: 하루 한 번 에피소드를 요약해 핵심 기억을 갱신하고, 오래된 원본은 정리한다.
쓰기 정책: 에피소드와 진행 상태는 자동으로 기록한다. 핵심 기억은 에이전트가 직접 고치되, 모든
변경을 기록하고 하루 한 번 Discord로 변경 요약과 되돌리기 버튼을 보낸다.
사용자 교정이 우선이다: "그건 틀렸어", "앞으로는 이렇게 해" 같은 교정은 즉시 핵심 기억에 반영한
다.
인젝션 스캔: 핵심 기억과 점검 목록에 들어가는 내용에서 지시문 패턴(지시 무시 문구, 태그 위조, 디
코드 파이프)을 검사한다. 걸리면 반영을 보류하고 알린다.
성공한 작업의 도구화
성공한 작업은 다음번에 더 빠르고 싸게 처리할 수 있는 형태로 굳힌다. Hermes의 자동 스킬 생성을 기
본으로 하되, 반복 작업을 결정적 코드로 옮기는 단계를 하나 더 둔다.
계기: 사용자가 완료로 확인한 작업 중 단계가 많았던 것, 막혔다가 해결한 것, 사용자에게 교정받은
것. 단순 질답은 대상이 아니다.
도구화 사다리: 아래로 갈수록 모델 의존이 줄고 비용이 낮아진다.
1. 스킬(SKILL.md): 절차, 주의할 점, 검증 방법을 적은 문서. 관련 작업 때 불러 쓴다.
2. 스크립트: 스킬 안의 반복 단계를 실행 가능한 스크립트로 만든다. 샌드박스 안에서만 실행한다.
3. 사전 체크 모듈: 주기적으로 반복되는 확인 작업(예: 특정 사이트의 공지 확인)은 데몬의 결정적
모듈로 승격해, 이후에는 모델 없이 돈다. 데몬 코드가 되므로 에이전트는 초안과 PR까지만 만
들고, 반영은 사람이 리뷰한 뒤 한다.
생애 주기:
1. 작업이 끝나면 회고 단계(저렴한 모델)가 재사용 가치를 판단한다.
2. 가치가 있으면 초안을 만들어 시험 상태로 저장한다.
3. 비슷한 작업에서 쓰며 결과를 기록하고, 성공이 쌓이면 활성으로 올린다.
4. 오래 쓰지 않으면 오래됨을 거쳐 보관으로 옮겨 로딩 대상에서 뺀다. 비슷한 스킬은 합치기를
제안한다.
수정: 쓰다가 실패하거나 교정받으면 전체 재작성보다 부분 수정을 우선한다. 모든 개정은 git으로
버전을 남겨 되돌릴 수 있게 한다. 사용 횟수, 마지막 사용, 성공률을 기록한다.

스킬은 권한을 넓히지 못한다. 새 도메인, 새 도구, 외부 쓰기가 필요한 스킬은 사용자 승인 뒤에

읽기 전용 절차만 담은 스킬은 자동으로 저장하되, Discord로 "새 스킬 저장" 알림과 고정·폐기
버튼을 보낸다.
저장 전에 인젝션 스캔을 거친다. 외부 콘텐츠에 있던 지시문을 그대로 옮겨 적지 않는다.
훅, 권한 설정, 데몬 코드는 학습 루프가 건드릴 수 없는 영역이다.
사람이 고정한 스킬은 자동 수정과 보관 대상에서 빠진다.
사용자 명령: "이거 스킬로 만들어", "그 방식 쓰지 마", "이 스킬 고정"처럼 Discord에서 직접 조작할
수 있다.
운영
데몬은 Rust로 만든 단일 바이너리를 systemd 서비스로 돌리고, 조용히 멈추는 일이 없게 한다.
언어와 런타임: Rust(tokio). 라이브러리 후보는 rmcp(MCP), serenity 또는
twilight(Discord), rusqlite 또는 sqlx, axum(로그인 폼·관리 API), tracing이다.
내부 구조: 태스크끼리 메시지를 주고받는 액터형(mpsc)으로 짠다. 공유 상태는 SQLite 하나로 모
은다.
배포: systemd 유닛, Type=notify 와 watchdog(sd-notify). 전용 사용자와 systemd 샌드박
싱 옵션으로 권한을 최소화한다.
네트워크 노출: 로그인 폼, noVNC, 관리 API는 WireGuard 내부에서만 연다. 밖으로 열어야 하면
Traefik 뒤에 두고 인증을 붙인다.
감시: 데몬 상태, 샌드박스 상태, 인증 유효성, 큐 적체를 주기적으로 점검하고 이상이 있으면
Discord로 알린다. 데몬이 죽으면 systemd가 재시작한다.
로깅: 구조화 로그와 작업 원장을 남긴다. 비밀 마스킹 필터는 필수다.
백업: SQLite와 프로필을 정기 백업한다. 인증 정보는 백업에서 뺀다.
업그레이드: Claude Code와 sbx는 버전을 고정하고 수동으로 올린다. 올린 뒤에는 스모크 테스트
작업을 돌린다.
테스트: 실행 계층은 가짜 CLI로 기록된 stream-json을 재생해 테스트한다. 채널 어댑터는 공통 계
약 테스트를 통과해야 한다.
